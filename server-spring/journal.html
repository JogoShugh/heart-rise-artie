The backend tracks garden beds as event-sourced aggregates — nothing about a bed's current state is stored directly, it's folded from an append-only log. Each bed exposes its available actions two ways: HAL-FORMS, embedded inline, and hal-schema-forms, split into three content-addressed layers.

00

Returning to bare soil

why determinism matters before anything else

Content-addressed data never goes stale — a schema's hash is valid forever. Mutable state is the opposite: a bed's status depends on real history, and Postgres doesn't forget between runs. So every session starts by truncating the event log and replanting the same three seed beds.

Planting bed-1 — sowSeed

layer 1 → layer 2 → layer 3, captured live

An EMPTY bed allows exactly one action: sowing a seed. With no Prefer header (rung L0) everything arrives in one response: state, the form, and its full schema.

     -H 'Accept-Profile: <https://github.com/jogoshugh/heart-rise/hal-schema-forms>' \
     http://localhost:8080/beds/1

02

Watering bed-1 — waterCell

the halforms dialect's writable-field check

After sowing, bed-1 is PLANTED and watering is the only legal action. This entry checks the HAL-FORMS dialect specifically for a known historical fault: Kotlin val properties (getter-only, no setter) can cause Spring HATEOAS's reflection-based property inspection to mark a field readOnly: true — confirmed against a real, open Spring HATEOAS GitHub issue (#1310) rather than assumed.

input
curl -H 'Accept: application/prs.hal-forms+json' \
     http://localhost:8080/beds/2
output
id: 2
label: bed-2
status: PLANTED
cropName: tomato
growthPoints: 80
moistureLevel: 40
_links:
  self:
    href: /beds/2
_templates:
  default:
    method: POST
    properties:
      -
        name: milliliters
        min: 1
        max: 1000
        type: number
    target: /beds/2/actions/water-cell
Correct

Every input field renders writable. If this had regressed to val, this check would fail loudly instead of silently shipping a form nobody can fill in.

05

Asking bed-2 what it looked like, in the past

the payoff of event sourcing over current-state storage

Asking for bed-2's state before its first event occurred should return the same thing as a bed with no history at all.

input
curl http://localhost:8080/beds/2?asOf=2026-07-08T00:00:00Z
output
id: 2
label: bed-2
status: EMPTY
cropName: null
growthPoints: 0
moistureLevel: 0
_links:
  self:
    href: /beds/2
_templates:
  default:
    method: POST
    properties:
      -
        name: depthCm
        min: 1
        max: 10
        type: number
      -
        name: seedType
        regex: "^(?=\\s*\\S).*$"
        required: true
        type: text
    target: /beds/2/actions/sow-seed
Correct

Folded state at that instant: status=EMPTY, growthPoints=0 — zero qualifying events folds to the same empty seed state as no history at all.

06

Ways to fail, correctly

distinct failure modes, distinct status codes, checked live

A missing precondition, a stale write, an illegal transition, a bad body, and an unknown resource are different problems. SPEC 0.4 gives each its own code, and checks acts in that order.

Correct

act without If-Match → 428, stale If-Match → 412, act not in the manifest → 409, body fails the schema → 422, unknown schema → 404, Layer 1 revalidation, nothing changed → 304. Each problem has its own code.
