Our Own Controls

GitHub's API takes whatever a client sends. A gateway its owner runs, even on a laptop, can add the controls GitHub lacks. Any client gets most of them by changing its base URL; a HEART client gets all of them.

In short

  • One task, one teammate. A client retitles issue 7 "… (triaged)" and closes it. Right after the client reads it, a teammate on GitHub itself retitles it and closes it as not planned. No model anywhere: every client here is a script.
  • GitHub as it is: the plain client wrote over both of the teammate's changes, 3 of 3, finished with exit 0, and said nothing.
  • Validators alone don't help: the same client sending If-Match lost both changes too. GitHub ignores it on a write.
  • The gateway's offered rung stopped the close with GitHub's own rule, "The issue is already closed.", keeping the teammate's reason; the title was still lost.
  • The gateway's conditional rung refused the stale write (412) and kept both changes, 3 of 3. The task was not done; the client said why.
  • A HEART script kept both changes and did the task on the teammate's new title, 3 of 3, and noted why it didn't close.
  • The window is narrowed, not closed. GitHub has no conditional write, so the gateway checks, then writes. A teammate could only land in between; a client's own read-to-write gap is far wider. On an API we own, the check and the write are one.

  • GitHub guards some of this itself: it checks bodies, and its tokens are scoped. The rungs add what it doesn't: conditional writes, reasons before the act, and policy per operation.
  • The owner turns the rungs on (GATEWAY_DAM). The caller only asks for pass-through (X-Gateway-Mode: pass-through). Refusals are problem+json with GitHub's own message member, so a client written for GitHub reads them.

The window

  • The gateway's check, then write, from its own Server-Timing over 30 writes: read again 0.3 ms, write 0.2 ms (median; slowest write 0.6 ms). Here GitHub is the in-memory small GitHub of the gateway's tests; against GitHub itself the write is GitHub's own latency.
  • A client's own read-to-write gap: a bare script 42 ms; an AI agent at least one model call, 1.3 to 1.7 s (median, Sonnet 5.5, the earlier MCP bench).
  • So the gateway shrinks the window from the client's gap to its own write. It can't close it: GitHub would have to take the condition. On an API we own, it is closed: the employees service checks the version and writes in one step.
How it was run service, teammate, clients
  • Service: heart-sims' GitHub service, the gateway as shipped with its GitHub connector, in front of the small GitHub of its tests; alone on one port (docker run -p 8098:8099 heart-sims 8099 github.test), reset before every run.
  • Teammate: PUT /_sim/github/meddle: right after issue 7 is next read on GitHub, it is retitled "The nightly build is slow on Mondays" and closed as not planned, on GitHub itself, past the gateway.
  • Rungs: PUT /_sim/github/dam with the owner's words.
  • Bare client: scripts/bare.kts: read, retitle from what it read, close. artie generate --bare --validators --through URL writes the same shape from a recorded run (generate-bare.feature).
  • HEART client: scripts/heart.kts: decide { } around the retitle, and the close only if offered.
  • Runs: exhibits/own-controls/ladder.sh 3 and window.sh 30; the lines and traces are in runs/.
Limits said plainly
  • The small GitHub is GitHub's shape, not GitHub. Its write is in memory, so the measured window is the gateway's part alone.
  • The teammate always lands right after the first read: the conflict is certain, not likely. In life it is rarer, and silent when it happens.
  • The offered rung matches a raw write to its act by operation and fixed values. A write no act describes passes it.
  • The described rung checks GitHub's own description, which nests "nullable" in places a JSON Schema validator reads differently; GitHub stays the last word.

Built here

  • GATEWAY_DAM and its four rungs, with Server-Timing on a conditioned write (heart-gateway, github-dam-*.feature).
  • bare(validators = true, headers = …) and artie generate --bare --validators --through (heart-script, artie-cli).
  • The teammate and the owner's rungs for heart-sims' GitHub service; the gateway's guard held for both clients in the shared suite (acts.feature).
