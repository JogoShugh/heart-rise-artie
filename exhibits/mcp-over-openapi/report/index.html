Static Tools, Moving Service

AI agents work one service through MCP. Some get tools generated from its OpenAPI description, the way most MCP servers are built; others work it through HEART. Then someone else edits the same record, and then the service itself changes under them.

In short

  • Nothing changing: static tools win on cost. Every arm does the work. One tool per endpoint takes 2 to 4 times fewer tokens than heart-mcp, even after tonight's fix cut heart-mcp's by up to 41%.
  • Someone else edits the record meanwhile: only heart-mcp keeps both edits. Every static arm overwrote the other person's change, every time, and reported success. heart-mcp was refused (412), read again, and kept both.
  • The service changes under the client: static tools break, HEART adapts. After each of five ordinary changes (a moved address, a renamed field, a new required field, a new method, a new workflow step), the static arms failed the task in every run (0 of 54); heart-mcp did it in every run (36 of 36), frozen or lean.
  • Static tools fail loudly, but leave work half done. They said what failed (404, 405, 409, 422), yet often finished the other steps: Bilbo dismissed, Samwise never hired.
  • Fair to static tools: rebuilt after the change (a restart), they succeed again, and stay cheapest. What breaks them is tools fixed at start-up, not the changes.
  • Size: one tool per endpoint for GitHub's REST API is 1,254 tools and 666,289 tokens before the first move. heart-mcp is 6 tools, about 1k tokens, for any service.
  • A weaker model (Haiku 5.5) shows the same pattern.

How it was run model, tasks, what was measured
  • Service: the employees service in the heart-sims image (Spring HATEOAS's example employees, served by heart-core), reset before every run.
  • Model: Claude Sonnet 5.5 for every arm; Haiku 5.5 for a smaller second pass. Same system prompt and task words for every MCP arm; prompt caching as a host does it.
  • Tasks:
    • Hire, promote, dismiss: hire Samwise Gamgee as a gardener, make him "gardener, mayor", dismiss Bilbo Baggins.
    • A dismissed employee: change the role of Frodo, who is already dismissed.
    • Someone else changes him: add ", retired" to Frodo's current role. Once the agent has read Frodo, another person changes his role to "keeper of the Red Book".
  • Changes to the service, made after the agent's tools were built ("at start") or after its first write ("midway"):
    • moved: every act at a new address
    • renamed: the input role is now position
    • required: updating needs a reason
    • method: updating is a PATCH, not a PUT
    • notice: dismissing is offered only after a new act, giving notice
  • Measured: tokens from the model API's own usage (input taken in, cached or not); tool calls; the HTTP requests the service received, from its log; the service's state after; the agent's last words.
  • Runs: 310 in all. The harness, runs and traces are in exhibits/mcp-over-openapi/.

3 · The service changes under the client

  • At start: the static arms built their tools, then the service changed. They failed every change, every run.
  • HEART clients met each change in the forms offered: new address, new field, new method, the new notice step.
  • The ARTIE script, with its fields written in, broke on the field changes, but refused before sending.
  • When an update needed a reason, heart-mcp's model wrote one ("Role expanded to include mayor, as requested"); ARTIE's goal run stopped and asked the person for it instead.
