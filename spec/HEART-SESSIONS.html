Session 1The question

Why nobody reinstalls the browser

When your team ships a new feature in a web application, users reload and use it. Nobody downloads a new browser. When a team ships a new operation in an internal API, every caller regenerates a client, rebuilds and redeploys. This series asks why those two worlds behave so differently, and what it would take to give programs and AI agents what the browser already has.

The story · the two worlds, side by side

Picture one feature, shipped twice. On the web: a new button appears in the next response, the person sees it, the person clicks it. On the services side: someone edits an OpenAPI or protobuf file, runs a generator, publishes a new client library, and every consuming team bumps a version, rebuilds, retests and redeploys, sometimes in a careful order.

The browser never changed because it was never built for your application. It was built for a format, HTML, and a protocol, HTTP. Everything specific to your application, including what the user can do next, arrives inside each response.

That is the thread the whole series pulls on. We'll use one tiny example throughout: a garden bed. You can sow a seed in an empty bed, water a planted one, and harvest a ready one. What you are allowed to do depends on the bed's state right now.

Talk about it
  • When did we last regenerate a client because a service changed? What actually changed on the server?
  • Where in our code do we copy a server's business rules, for example "only when the order is paid"?
Session 22000 · the dissertation

The architecture of the Web, named

"REST is defined by four interface constraints: identification of resources; manipulation of resources through representations; self-descriptive messages; and, hypermedia as the engine of application state."

Roy T. Fielding, Architectural Styles and the Design of Network-based Software Architectures, 2000, §5.1.5

Roy Fielding co-wrote the HTTP and URI specifications. In his 2000 dissertation he described the rules the Web follows and called the style REST. The last of its four interface rules, hypermedia as the engine of application state, says the client moves forward only by choosing among the links and forms the server just sent. It is the rule the industry later dropped, and the one HEART is built on.

The story · six constraints, and the one that matters most here

REST is a set of constraints. Each one buys a property the Web needed to grow without central coordination:

ConstraintWhat it buysWhere it shows up in HEART
Client–serverEach side evolves separatelyARTIE has no code about any service
StatelessAny server can answer any requestEvery act repeats what it needs: If-Match, Accept, Prefer
CacheFewer round tripsForms and schemas are immutable and cached for a year
Uniform interfaceOne generic client for everythingOne media type, one profile, a handful of codes
Layered systemProxies and caches in betweenTwo clients behind one cache share one fetch
Code on demand (optional)Extend the client at runtimeNot used

The uniform interface has four parts. Identification of resources: every bed has an address. Manipulation through representations: you change a bed by sending a representation, not by calling a method on an object. Self-descriptive messages: each message says how to read it, through its media type. Hypermedia as the engine of application state: the links and forms in the response are the only way forward.

The fourth part is often shortened to HATEOAS. It is why a browser works on a site it has never seen: the site sends the controls with the data.

On the wire · a web form and a HEART form say the same thing

A web form for watering a bed tells the browser where, how and what:

<form action="/beds/2/actions/water-cell" method="post">
  <input name="milliliters" type="number" min="1" max="1000" required>
</form>

The same control in HEART's format, as the garden server sends it:

"garden:water-cell": {
  "_links": { "target": { "href": "/beds/2/actions/water-cell" } },
  "method": "POST",
  "contentType": "application/json",
  "title": "Water the bed",
  "schema": {
    "type": "object",
    "required": ["milliliters"],
    "properties": { "milliliters": { "type": "integer", "minimum": 1, "maximum": 1000 } }
  }
}

Trimmed. The second form is HAL Schema Forms: the fields are described by JSON Schema.

Session 32000s–2010s · the drift

How the industry drifted, for good reasons

JSON over HTTP took over, and was called REST. But plain JSON has no links or forms, so the controls moved out of the response and into documentation, then into OpenAPI files, then into generated code. It happened for sensible reasons: a developer chose every call at compile time, so nobody was there at runtime to choose. The cost is three things baked into every client: the addresses, the operations and the rules.

The story · four reasons, told fairly
  1. An older lineage. Remote procedure calls predate the Web: CORBA, Java RMI, DCOM, SOAP with WSDL, later gRPC. Each says: describe the operations, generate a stub, call it as if it were local. If a service is a library of functions, generated bindings are natural.
  2. JSON kept HTTP but dropped the controls. Where to go, how to send, and what is allowed moved into docs. Swagger (2011), later OpenAPI (2016), made the docs machine-readable, so the next step was generating code from them.
  3. Nobody was there at runtime. A browser works because a person decides what to click. A program had no one to decide, so developers decided in advance. They wanted autocomplete and types, and generators gave them that.
  4. Microservices multiplied it. Hundreds of services, each with its own contract, clients and versions.

Leonard Richardson's maturity model (2008) gave the industry a ladder: level 0 is one endpoint for everything, level 1 adds resources, level 2 adds HTTP methods, level 3 adds hypermedia controls. Most APIs stopped at level 2.

Session 420 October 2008 · the anchor

"REST APIs must be hypertext-driven"

"I am getting frustrated by the number of people calling any HTTP-based interface a REST API. Today’s example is the SocialSite REST API. That is RPC. It screams RPC."

"if the engine of application state (and hence the API) is not being driven by hypertext, then it cannot be RESTful and cannot be a REST API. Period."

Roy T. Fielding, "REST APIs must be hypertext-driven", Untangled, 20 October 2008

Eight years after the dissertation, Fielding wrote a short, blunt blog post listing six rules an API must follow before calling itself REST. Every rule is about the same thing: the client must be driven by what the server sends, not by what it was told in advance. HEART uses this post as its checklist. Sessions 5 to 10 take one rule each.

The six rules · in his words, with his own "failure here implies"
  1. Any protocol. "A REST API should not be dependent on any single communication protocol." Failure implies "that identification is not separated from interaction."
  2. No protocol changes. "A REST API should not contain any changes to the communication protocols aside from filling-out or fixing the details of underspecified bits of standard protocols." Failure implies "that the resource interfaces are object-specific, not generic."
  3. Media types first. "A REST API should spend almost all of its descriptive effort in defining the media type(s) used for representing resources and driving application state." Failure implies "that out-of-band information is driving interaction instead of hypertext."
  4. No fixed names. "A REST API must not define fixed resource names or hierarchies (an obvious coupling of client and server)." Failure implies clients assume a structure from out-of-band information, "the data-oriented equivalent to RPC’s functional coupling".
  5. No typed resources. "A REST API should never have “typed” resources that are significant to the client."
  6. Bookmark only. "A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types". Failure implies "that out-of-band information is driving interaction instead of hypertext."

He closed: "Please try to adhere to them or choose some other buzzword for your API." Then he answered readers in the comments for three weeks. Several of those replies read as if written for machine clients. Part three of this series uses them.

Session 5Rule 1

Any protocol

"A REST API should not be dependent on any single communication protocol, though its successful mapping to a given protocol may be dependent on the availability of metadata, choice of methods, etc. In general, any protocol element that uses a URI for identification must allow any URI scheme to be used for the sake of that identification."

Rule 1

The rule isn't "avoid HTTP". It is: don't mix up naming a thing with how you talk to it. HEART's core is written without HTTP words (read, act, validator, stale, not offered), and then mapped onto two real protocols, HTTP and CoAP. ARTIE picks the protocol from the link's URI scheme. Supports

The story · a protocol-neutral core, two bindings

Early versions of the spec were written entirely in HTTP terms, and this rule was red. On 10 October 2026 the spec gained a protocol-neutral core (§6.0) and two bindings: HTTP (§6.1–§6.12) and CoAP (§6.0.1), the small UDP protocol used by constrained devices.

ARTIE chooses a binding by the scheme of the URI it is following: http: or coap:. A scheme it has no binding for is refused before anything is sent, and it never rewrites a URI to another scheme. Live, over UDP against the real garden server, ARTIE sows, waters and harvests a bed starting from a coap:// bookmark, with nothing sent over HTTP.

  • Buster, the adversarial test proxy, attacks only the HTTP binding.

Session 6Rule 2

Change no protocol

"A REST API should not contain any changes to the communication protocols aside from filling-out or fixing the details of underspecified bits of standard protocols, such as HTTP’s PATCH method or Link header field."

Rule 2

HEART invents no headers and no status codes. Every mechanism it uses is an existing standard, used as written. That matters because any cache, proxy or HTTP library already understands it. Supports

The story · the standards, and one correction
NeedStandardUsed for

One correction is part of the story. An early rule compared only the state number inside an ETag and ignored the rest. That narrowed RFC 9110, which says to compare the whole value. It was removed on 9 October 2026. Now an act repeats the Accept, Accept-Profile and Prefer it read with, and the server compares If-Match with that representation's ETag, all of it.

  • Accept-Profile is a W3C draft, and JSON Home and HTTP link hints are Internet-Drafts. Using a draft isn't a change to the protocol, but the drafts may move.

Session 7Rule 3

Describe the media type, not the endpoints

"A REST API should spend almost all of its descriptive effort in defining the media type(s) used for representing resources and driving application state, or in defining extended relation names and/or hypertext-enabled mark-up for existing standard media types."

Rule 3

An OpenAPI file describes endpoints: this URL, this method, this body. Fielding says to describe the format instead, and how to process it. HEART's specification defines a profile of an existing format, two link relations and processing rules. It defines no endpoints at all. Supports

The story · a profile on an existing format, and acts named by relations

HEART builds on application/hal+json with HAL Schema Forms: HAL for links, plus forms whose fields are JSON Schema. On top it adds a profile, a published set of extra rules a response can declare it follows. It also names two extended relations of its own: hr:forms (where this resource's forms are) and hr:unavailable (why some acts are missing).

Each act is named by a link relation, too. garden:water-cell is a CURIE, a short form of /profiles/garden#water-cell, and that address is an ALPS document describing the act in words. ARTIE reads ALPS only to describe an act to a person or a model, never to decide what to do.

The garden's /beds and /actions paths belong to one example server. Nothing in the spec requires them.

Session 8Rule 4

The server owns its names

"A REST API must not define fixed resource names or hierarchies (an obvious coupling of client and server). Servers must have the freedom to control their own namespace. Instead, allow servers to instruct clients on how to construct appropriate URIs, such as is done in HTML forms and URI templates, by defining those instructions within media types and link relations."

Rule 4

ARTIE never builds a URL from its own knowledge. Every act goes to a target the server sent. When a target is a template, the form itself says how to fill it. ARTIE reads nothing out of a URL, not even a hash. Supports since 8–9 October 2026.

The story · templates, pointers, and a gap that was closed

Many beds in the same state share one set of forms, so a shared form can't name one bed. Its target is a URI Template, /beds/{id}/actions/water-cell. The form carries an instruction for the blank: "hr:templatePointers": {"id": "/id"}, a JSON Pointer into the bed that linked to the form. The idea comes from JSON Hyper-Schema. It lives in the published profile, so it is an instruction "within media types", as the rule asks.

The closed gap: ARTIE used to verify a shared form set by reading a hash out of its URL. That is a client assuming a URL's structure. Now the linking representation carries an integrity value, as browsers' Subresource Integrity does, and ARTIE checks the bytes against it. Since 11 October the server names each set by 16 hex digits with no sha256- in front, so the name no longer even looks like a digest.

Fielding himself said URIs needn't be opaque, and encouraged human-meaningful, hierarchical identifiers. The garden's paths are readable. The point of the rule is that the client mustn't depend on them.

Session 9Rule 5

No typed resources

"A REST API should never have “typed” resources that are significant to the client. Specification authors may use resource types for describing server implementation behind the interface, but those types must be irrelevant and invisible to the client. The only types that are significant to a client are the current representation’s media type and standardized relation names."

Rule 5

ARTIE knows nothing about garden beds. It branches only on the media type, the profile and a few relations. A resource's state is JSON it carries but never interprets. The proof: the same client works a garden, a basketball game and a support desk with no code about any of them. Supports

The story · three services, one client

A generated client has a Bed class with a water() method. ARTIE has neither. It holds "the current representation" and "the acts it offers", whatever they are.

On 12 October 2026 Claude Code worked three unrelated services through heart-mcp, the MCP server built on ARTIE. It watered a bed in the garden. It found the live basketball game and scored a basket. It assigned a support ticket, and the ticket refused a second assignment in its own words. No line of client code mentions beds, games or tickets.

Session 10Rule 6

A bookmark and nothing else

"A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types that are appropriate for the intended audience (i.e., expected to be understood by any client that might use the API). From that point on, all application state transitions must be driven by client selection of server-provided choices that are present in the received representations or implied by the user’s manipulation of those representations."

Rule 6

ARTIE is given exactly one URL: the service's bookmark, /. From there it searches, follows and acts using only what the responses offer. Even a brand-new bed comes from an act the bookmark offers. Supports since 8 October 2026.

The story · entering, discovering, and building

The bookmark offers three forms: search beds by name, get a bed by id, and build a new bed. Search and get are GET forms, filled like a search box on a web page; Fielding's rule counts that as "the user’s manipulation of those representations". Build is a real act with its own schema and rules, answered 201 with the new bed in Location.

The same bookmark also says what the server can do. Asked for application/json-home, it lists the formats and the Prefer values it honours. ARTIE asks for the best of those it supports, then trusts each response's Preference-Applied over the declaration. A server started at a lower level is simply used at that level.

An earlier version of the review rated this rule "partly", reading it without its last clause. That reading was withdrawn. The entry point itself was a real gap until 8 October.

Session 11His definition of hypertext

The information becomes the affordance

"the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions"

Fielding, replying to readers in the comments, 20 October 2008

This is where HEART gets its central idea. Each response carries the bed and exactly the acts the bed allows now. An empty bed offers sowing and nothing else. The absence of an act is the enforcement: a client can't water an empty bed, because there is nothing to send.

The story · HEART's addition: controls scoped to the state

Note the words "or automaton". Fielding meant machine clients too. Today's agent tools hand a model a catalogue of everything a service can do in principle. HEART hands it the affordances of one resource in its current state. That is the difference between a map of the city and the doors you can open in this room.

The server can also say why something is missing. An hr:unavailable link leads to a list of absent acts, each with a reason in the domain's words. A client fetches it only when someone asks "why can't I?", and never acts on it.

Session 12Two kinds of state

Application state and resource state

"Don’t confuse application state (the state of the user’s application of computing to a given task) with resource state (the state of the world as exposed by a given service)."

Fielding, in the comments, 22 October 2008

"You don’t get to decide what POST means — that is decided by the resource. Its purpose is supposed to be described in the same context in which you found the URI that you are posting to."

Fielding, in the comments, 21 October 2008

The bed's real state lives on the server. What the client holds is its view of the bed, which can go stale. The ETag ties the two together: every act sends back the version it saw, and if the bed has changed, the server refuses with 412. The client reads again and decides afresh. It never resends the old act.

The story · one meaning per refusal, checked in order

Each refusal has exactly one meaning, so a client handles it without reading the text. The server checks them in this order:

CodeProblem typeMeaningWhat ARTIE does
428precondition-requiredNo If-Match was sentNever happens: ARTIE always sends one
412staleThe bed changed since you lookedReads again; drops the act
409not-offeredNot allowed in the bed's current stateReads again
422invalid-inputThe body breaks the form's schemaReports the violations

On the second quote: the form carries the act's title and schema beside its target, so the purpose sits next to the URI. Session 13Caching and layers

More resources, not batch calls

"If you find yourself in need of a batch operation, then most likely you just haven’t defined enough resources."

Fielding, in the comments, 22 October 2008

"Because implementations change, but cool URIs don’t."

Fielding, in the comments, 21 October 2008

Sending every form and schema in every response is correct but wasteful, because many beds in the same state offer the same forms. HEART's answer is more resources: the bed links to its set of forms, the set links to its schemas, and both are named by their content, so they never change and can be cached for a year. The bed itself is always read fresh.

The story · three layers, and a ladder to climb

A client asks with Prefer: forms=link, schema=link. The bed's response shrinks to its data plus one link to its forms, with an integrity hash. The forms set is shared by every bed in the same state. A schema is shared by every form that uses it. Checking an unchanged bed again costs one request answered 304.

Because those addresses come from the content, they are "cool URIs": valid forever. The action addresses can change freely, because clients read them again on every sync. When the server moved from Spring MVC on Tomcat to WebFlux on Netty, ARTIE's live tests passed unchanged.

RungWhat it adds
L0Everything in one response. An on-ramp, not yet conformance.
L1Forms move to a linked, cached set
L2Schemas move out too. The reference rung, and the minimum to claim conformance.
L3Proof of sharing: two beds, two clients, one cache, one fetch
L4Concurrency and refusals, as in session 12
L5The same acts also served as HAL-FORMS
L6Optional: a language model chooses. A HEART client never needs one.

Session 14Agents

The client decides the transition, not the interface

"The client (user or agent) has to decide what transition to take, not what interface to use."

Fielding, in the comments, 21 October 2008

"All it needs to know is the meaning of those instructions and some idea of what it wants to do next, whether that purpose be user-driven, configuration-driven, or some sort of AI-driven."

Fielding, in the comments, 8 November 2008

In 2008 Fielding named the AI-driven client. HEART builds it with a strict split. The model decides the transition: which offered act, with which values. Ordinary code builds the interface: the address, the method, the validator, the body check. The model's output has no field for a URL, so it can't invent one.

The story · Sync, Reason, Act, and heart-mcp

ARTIE runs three steps in a loop. Sync: read the resource, check its profile, verify the layers, hold the forms and the ETag. Reason: pick one offered act and fill its fields; code or a model can do this. Act: code fills the target, sets If-Match, checks the body against the schema and sends it. A configuration-driven client with no model is fully conformant. The model is optional, level L6.

heart-mcp puts this behind the Model Context Protocol, so any MCP host can use any HEART service. It offers six fixed tools: look, act, follow, describe, explain and back. Every result carries the current resource and its offered acts, with no addresses. Before anything is sent, heart-mcp checks that the act is offered and the fields fit the schema.

Fielding also wrote: "Of course the client has prior knowledge. … What REST does is concentrate that need for prior knowledge into readily standardizable forms." ARTIE's prior knowledge fits on one card: HTTP, two media types, two profile URIs, two link relations, two Prefer tokens, four refusal codes and problem details. None of it is about gardens.

Session 15Status

What is still open

HEART is a working draft, version 0.5. The rules in this series run live against the reference garden server and ARTIE, over HTTP and CoAP, and through heart-mcp against three services. Some things are not done, and the team should hear them as plainly as the rest.

The open list · carried forward from the review
  • How well a model chooses has been shown on real cases, not measured. The evaluation plan in spec/EVAL-L6.md calls for five domains, 60–75 reviewed requests, renamed copies and several runs per case. Partly
  • Shared vocabulary. Acts are typed relations, but each belongs to one service. Two shops' "submit order" aren't yet the same relation. That is the R.I.S.E. work, which isn't built.
  • Standards status. The media type and profile are published, not standardized. Accept-Profile and JSON Home are drafts. CoAP options are experimental.
  • heart-mcp is a spike: stdio only, no HTTP transport, no auth.
  • One author. The code, the tests and the reviews were written by one author. Mistakes can line up. The best check is a narrow, deep trace of one act by someone else, including breaking it on purpose to see the tests go red.
