From the Web to HEART

How the browser learned to work any website without knowing it in advance, how JSON APIs lost that ability, and how HEART gives it back so an AI agent can use a service the way a person uses a website. Then one plain data API, changed step by step until it speaks HEART's profile of HAL Schema Forms.

1. The landscape 2. Evolving one API 3. The agent's loop 4. Checklist

1. The landscape

Every example below talks to the same thing: a garden bed. You can sow a seed in an empty bed, water a planted one, and harvest it when it is ready. What you are allowed to do depends on the bed's state right now. That last sentence is the whole story.

  1. 1989–1995

    The Web: a client that knows nothing about the site

    Tim Berners-Lee combined three things: URIs to name resources, HTTP to transfer them, and HTML to represent them. HTML carries the data and also the controls: links to follow and forms to fill in. A browser knows HTML and nothing about any particular shop or bank. The site tells it, in every response, what can be done next. When the site changes, nobody reinstalls the browser.

  2. 2000

    REST names why it works

    Roy Fielding's dissertation describes the Web's architecture as REST. One of its constraints is "hypermedia as the engine of application state": the client moves from state to state only by choosing among the links and forms the server sent. This is what lets clients and servers change independently.

  3. 2000s–2010s

    JSON APIs drop the controls

    Programs started talking to servers in JSON over HTTP, and called it REST. But JSON has no links or forms, so the controls moved out of the response and into documentation: which URL to build, which method, which body, and which rules apply. Swagger (2011), later OpenAPI (2016), made that documentation machine-readable. Clients hard-code the URLs and the rules. In 2008 Fielding objected: "REST APIs must be hypertext-driven." Leonard Richardson's maturity model (2008) put hypermedia at the top level, and most APIs stopped below it.

  4. 2011 onward

    Hypermedia JSON formats appear

    Several formats put links and forms back into JSON: HAL (Mike Kelly, 2011) for links, Siren, JSON Hyper-Schema, HAL-FORMS (Mike Amundsen) and HAL Schema Forms (forms whose fields are JSON Schema). They worked, but they stayed niche, because a developer was writing each client by hand from the docs anyway.

  5. 2023 onward

    AI agents get a catalogue, not a map

    Agents call APIs through tool definitions: function calling, OpenAPI documents in the prompt, tool search, and the Model Context Protocol (MCP, 2024). Each gives the agent a list of what the system can do in principle. None says what is allowed for this bed now. So an agent tries "water bed 1", and only learns from the refusal that nothing is planted.

  6. 2026

    HEART: the browser's idea, for agents

    H.E.A.R.T. (Hypermedia Enforced Agentic Reliable Transactions) puts the controls back in the response, scoped to one resource in its current state. An agent gets the bed and exactly the acts the bed allows now. An act that is not offered is not allowed: the absence is the enforcement. ARTIE is the reference client. An agent built on it can work a garden, a basketball game or a ticket desk with no code about any of them.

2. Evolving one API

We start with an ordinary data API and add one idea at a time. Each step shows what goes on the wire. Lines in green are new in that step. The responses come from the reference garden server, trimmed with ….

0The starting point

A data API: state only

GET /beds/1   Accept: application/json
HTTP/1.1 200 OK
Content-Type: application/json

{"id":1, "label":"bed-1", "status":"EMPTY", "moistureLevel":0}

Everything else lives in a document the client's developer read once:

API docs (out of band)
POST /beds/{id}/sow-seed    body {"seedType":string, "depthCm":1..10}   only if status is EMPTY
POST /beds/{id}/water-cell  body {"milliliters":1..1000}            only if a seed is planted
POST /beds/{id}/harvest     body {}                                 only if READY_TO_HARVEST
What goes wrong

The client builds URLs itself, and copies the rules about status into its own code. When the server changes a rule or a path, the client breaks or quietly does the wrong thing. An agent given these docs will try acts the bed does not allow, and learn the rules by being refused. Two clients acting at once can overwrite each other.

1Adds a hypermedia type and links

Say it is HAL, and link instead of documenting

GET /beds/1   Accept: application/hal+json
Content-Type: application/hal+json

{"id":1, "label":"bed-1", "status":"EMPTY", "moistureLevel":0,
 "_links":{"self":{"href":"/beds/1"}}}
Why

The media type tells the client how to read the response, the way text/html does for a browser. Addresses now come from the server inside _links, so the client stops building them. HAL alone can only say "go there". It cannot say "send this".

2Adds forms, only the legal ones

Put the acts in the response, with HAL Schema Forms

{"id":1, "status":"EMPTY", …,
 "_links":{"self":{"href":"/beds/1"}},
 "_forms":{
   "sow-seed":{
     "_links":{"target":{"href":"/beds/1/actions/sow-seed"}},
     "method":"POST", "contentType":"application/json",
     "schema":{"type":"object", "required":["seedType"],
       "properties":{"seedType":{"type":"string","minLength":1},
                     "depthCm":{"type":"integer","minimum":1,"maximum":10}}}}}}
Why

Each form carries everything needed to act: where, how, and what the body must look like. The important part is what is missing. Bed 1 is empty, so it offers only sow-seed. Watering and harvesting are not in the response, so the client cannot even try them. Bed 2, which is planted, would offer water-cell instead. The rule about status has moved from the client's code into the server's response. At this point the API is like a website again.

3Adds meaning: relations, a profile, descriptions

Name each act so a stranger can understand it

Link: <https://w3id.org/heart-rise/hal-schema-forms>; rel="profile"

{… "_links":{"self":{"href":"/beds/1"},
   "curies":[{"name":"garden","href":"/profiles/garden#{rel}","templated":true}]},
 "_forms":{
   "garden:sow-seed":{
     "title":"Sow a seed",
     "description":"Plants a seed in an empty bed. The bed becomes planted.",
     …
     "schema":{… "seedType":{"type":"string", "title":"Seed", "description":"The kind of seed to sow", "examples":["basil"]} …}}}}
Why

The profile link tells the client this response follows HEART's profile of HAL Schema Forms, so it may rely on the profile's rules. The form's name is now a link relation. garden:sow-seed is a short form (a CURIE) of /profiles/garden#sow-seed, and that address is a description of the act in an ALPS profile. A client learns the CURIE and the profile from the response itself, during the interaction. Titles, descriptions and examples are written for whoever chooses: a person, or a language model.

4Adds safe acts: validators and clear refusals

Act only on the state you saw

GET /beds/1
ETag: "seq-0.hsf.L0"
Cache-Control: no-cache

POST /beds/1/actions/sow-seed
If-Match: "seq-0.hsf.L0"
Content-Type: application/json

{"seedType":"basil"}

The ETag names the version of the bed the client saw. Every act sends it back in If-Match. If the bed has changed since, the server refuses. Each refusal is an RFC 9457 problem details body with its own type, and the server checks them in this order:

CodeMeaningReal detail from the garden
428No If-Match was sentgarden:water-cell needs a validator: the current one of the resource offering it
412Stale: the bed changed since you lookedthe validator does not match the current one of the selected representation
409Not offered in the bed's current stategarden:harvest is not offered now: Nothing is growing yet; sow a seed and water it until it is ready.
422invalid-input: the body breaks the form's schema/depthCm: must have a maximum value of 10
422rule-refused: the body is valid, but a rule of the resource says noThe bed would be waterlogged: at most 600 ml now.
Why

Two clients can no longer overwrite each other. On a 412 the client fetches the bed again and decides afresh. It never resends the old act. Each code has exactly one meaning, so a client handles refusals without reading the text.

5Adds one entry point

Start from a bookmark, nothing else

GET /   Accept: application/hal+json
{"title":"Garden beds",
 "_forms":{
   "garden:search-beds":{"_links":{"target":{"href":"/beds{?name}","templated":true}}, "method":"GET", …},
   "garden:get-bed":{"_links":{"target":{"href":"/beds/{id}","templated":true}}, "method":"GET", …},
   "garden:build-bed":{"_links":{"target":{"href":"/actions/build-bed"}}, "method":"POST", …}}}
Why

A client needs to know only one URI. From the bookmark it can search for a bed by name, go to a bed by id, or build a new one. A new bed comes from an act the bookmark offers, with its own form and rules. It is not a generic "create" on a collection. Asked for application/json-home, the same / also lists the formats and the Prefer options the server supports.

6Adds layers, so the forms can be cached

Send the state, and link to the forms

Until now every response repeats every form and schema. That is correct but wasteful. Many beds are in the same state and offer the same forms. A client may ask for the forms and schemas as separate, cacheable resources:

GET /beds/2   Prefer: forms=link, schema=link
ETag: "seq-3.hsf.L2"
Preference-Applied: forms=link, schema=link

{"id":2, "status":"PLANTED", "cropName":"tomato", …,
 "_links":{"self":{"href":"/beds/2"},
   "hr:forms":{"href":"/affordance-sets/aab67c2bd106ace1",
               "integrity":"sha256-qrZ8K9EGrOGeWjyrqHskN7gZvS6ib1NGBk3/Vnx2JaM="}}}

GET /affordance-sets/aab67c2bd106ace1      (shared by every bed in this state; cached for a year)
{"_forms":{"garden:water-cell":{
   "_links":{"target":{"href":"/beds/{id}/actions/water-cell","templated":true}},
   "hr:templatePointers":{"id":"/id"},
   "method":"POST", "title":"Water the bed", …,
   "schema":{"$ref":"/schemas/7f232c04c52671dd",
             "hr:integrity":"sha256-fyMsBMUmcd0HdvI4xkfZO3dvViJqO0HdGynlKasuMdQ="}}}}

GET /schemas/7f232c04c52671dd             (shared by every form that uses it)
{"type":"object", "required":["milliliters"],
 "properties":{"milliliters":{"type":"integer","minimum":1,"maximum":1000, …}}}
Why

The bed itself is never cached as fresh: it can change at any moment. The forms and schemas are named by their content, so they never change and are served immutable. A shared set cannot name one bed, so its target is a URI Template, and hr:templatePointers says to fill {id} from /id in the bed that linked to it. The client checks every fetched set and schema against the integrity hash in the link that led to it, so a year-old cached copy can be trusted. The bed's own response is now small, and checking an unchanged bed again costs one request answered 304.

These choices form a ladder. A server can climb it one rung at a time:

  • L0Everything in one response, no special headers (steps 1–5). An on-ramp: it gives correct behaviour, but is not yet HEART conformance.
  • L1Prefer: forms=link: the forms move to a linked, cached set; schemas are still inside it.
  • L2Prefer: forms=link, schema=link: schemas move out too. The reference rung, and the minimum to claim conformance.
  • L3Proof of sharing: two beds in one state, two clients, one cache, one fetch of the set.
  • L4Concurrency and refusals: 428, 412, 409, 422, as in step 4.
  • L5Cross-dialect: the same acts also served as HAL-FORMS, an L0 on-ramp format.
  • L6Optional: a language model chooses the act. A HEART client never needs a model.
7Optional: explains what is missing

Say why an act is absent

"hr:unavailable":{"href":"/unavailable/d1995ab17483fab3", "integrity":"sha256-0Zla…"}

GET /unavailable/d1995ab17483fab3
{"unavailable":[
  {"rel":"/profiles/garden#water-cell","reason":"Nothing is planted yet; sow a seed first."},
  {"rel":"/profiles/garden#harvest","reason":"Nothing is growing yet; sow a seed and water it until it is ready."}]}
Why

When a person asks "why can't I water bed 1?", the client can answer from the server's own words. It fetches this only when asked, and never acts on it.

3. The agent's loop

A HEART client runs the same three steps over and over: Sync, Reason, Act.

  1. Sync. Fetch the resource, check the profile, follow and verify the layers, and hold the bed with its current forms and ETag.
  2. Reason. Pick one of the offered acts and fill in its fields. Code or a language model can do this. A model sees only the forms, their titles, descriptions and schemas. Its whole output is a choice such as "act garden:water-cell with {"milliliters":250}", or "follow item titled bed-2", or "ask the user". It has no way to write a URL, a method or a header.
  3. Act. Ordinary code fills the template, sets the method and If-Match, checks the body against the schema, and sends it. The answer is the bed's new state with its new forms, so the loop starts again. On a refusal, the client syncs and reasons again.

4. Checklist: from data API to HEART

  • Serve application/hal+json, and send Link: <…/heart-rise/hal-schema-forms>; rel="profile".
  • Give every resource _links.self, and link instead of documenting URLs.
  • Put the acts in _forms, with target, method, content type and a JSON Schema, and only the acts legal in the current state.
  • Name each form by a link relation (a CURIE), described in an ALPS profile, with a title and a description; annotate each field.
  • Send a strong ETag and Cache-Control: no-cache on every resource. Require If-Match on every act.
  • Refuse with problem details, checked in order: 428, 412, 409, 422.
  • Offer one bookmark that reaches everything, new resources included.
  • Honour Prefer: forms=link, schema=link: content-addressed, immutable affordance sets and schemas, linked with integrity, and hr:templatePointers for shared targets. Report what you did in Preference-Applied.
  • Optionally, explain absent acts with hr:unavailable.

H.E.A.R.T. is a working draft (version 0.5). L0 to L2 run live against the reference garden server and the ARTIE client; L6 has been tested with a scripted reasoner and once with a real model. R.I.S.E., the companion protocol for system-to-system exchange, is not built. The wire samples on this page come from the garden server on 12 October 2026.
