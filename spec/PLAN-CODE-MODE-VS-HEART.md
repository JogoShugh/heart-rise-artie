# Plan: code mode against ARTIE's kept script as data, run again and again while things change

Status: proposed, 2026-11-02. Follows spec/PLAN-KEPT-SCRIPTS-AS-DATA.md (steps 1 to 4 done) and the code-mode
discussion of the same day. The bench is `exhibits/mcp-over-openapi/bench.py`, extended (it predates the no-Python
rule and was allowed for this experiment).

## The question

A repeatable business process, run many times, while a teammate changes records and the service changes a field.
Which client keeps doing the right thing, at what cost in tokens, and what does it need to run safely?

- **Code mode, steelmanned** (Anthropic, "Code execution with MCP", 2025-11-04; Cloudflare's Code Mode): a model
  writes a program against an API's functions, and a sandbox runs it. Credited plainly; its token savings are
  real.
- **ARTIE as data:** a model does the task once; `artie generate --format yaml` keeps it; `artie run` replays it,
  held to the server's controls, with no model and no sandbox.

## The arms

| Arm | How it runs each time | Model each run | Sandbox |
|---|---|---|---|
| `code-fresh` | The model writes a program for the task from the API's functions; the sandbox runs it; the model sees the output and may write again, up to 5 turns | yes | yes |
| `code-saved` | The first program that finished is saved, reviewed once, and run again each time; if it fails, the model writes a new one from the error (its own fallback, the steelman) | only on failure | yes |
| `artie-data` | One goal run with the model; the kept `.heart.yaml` replayed each time; a changed form falls back to its words (`on-change: intent`) | only on change | no |

Same model (Sonnet 5.5), same task words, same service, same system prompt where a model is used.

## The service and the task

The employees service of heart-sims (`employees.test`), our own API: HEART for ARTIE, its OpenAPI twin for code mode
(the same operations). Checked 2026-11-02: a plain JSON read carries no `ETag`, and the twin declares neither `ETag`
nor `If-Match`, though a write with a stale `If-Match` is refused (412). So code mode can't make a conditional write
today; the steelman fixes that first (step 0). Two tasks of the earlier bench:

- **t3:** "Frodo Baggins is retiring: add ', retired' to the end of his current role."
- **t1:** hire, promote, dismiss.

## The changes, across the runs

N = 10 runs per arm per task, in order:

| Runs | What changes |
|---|---|
| 1 to 3 | nothing |
| 4 to 6 | a teammate changes Frodo right after the client reads him (`PUT /_sim/employees/meddle`) |
| 7 to 10 | the service renames a field the task writes (`PUT /_sim/employees/changes`, `renamed`), as a release would |

## What is measured, per run

| Measure | How |
|---|---|
| Right behaviour | the bench's own check per task (t3: the teammate's role kept and ", retired" added, or the change said) |
| Wrong writes | a write over the teammate's change (a lost update), or a write the service refused |
| Variance | `code-fresh`: distinct programs (by hash) and distinct HTTP call sequences across the 10 runs; the others: distinct call sequences |
| Tokens | from the API's usage, per run and in total |
| What it needed to run | sandbox or not; a model or not; a person's review |

## The sandbox (code mode's, as its makers advise)

- A Docker container, `python:3.12-slim`, on a Docker network marked internal that holds only the heart-sims
  container: it reaches the service, nothing else.
- Read-only code, no secrets inside but the service's test token, a CPU and time limit, removed after each run.
- The functions the program calls: one per operation of the OpenAPI twin, generated by the bench from the
  description at run time (`api.update_employee(id, body, if_match=None)`), each returning the JSON and the `ETag`.
  So code mode can do what HTTP offers (conditional writes), if the model chooses to.

## Steps

0. **The twin, made fair** (heart-core, test first): a plain JSON read answers with the resource's `ETag`, and the
   OpenAPI twin declares it on the read and `If-Match` on each write, as the HEART side has them. Then the
   function library can offer conditional writes, and a model can use them.
1. The sandbox and the function library; a hand-written program run in it against the service (no model).
2. The `code-fresh` arm in the bench: the model's tool is `run_program(code)`, with the functions' signatures in its
   prompt; one run of t3, by hand.
3. `code-saved`, with its fallback; `artie-data`, from a goal run's capture.
4. The changes across the runs (`--sequence`).
5. The runs: 3 arms × 2 tasks × 10. Then a report: one table per task, the measures above, the variance, the tokens;
   where code mode did well, said so.

## Cost and limits

- Model cost: `code-fresh` about 20 runs × up to 5 model calls; `code-saved` and `artie-data` only on failure or
  change. Estimated well under the bench's earlier runs.
- The employees service is ours, so its controls are built in. GitHub through the gateway is the next step, if this
  says something worth saying.
- One model, one service, 10 runs: a demonstration, not a statistic.

## Gate notes

- Step 0 changes heart-core: feature first, a red run at test level logged, then the code; heart's TCK and the
  domains stay green. No change to spec/SPEC.md is expected; if the twin's rules are written there, stop and ask.
- The bench is an exhibit, not product code. If ARTIE needs a change (the renamed-field fallback, say), it is test
