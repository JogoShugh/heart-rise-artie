The six rules

Full exchanges. Each one starts from the rule as Fielding wrote it.

Rule 1

Any protocol, any URI scheme

"A REST API should not be dependent on any single communication protocol … any protocol element that uses a URI for identification must allow any URI scheme to be used"Fielding, 20 Oct 2008, rule 1
Roy Bott

Every example you've ever shown me is HTTP. Is the HTTP-only part your examples, or your client?

Josh

It's just the examples. The spec has a protocol-neutral core: read, act, validator, stale, not offered, invalid. Each of those maps to a binding. ARTIE picks the binding from the URI's scheme. Tonight's live run took bed 1 through sow, water and harvest over CoAP on UDP 5683. Here's ARTIE's own decision log from that run:

// server-spring/build/artie-events.jsonl, 01:05:58Z
{"event_name":"act.sent",
 "body":"sent garden:sow-seed with validator da37a3acbb86a10d",
 "attributes":{"url.full":"coap://localhost:5683/beds/1/actions/sow-seed",
   "heart.method":"POST", "heart.if_match":"da37a3acbb86a10d",
   "heart.code":"2.04"}}

That scenario ends by checking that nothing went over HTTP. It passed, and so did the CoAP version at L2 and the one from the CoAP bookmark.

Roy Bott

An 8-byte validator. HTTP gives you more than that. Are these the same ETags in a shorter coat?

Josh

Yes. Eight bytes is CoAP's limit, so the binding uses a short form of the same validator. The refusals are the same problem types under CoAP codes: 4.12, 4.09, 4.22. The client tests check that each one maps to the same refusal in the core.

Roy Bott

And the options that carry your profile and Prefer? CoAP has no such options.

Josh

We put them in the experimental range, one for one with their HTTP headers:

// client/src/main/kotlin/heart/CoapBinding.kt:79
val ACCEPT_PROFILE = StringOptionDefinition(65_000, "Accept-Profile", …)
val NO_CACHE = EmptyOptionDefinition(65_003, "No-Cache")
val PREFER = StringOptionDefinition(65_004, "Prefer", …)

They aren't registered with IANA, there's no coaps, and HAL-FORMS isn't served over CoAP. Also, the log shows "span_id":"" on the CoAP lines, because a CoAP request carries no trace context yet.

flowchart LR

enter · act · follow"] --> B{"URI scheme"}
  B -- "http:" --> H["HttpBinding

  B -- "coap:" --> C["CoapBinding

same services, same act checks"]
  C --> S
✓ Supports

Two real bindings, picked by scheme, live tonight. The gaps are about registration and hardening, not about the rule: unregistered option numbers, no coaps, and no trace context over CoAP.

Rule 2

No changes to the protocols

"A REST API should not contain any changes to the communication protocols aside from filling-out or fixing the details of underspecified bits of standard protocols"Fielding, 20 Oct 2008, rule 2
Roy Bott

Show me a response and I'll tell you which headers you invented.

Josh

Bed 1, asking for L2:

$ curl -si localhost:8080/beds/1 -H 'Accept: application/hal+json' -H 'Prefer: forms=link, schema=link'
HTTP/1.1 200 OK
Content-Type: application/hal+json
ETag: "seq-0.hsf.L2"
Cache-Control: no-cache
Link: <…/heart-rise/hal-schema-forms>; rel="profile", <…/heart-rise>; rel="profile"
Vary: Accept, Prefer, Accept-Profile
Preference-Applied: forms=link, schema=link

Every header there is a standard. Prefer and Preference-Applied are RFC 7240, which allows tokens of your own. The profile link is the W3C profile-negotiation draft. The rest is RFC 9110 and 9111.

Roy Bott

Acts are where people usually bend things. What does a stale write get back?

Josh

Bed 2 was at seq-3, and I sent the old seq-0:

$ curl -si -X POST localhost:8080/beds/2/actions/water-cell -H 'If-Match: "seq-0.hsf.L0"' …
HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json

{"type":"…/heart-rise/problems/stale","title":"The act is stale: the state has changed","status":412,
 "detail":"the validator does not match the current one of the selected representation"}

The comparison is strong, over the whole ETag, as RFC 9110 §13.1.1 says. We used to read only the state number inside it. That was a narrowing of the standard, so we removed it in e2a773f.

Roy Bott

And the drafts?

Josh

Accept-Profile is a W3C draft. JSON Home and link hints are Internet-Drafts. Using a draft doesn't change the protocol, but a draft can move under us.

✓ Supports

Standard mechanisms used as written, and the one narrowing is gone. Keep an eye on the drafts.

Rule 3

Effort goes into media types and relations

"A REST API should spend almost all of its descriptive effort in defining the media type(s) used for representing resources and driving application state, or in defining extended relation names and/or hypertext-enabled mark-up for existing standard media types."Fielding, 20 Oct 2008, rule 3
Roy Bott

How many endpoints does your spec document?

Josh

None. It defines a profile of HAL Schema Forms, two relations (hr:forms and hr:unavailable), and the rules for processing the layers. The garden adds its own relations, each named by a CURIE that expands to a fragment of its profile:

"curies":[{"name":"garden","href":"/profiles/garden#{rel}","templated":true},
          {"name":"hr","href":"https://github.com/jogoshugh/heart-rise/rels/{rel}",…}],
"_forms":{"garden:sow-seed":{"title":"Sow a seed","method":"POST", …}}
Roy Bott

So /beds and /actions are the garden's business, not the spec's?

Josh

Yes. The same HEART library also runs a basketball game and a ticket desk, on different paths, and each runs the same conformance features. Tonight I ran them against the garden only.

✓ Supports

The descriptive effort goes into a profile, relations and processing rules. Paths belong to the example.

Rule 4

No fixed names; the server teaches URIs

"A REST API must not define fixed resource names or hierarchies … allow servers to instruct clients on how to construct appropriate URIs, such as is done in HTML forms and URI templates"Fielding, 20 Oct 2008, rule 4
Roy Bott

Your L2 affordance set is shared by many beds, so its target can't name one bed. Who fills in the {id}?

Josh

The form says how:

$ curl -si localhost:8080/affordance-sets/588773b4c4ba671e
Cache-Control: public, max-age=31536000, immutable
{"_forms":{"garden:sow-seed":{
   "_links":{"target":{"href":"/beds/{id}/actions/sow-seed","templated":true}},
   "hr:templatePointers":{"id":"/id"},
   "schema":{"$ref":"/schemas/8547ad80c90a3125","hr:integrity":"sha256-hUet…/s="}, …}}}

/id is a JSON Pointer into the bed's own representation, and the idea comes from JSON Hyper-Schema's templatePointers. ARTIE's act() takes a relation name and a body, never a URL.

Roy Bott

Those addresses, 588773b4c4ba671e, look like hashes. Does your client read them?

Josh

No, it reads nothing from a URL. It checks the bytes against the integrity the link carried:

$ curl -s localhost:8080/affordance-sets/588773b4c4ba671e | openssl dgst -sha256 -binary | base64
WIdztMS6Zx56SESW+RccbZJiq08B5t1TG6arfbMFom4=
# the hr:forms link on bed 1 said: "integrity":"sha256-WIdztMS6Zx56SESW+RccbZJiq08B5t1TG6arfbMFom4="

As of today the address is only a short name the server picked. Integrity is the only check. The client tests include a URL shaped like a hash, and ARTIE ignores it.

Roy Bott

Then your review document is wrong. It still says the reference server uses /sha256- paths.

Josh

Fair. We dropped the prefix in dce1fa9, and the review still cites b7f4d00. The rule holds, but the document needs updating.

✓ Supports

The server teaches every URI, through templates and pointers. The client reads nothing from a URL. One fix needed: §Rule 4 of FIELDING-REVIEW.md still describes /sha256- paths.

Rule 5

No typed resources

"A REST API should never have “typed” resources that are significant to the client … The only types that are significant to a client are the current representation’s media type and standardized relation names."Fielding, 20 Oct 2008, rule 5
Roy Bott

Does ARTIE know it's looking at a bed?

Josh

No. It branches on two things only: the dialect, from the media type plus the profile, and the relations. State is JSON it carries without interpreting. The word "bed" appears only in test data. The architecture test that ran tonight also checks that only the Transport and Binding classes import network libraries.

// client/src/main/kotlin/heart/Dialect.kt
enum class Dialect(val mediaType: String, val profile: String, val maxRung: Rung) {
    HAL_SCHEMA_FORMS(HAL_JSON, HAL_SCHEMA_FORMS_PROFILE, Rung.L2),
    HAL_FORMS("application/prs.hal-forms+json", "…/heart-rise/hal-forms", Rung.L0),
}
Roy Bott

A bed's status says READY_TO_HARVEST. Does ARTIE ever read it to decide something?

Josh

Only the tests read it, to check results. ARTIE decides from what's in _forms. When the bed is ready, the only form left is garden:harvest.

✓ Supports

The only types the client cares about are the media type, the profile and the relations.

Rule 6

Bookmark and media types only

"A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types that are appropriate for the intended audience … From that point on, all application state transitions must be driven by client selection of server-provided choices that are present in the received representations or implied by the user’s manipulation of those representations."Fielding, 20 Oct 2008, rule 6
Roy Bott

Give me only /. How do I get to bed 1?

Josh

The bookmark offers two GET forms:

$ curl -si localhost:8080/ -H 'Accept: application/hal+json'
ETag: "index-hsf-a3ccaf8cf64d5ccc"
{"title":"Garden beds",
 "_forms":{"garden:search-beds":{"_links":{"target":{"href":"/beds{?name}","templated":true}},"method":"GET",…},
           "garden:get-bed":{"_links":{"target":{"href":"/beds/{id}","templated":true}},"method":"GET",…}}}

$ curl -si 'localhost:8080/beds?name=BED-1' -H 'Accept: application/hal+json'
{"count":1,"_links":{"self":{…},"item":[{"href":"/beds/1","title":"bed-1"}]}}

ARTIE fills the form, then follows item by its title. Tonight that path passed live at L0 and L2, in HAL-FORMS, and over CoAP.

Roy Bott

You said "no prior knowledge", but you asked with Prefer: forms=link, schema=link. How did you know to ask for that?

Josh

The bookmark told us. Asked for JSON Home, the same / answers:

$ curl -si localhost:8080/ -H 'Accept: application/json-home'
"hints":{"formats":{"application/prs.hal-forms+json":…,"application/hal+json":…},
         "accept-prefer":["forms=link","schema=link"],
         "precondition-req":["etag"]}

After that, ARTIE trusts each response's Preference-Applied over the promise. A server that says nothing gets used at L0.

Roy Bott

Then what's left is my first sentence: "standardized media types". Is HAL Schema Forms standardized?

Josh

Not yet. HAL is an IETF draft, HAL Schema Forms is published but not standardized, and the HEART profile is ours. A plain HAL Schema Forms client can work at L0. L1 and L2 need the profile.

Roy Bott

That's a question of adoption, not a broken rule. Your client does what the rule asks. Whether the world knows your media type is a different question.

One bookmark reaches everything, and every step is a choice the server offered. Still open: the media type and profile are published but not standardized.

Reply to TheOtherMarcus, 21 Oct

The client picks the transition, not the interface

"The client (user or agent) has to decide what transition to take, not what interface to use."
Roy Bott

Your model chooses. What can it choose?

Josh

This, and nothing else:

// client/src/main/kotlin/heart/Reasoning.kt
/** The Reason step's entire output space. It has no field for a URI, method, header or precondition. */
sealed interface Selection {
    data class Act(val affordance: String, val fields: JsonObject) : Selection
    data class Follow(val rel: String, val title: String?) : Selection
    data class Describe(val affordance: String) : Selection
    data class Explain(val affordance: String) : Selection
    data class Clarify(val question: String) : Selection
}
✓

The model picks the transition. Deterministic code builds the target, method, If-Match and body.

Reply to TheOtherMarcus, 22 Oct

"Don’t confuse application state (the state of the user’s application of computing to a given task) with resource state (the state of the world as exposed by a given service)."

Josh

That's a design question we've parked: showing a past state with the acts it offered then, inert. Notes are in spec/ideas/past-states-as-mementos.md.

✓

The two are kept apart, and 412 is where they meet.

Roy Bott

Why 65020 and not 65016?

Josh

In CoAP, an option's number sets its properties. 65020 is even, so it's elective: a server that doesn't know it ignores it. Its second bit is clear, so it's safe to forward. Its bits 2 to 4 are 111, so it's not part of the cache key, and a trace never splits a cache. 65016 would have been part of the key. SPEC §6.0.1 used to say "Not carried"; it now names the option and says it's experimental like the others.
