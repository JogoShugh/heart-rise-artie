Find the Way Once, in Brief

The same business process over many records, run again and again. Find the way once with a model, keep it, and run it with none, held to the controls the server puts in each answer.

5 runs each at 6, 30 and 90 employees; the kept ways found at 6. Wrong runs exited 0: the kept skill guessed the paging at one page and stopped at the first 20 of 90; the kept programs moved the 6 they were written for. ARTIE follows the next link the search answer carries.

At 1,000,000 runs: projected from the measured runs, at each client's measured rate. One service, one model (Claude Sonnet 5.5).

Why

  • The controls are in the answer. Each answer carries what is true and what can be done now, so a client finds its way from a bookmark, and a kept way runs again with no model.
  • A change is caught before a write. ARTIE holds each act to the form it was offered; a renamed field stops the step, the model repairs it once, and the repair is kept. Kept code wrote on, and was wrong.
  • The cost follows the states, not the records. One form set per state, shared by every record in it: three a run, at 6 employees or 90.
  • Data, not code. A kept script is YAML a person or a policy can read before it runs: no sandbox, no token in model-written code, and a release is a diff of a few lines.
  • Code mode and ARTIE fit together. Code mode reads the task in plain words; ARTIE does the acts. Run by a plain harness, the model is called only when ARTIE fails.

Two architectures

A bag of endpoints

flowchart TD
  D["1 Description: every operation"] --> M{{"2 Model writes code"}}
  M --> P["3 Program builds URLs"]
  P --> S[("Service")]
  S -- "4 status, body" --> P
  1. The client is told every operation up front: paths, methods, bodies.
  2. The model works out the way and writes the code, every run.
  3. The program builds each address itself, from templates and IDs.
  4. The server's rules show only after the call.

Hypermedia

flowchart TD
  B(["1 Bookmark"]) --> R["2 State + controls now"]
  R --> C{{"3 Client picks a control"}}
  C -- "act + If-Match" --> S[("Service")]
  S -- "4 next state or refusal" --> R
  1. The client enters at a bookmark, knowing only media types.
  2. Each answer carries what is true now and what can be done now.
  3. The client picks a link or a form; an act carries the ETag it read.
  4. The server answers with the next state, or refuses with a reason.

  • The goal is the stable layer. Of seven changes, one reached it: a reason, which only a person can give. ARTIE stopped and asked; the skill made one up.
  • The kept script is the goal's lock file. A release re-records it, and a person reviews the diff; the goal changes when the task does.
  • A pin holds what a form does, not where it is. Its act: the method, content type, template pointers and schema, the target set aside. ARTIE never builds an address, so a form the server moves goes on with no model. A new method or a new field is a new act, and stops the step before the write. Strict stops at any change.
  • Kept code holds the domain. Field names, the state rules and the paging were the code's own copies; in kept programs, each went wrong without a word.
More
  • Task t1 (hire, promote, dismiss): one run per release, on the way kept before it. The rename and the teammate are from the 20-run sequence; the paging from the runs at 90 employees. Figures are the model's input tokens.
  • * The SDK was generated from the description at the start of every run: code mode at its best. One built once needs a rebuild for each of these.
  • Every release changed the description and the answer; ARTIE itself never changed.
  • A form's own integrity covers its target too (the profile's Rule 10), so a moved form has a new one. The lock file also pins each form's act, the same digest with the target set aside: a lenient run goes past a form whose integrity changed while its act did not, and its trace says it was held by its act. With repin: auto, the new integrity is written into the lock file. A lock file without acts holds to the integrity alone.
  • A repair that makes a new act (give notice) is proposed, not kept, so the model is called each run until a person keeps it.

Fielding, in brief

  • The principle (2000): REST's least-followed constraint is hypermedia as the engine of application state: the client moves from state to state by choosing among the controls each answer carries.
  • Information and controls together: "When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions."
  • The complaint (2008): most "REST APIs" are a list of operations a client must know in advance. "That is RPC. It screams RPC."
  • Enter knowing almost nothing: "A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types…"
  • For change over time: "REST is software design on the scale of decades: every detail is intended to promote software longevity and independent evolution."

Roy T. Fielding, dissertation, 2000, §5.1.5; "REST APIs must be hypertext-driven" and its comments, 20 October 2008. More: Information and Controls.

Limits said plainly
  • One service, one model, three tasks; 5 to 10 runs per row.
  • Projections are arithmetic on the measured runs, not runs.
  • A kept script does what its first run did. A goal that asked for less than the task would be kept that way: a person reviews it.
  • The example dismisses people; a gentler domain would carry the same point.
