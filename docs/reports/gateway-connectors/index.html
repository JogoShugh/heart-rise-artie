Take HEART · Part 2 · configuring the gateway

Gateway Connectors

The HEART gateway serves an API that publishes only OpenAPI as a HEART server: forms for what each resource allows now, reasons for the rest. Everything it knows about one API sits in that API's connector, a folder of YAML. GitHub's is the worked example.

The engine is code, written once for every API. An API is configuration: one folder, three kinds of file, no code.

Code, the same for every API

  • Read an OpenAPI description, keeping only the operations a connector includes, before parsing it.
  • Turn a resource file into a HEART resource type: its address, its search, its forms.
  • Turn an act into a call: the fixed body, the client's fields, the fields bound from state.
  • Decide what an answer allows: the reader's signal, then its rules, each with its reason.
  • Call the upstream as each caller, and revalidate what it read with ETags.
  • Serve all of it as HEART, through heart-core and heart-http4k.

Kotlin, in heart-gateway/src/main. It names no API.

Configuration, one folder per API

  • connector.yaml: which operations to read, headers for every call, and which files follow.
  • <name>.resource.yaml: one resource of the API, its acts and the other answers it reads.
  • <name>.reader.yaml: how to tell what an answer allows now, and why not the rest.
  • Optionally a .jsonata file, for an API whose signal no built-in reader understands.

GitHub's is heart-gateway/connectors/github, shipped in the gateway's distribution.

The standard approach

Every connector is written the same way, in this order. Each step is a file or a key; none is code.

  1. Slice the description.In connector.yaml, list under include only the operations the connector uses. The gateway cuts the rest out before parsing: GitHub's 13.5 MB description loads in about a second. Add any headers every call needs.
  2. Name each resource by its own paths.In a resource file, say which operation reads one (read) and which lists them (search), and give a JSON Pointer into the resource's state for each variable of the read's path (pointers). An upstream whose paths are already HEART's, /{collection}/{id} with acts at /actions/{name}, needs no resource file at all.
  3. Name acts after what people do, not after operations.Each act is one operation with a body fixed by the connector, the fields the client fills, and the fields bound from the state the client's validator matched (bind). GitHub's close and reopen are the same operation with a different fixed body.
  4. Bind the upstream's own concurrency checks.Where an operation takes the version it expects, bind it from the state, so the upstream refuses a write on a view that's out of date. Merge's sha and update-branch's expected_head_sha both come from /head/sha.
  5. Say what the upstream's refusals mean.stale names the status that means the client's view is out of date (answered 412); refused the one that means not now (answered 409, in the upstream's words). Anything else passes through as the problem it is.
  6. Read what's allowed, standards first.An answer with HEART's affordance Link or OData's advertised actions needs no reader. Otherwise a reader names one signal: names, booleans, links, odata, a table by a state field, or a jsonata file.
  7. Refine with rules, each with its reason.After the signal, a reader's rules, in order: when every condition holds, the acts named are absent, with that reason. The first reason given for an act stands. A condition may read a fact, another of the upstream's answers, such as the repository's permissions.
  8. Leave the last word to the upstream.Rules only say early, and why. The gateway reads the resource again just before acting, and the upstream's own refusal of an act always reaches the client.

Every key

connector.yaml

KeySays
profileThe profile the API's relations are named in: forms are keyed github:merge, described at /profiles/github.
includeThe operations to read, by operationId. Without it, every operation is read.
headersHeaders every upstream call carries.
resourcesThe resource files, in order.
readersThe reader files, in order: the first that recognizes an answer reads it, so the API's default reader comes last. A reader file in the folder but not listed stops the gateway.

<name>.resource.yaml

KeySays
noun, collectionWhat one is called, and the collection's name.
readThe operation that reads one. Its path is where the resource lives in HEART too.
searchThe operation that lists them. A bare JSON array, paged by Link: rel="next", is followed to the end.
pointersFor each variable of the read's path, a JSON Pointer into the state: pull_number: /number.
filtersThe list's query parameters the search form offers.
titleWhere a listed item's title is, for the search page's item links.
addressWhere the item's own URL is, when its state names its parts only there, as an issue's /url does: the read's path variables are read from it and kept in the state as hr:address. Instead of pointers.
skipConditions under which a listed item is not one of these resources: GitHub lists pull requests among issues (/pull_request: {present: true}).
listsOther list operations whose members are these resources, each served at its own path and linked from the resource: an issue's sub-issues.
linksList operations under the resource that another resource file searches by, linked from it: an issue's comments.
actsThe acts, each by name: operation, title, description, body (fixed), fields (the client's), bind (from state), stale and refused (what the upstream's statuses mean), and creates (the noun of the resource the operation's answer is: the gateway answers 201 with its address in Location). A field the state doesn't fill but the operation's path names goes in the path: remove-label's {name}.
factsOther answers a reader's rules may read, each by name: an operation, and pointers filling its path from the resource's state.

<name>.reader.yaml

KeySays
matchesWhich answers this reader reads: by members of the body, its mediaType, or the description's path template it was asked at. None means every answer: the default reader.
allowedOne signal: names (a list of action names), booleans (a map of capabilities), links (an array of links by rel), odata (OData's advertised actions), table (a state field, with rows of allow and absent reasons), always (the same acts in every state, for a resource with no state to choose by, as a comment), or jsonata (a file). map renames the API's words to operationIds.
allowed.rulesIn order: when (each JSON Pointer, or fact:/pointer, against a condition: a JSON value it must equal, null matching a member that is there and null; {present: true}; {not: value}; {same-as: term} or {not-same-as: term}, another pointer or fact, as an issue's author and the caller) and absent (act to reason). Every condition of a rule must hold.
hideMembers that are control, not state, left out of the HEART state.

Two kinds of upstream

An API whose answers already say what is allowed needs very little. The door service the gateway's tests run against lists the names of the actions allowed now, and its whole connector is this:

doors-names/connector.yaml

profile: doors
readers:
  - door.reader.yaml

doors-names/door.reader.yaml

allowed:
  names: /allowedActions
hide: [/allowedActions]

GitHub says nothing about what is allowed. Its answers carry the facts, state, draft, merged, mergeable, mergeable_state, and the repository's permissions, but no decisions, and its paths aren't HEART's. So its connector writes the decisions down, once, with their reasons, and names its resource by its own paths. That is the most a connector has to say.

What the gateway checks at start

A connector that doesn't fit the description stops the gateway before it serves anything, naming the file: an included operation the description lacks, a resource or reader naming an operation or path it lacks, a field an act asks for that its operation's body doesn't have, a reader file present but not listed, a listed file that isn't there, a key that isn't a JSON Pointer.

Testing a connector

  • A small upstream in memory, answering as the real one does. GitHub's serves GitHub's own example answers, from its description, set to each state.
  • Features in tables: what each state offers, as one matrix of state by act, and why each act is absent, as rows of state, act and reason.
  • HEART's conformance kit, run through the gateway in front of that upstream: the same scenarios every HEART server passes.
  • A live run on a scratch repository: live/github/seed.py makes the states, capture.py reads them both ways, act.py acts through the forms.

GitHub's connector, as of 2026-10-17: every act tested against the fake GitHub. Against real GitHub: every pull request act but an accepted review request (the repository has one collaborator), and every state but behind and no push permission; every issue, repository and comment act but set-milestone, through the forms, with the issues opened and commented on by the forms themselves (live/github/issues.py, capture-issues.py). Who may do what by role is tested against the fake only: the live token is the owner's. The report GitHub Gateway Status has the full tables and the live JSON.

Not yet

  • Conditions say equal, present, not and same-as; a rule can't yet say "more than".
  • One read path per resource.
  • A fine-grained token narrower than its user's permissions: the gateway offers what the user may do, and the upstream's 403 has the last word. Nothing in GitHub's answers says what the token may do.
  • OpenAPI 3.0's nullable isn't translated to JSON Schema 2020-12 in act schemas; no field GitHub's acts use needs it.
