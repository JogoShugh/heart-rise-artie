One script, three bindings

The same heart-script, run three times against the garden: over plain CoAP, over coaps (CoAP secured with DTLS and a pre-shared key), and over HTTP. Only its entry input differed. ARTIE chose the binding from the entry's scheme; the script knows no protocol.

Why this matters

In 2008 Roy Fielding listed the rules an API must follow before it calls itself REST, in “REST APIs must be hypertext-driven”. The first rule is about protocol:

A REST API should not be dependent on any single communication protocol, though its successful mapping to a given protocol may be dependent on the availability of metadata, choice of methods, etc. In general, any protocol element that uses a URI for identification must allow any URI scheme to be used for the sake of that identification. [Failure here implies that identification is not separated from interaction.]Roy T. Fielding, “REST APIs must be hypertext-driven”, October 20, 2008, his first rule, verbatim

Almost every API that calls itself REST fails this one before it fails anything else. Its documentation is a list of HTTP methods on URL patterns, so the API is its HTTP mapping. HEART is built the other way round, at every layer, and this page is the proof.

The specification

HEART's core is written in protocol-free terms (SPEC §6.0): read, act, done, a new resource brought into being, and refusals by meaning: not offered, stale, invalid input, precondition required. HTTP is one binding of those concepts. CoAP is another (SPEC §6.0.1). Each binding does exactly the work Fielding allows a mapping to need, “metadata, choice of methods”: HTTP's 201 and Location header become CoAP's 2.01 and Location-Path option; an HTTP ETag becomes a CoAP ETag option. The meaning stays the same.

The server

The garden declares itself once to the HEART library: its state, its acts, the rules that say which acts its state allows, and the reason for each one it doesn't. It has no controllers. Two front doors serve those same declarations: heart-spring over HTTP, and heart-coap's front door over CoAP on UDP. Neither knows the garden; the garden knows neither.

The client

ARTIE's core never sees a status code or a header. It talks to bindings, one per URI scheme, and each fills the same protocol-free outcome from its own protocol; a binding's own word for what happened (an HTTP status, a CoAP code) is only ever reported, never acted on. So the client meets Fielding's second sentence directly: an entry is any URI, and its scheme chooses the binding. Identification, the bed's address, is separate from interaction, how that address is reached.

The script

The heart-script DSL sits above all of that and knows only the core's concepts: select a form, follow a link, expect a new resource, expect “not offered”. It never names a protocol. Below, the same file runs three times, with only its entry input changed between coap://, coaps:// and http://. Different protocols, different transports (UDP, DTLS over UDP, and TCP), different adapters on both sides, and the same eight steps, the same outcomes, and the same refusals with the same reasons.

The result

8 of 8 steps the same, three ways: the same selections, the same outcomes, the same refusals with the same reasons, the same forms offered, and the same state, except each new bed's number and name. All three runs exit 0.

The commands

artie run tests/garden-bed.kts entry=coap://localhost:5683/ name="Bed over CoAP" artie run tests/garden-bed.kts entry=coaps://localhost:5784/ name="Bed over coaps" artie run tests/garden-bed.kts entry=http://localhost:8080/ name="Bed over HTTP"

The script

// Build a bed in the garden, sow it, and show what the garden refuses: a second sowing (not
// offered once planted) and a bed with no width (invalid input). The entry chooses the binding:
// the same script runs over CoAP or HTTP, unchanged.
//   artie run tests/garden-bed.kts
//   artie run tests/garden-bed.kts entry=http://localhost:8080/
val entry by input(default = "coap://localhost:5683/")
val name by input(default = "Scripted bed")
val seed by input(default = "basil")

heart(entry) {
    expect(InvalidInput) { act("garden:build-bed", "label" to name, "widthFt" to 0, "lengthFt" to 8) }
    expect(NewResource) {
        act("garden:build-bed", "label" to name, "widthFt" to 4, "lengthFt" to 8) {
            check(state["/status"] == "EMPTY") { "a new bed should be empty" }
            act("garden:sow-seed", "seedType" to seed, "depthCm" to 2)
            check(state["/cropName"] == seed) { "the bed should hold $seed" }
            expect(NotOffered) { act("garden:sow-seed", "seedType" to "mint") }
            note("offered once planted: ${held.offered}")
        }
    }
}
