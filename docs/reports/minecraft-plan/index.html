ARTIE in Minecraft

A Paper server plugin reads each HEART representation with ARTIE's own client and shows it as a Minecraft dialog: the acts on offer as buttons, their schemas as inputs, and the server's refusals as notices. Players need no mods.

The loop

  1. A player runs /artie open <address>. Later, a sign or a lectern can hold an address.
  2. The plugin reads the resource with ARTIE's client and keeps its ETag. It does this off the server's main thread, so the game doesn't stall.
  3. It builds a dialog with Paper's Dialog.create and shows it with showDialog.
  4. The player presses a button. The server receives the button's key and every input's value, read with getText, getBoolean and getFloat.
  5. The plugin sends the act with If-Match.
  6. The answer becomes the next dialog. A refusal becomes a notice in the server's own words.

Other routes considered
  • A real browser in the game (MCEF). Chromium inside Minecraft, a library for other mods. MCEF Modern supports Fabric, Minecraft 26.x and Apple Silicon. Every player must install the mod, and it downloads Chromium. Kept for phase 4.
  • Bedrock forms. A button-list form, and a form with text fields, dropdowns, sliders and toggles; also a newer data-driven UI. HTTP calls work only on Bedrock's dedicated server, and are experimental. JavaScript, so heart-ts, not ARTIE.
  • DialogAPI. A community library for 1.21.6. Paper's own dialog API, from 1.21.7, is the steadier choice.
Not checked yet
  • A dialog's values reaching the plugin on this Mac: phase 0.
  • How long state reads in a dialog's body, and where it needs to be shortened.
  • ARTIE's libraries packed into a plugin without clashing with Paper's: kotlinx-serialization, json-schema-validator and Californium (the CoAP client, which a plugin doesn't need).
  • Whether single option shows as a cycling button or a list on 26.1. The mock-up draws it as a button.
