OpenAPI and HEART, by Fielding's rules

Roy Fielding defined REST in 2000. In 2008 he listed six rules an API must follow to call itself REST. This page scores OpenAPI and HEART against them, using what the garden exhibit actually showed, and says what is still open to question about HEART.

OpenAPI describes HTTP APIs well and was never trying to be REST. HEART follows all six rules for the clients it's meant for: generic ones that know its media type. What's left to question is evidence, cost, and meaning the representation doesn't carry.

This page changed its mind

The first version of this page, published earlier on 14 October, listed five gaps in HEART. The project's author pushed back on three of them. I checked them against the exact text of Fielding's post, and the author was right. Those three are withdrawn. They're kept below, under "What I got wrong first", with the reason for each, so the change is visible rather than quietly erased. The scorecard moved with them: rules 2, 3 and 5 went from "Mostly" or "Partly" to "Yes".

It changed again on 25 October, to agree with the fuller Fielding's Rules, Checked, which had looked more closely at two rules. Rule 1 goes to "Yes": the spec's core is protocol-neutral, with HTTP and CoAP as two bindings of it (SPEC §6.0). Rule 2 went to "Partly" that morning, for one stretch of RFC 9110 §13.1.1: an act's If-Match carried the ETag of the resource that offered the form, while the act's own target had no representation at all. By the evening it was fixed: an act's target now answers GET with a small representation of its own, under its owner's ETag, so If-Match is compared with the target's own ETag, and no client had to change. Rule 2 is back to "Yes". Question 3 below now has a first answer.

Read this first

  • This is not Roy Fielding's opinion. It's a reading of his published rules, from his post "REST APIs must be hypertext-driven". The rules below are paraphrased. To know what he thinks, you would have to ask him.
  • The evidence comes from the OpenAPI-vs-HEART exhibit: one garden server, changed in seven ways, met by a bespoke dashboard generated from OpenAPI and by HEART clients that never changed.
  • REST isn't a grade of quality. An API can be good without being REST, and OpenAPI's own maintainers say "HTTP APIs" on purpose. The question here is narrower: which of the two follows REST's constraints, and where does each stop?

The six rules, in plain terms

Rule 1 Not tied to one protocol

The API's meaning should live in its representations, not in the quirks of HTTP. If the same resources and acts can travel over another protocol, the design is about the information, not the plumbing.

OpenAPIIts whole structure is HTTP paths, methods and status codes. There's no other binding.
HEARTOne declaration serves HTTP and CoAP, with the same forms and validators. The spec states its core without a protocol and maps it to each binding (SPEC §6.0), so this is a "Yes".

Rule 2 Don't change the protocol

An API should use HTTP as HTTP is defined. It may fill in things HTTP leaves open, but it shouldn't invent new rules that every client and intermediary has to learn. Caches, proxies and generic tools only understand standard HTTP.

OpenAPIDescribes HTTP as it is. No new protocol rules.
HEARTLeaves HTTP as it is. Its requirements, such as If-Match on every act and Prefer tokens for the layout, are rules of its media type, which is where rule 3 says they belong. A generic client learns them once, for every resource. An act's If-Match is checked against its target's own ETag: the target answers GET with a small representation, under the ETag of the resource that offered the form.

Rule 3 Describe media types and relations, not endpoints

The documentation effort should go into what a representation looks like (its media type) and what its links mean (link relations, such as next or edit). It should not go into a list of URLs and what each one does. Media types and relations are reusable across APIs; endpoint lists aren't.

OpenAPIAn OpenAPI document is, by design, a list of endpoints and their payloads.
HEARTDefines a profile of HAL Schema Forms and its processing rules, its own relations, and ALPS profiles. Each domain adds extended relation names, such as garden:water-cell, which the rule names as the other place effort should go.

Rule 4 The server owns its URLs

A client shouldn't build URLs from a pattern it learned in documentation, such as /beds/{id}/actions/water-cell. The server should hand it links, or forms and URI templates that say how to build one. Then the server can move things without breaking anyone.

OpenAPIPaths are the contract. When the garden moved water's target, the generated client still called the old one, and got 404.
HEARTEvery target comes in a form. All three ARTIE clients followed the move with no change.

Rule 5 No typed resources

A client shouldn't decide in advance that "/beds/2 is a Bed object with these fields". It should look at what it received: this is HAL with these forms. If the client hard-codes a type, every change to that type breaks it.

OpenAPIGenerated clients are typed classes. When moistureLevel was renamed, the bespoke card showed undefined.
HEARTThe ARTIE dashboard shows whatever members arrive, and Claude reads them by meaning. Neither assumes a type for the bed.

Rule 6 Bookmark in, choices out

This is the rule people mean by "HATEOAS". A client needs only the first URL and an understanding of standard media types. From then on, it moves by choosing among options the server put in the response, as a person does on a website. It needs no out-of-band list of what the API can do.

OpenAPIThe client learns the API from the spec, before it runs. The spec says what can ever be done, not what can be done now. That's why the bespoke dashboard offered Water on a frozen bed.
HEARTThis is HEART's core. The bookmark offers search and lookup, and each bed offers only the acts legal in its state. Each act carries the validator of the state it was chosen from.

What can still be questioned

Four questions a careful REST reviewer could still fairly ask. None is a rule HEART breaks. They're about evidence, cost, and limits.

Question 1. Someone still has to understand the choices

What it means

Rule 6 assumes a client that can read the offers and pick one. On the web, that's a person in a browser. For machine clients, this was always the weak point of HATEOAS: a program can see that a form exists, but not what it is for, unless someone coded that meaning in. That's a big reason most machine-to-machine APIs gave up on hypermedia.

What changed

A language model can read a form's title, relation and schema and decide whether it serves the goal. In the exhibit, Claude chose garden:thaw for a frozen bed it was never told about, and garden:irrigate after the rename. That's late binding of meaning, which REST always needed and rarely had.

The limit

This moves the problem; it doesn't remove it. Under new-required-input, Claude asked "Should the water reach bed 2 by drip or by spray?" instead of acting. That was right: the choice was real, and only the person could make it. Meaning that isn't in the representation can't be read from it, by a model or anyone else.

Question 2. The model's results are one run each

What it means

Claude tried each change once. It chose garden:thaw for the frozen bed, garden:irrigate after the rename, and asked about the new input. One run shows what can happen, not how often it happens.

What could close it

Run each change many times, with more than one model, and report rates: how often the model chose the right act, chose a wrong one, or asked.

Question 3. Reading by meaning has a cost

What it means

A script calls one act directly. A Reasoner reads the offers, sends them to a model, and waits for its choice. That costs tokens and time on every decision, and the same question can get different answers on different runs.

Why it matters

Resilience to drift is bought with that cost. Whether it's worth it depends on how often the server changes and what a broken client costs. That trade has to be measured, not assumed.

What could close it

Measure it: tokens and latency per decision, against the rework a change forces on early-bound clients. The exhibit already counts the rework; it doesn't yet count the model's cost.

A first answer (25 October)

Don't pay it on every run. A model decides once; artie generate writes those decisions as a script with a lock file that pins each form it used. The script then runs with no model, and before each act ARTIE checks the form against its pin, refusing to send if the server changed it. On the seed bench the script alone did a goal's work on new issues, 229 steps, with no model called (Seed Bench). Not yet built: handing a refused step back to a model. Not yet measured: how many runs one decision serves.

Question 4. The payoff shows at scale, and the exhibit is small

What it means

REST was designed for systems that live for decades, with many clients the server's owner never meets. That's how the web works. Its benefits, such as independent evolution, caching, and generic clients, grow with the number of clients and the length of time.

What the exhibit shows

One garden, four clients, one developer, a few days. It shows the mechanism working: a server changes, and the clients that didn't bind early carry on. It doesn't show the economics at scale: what happens across dozens of services, hundreds of independent clients, and years of change.

What could close it

More domains (there are already garden, basketball and tickets), more independent client implementations (there are already two HEART clients, in Kotlin and TypeScript, and a conformance suite), and clients written by people other than the server's authors.

What I got wrong first

The first version listed these three as gaps 1 to 3. Each is kept as it was published, followed by why it was withdrawn. The project's author raised all three; the reasons come from the text of Fielding's post.

Withdrawn gap 1. The garden's relations mean nothing outside the garden

What it means

A link relation is a name for what a link or form does. On the web, some names are shared by everyone: IANA keeps a registry with names such as next, prev and edit, and any client knows what they mean. HEART's own relations, such as https://w3id.org/heart-rise/rels/forms, are global names with a page that defines them. But the domain's acts are named garden:water-cell or garden:thaw. Only a client that learned this garden knows what they mean.

Why it matters

Rule 3 asks for meaning that is shared, so clients can be reused across services. A relation only one API uses is just an endpoint name with a different spelling. Code that names it is coupled to that API, exactly as a generated client is coupled to its paths.

What the exhibit showed

Under rename-act, garden:water-cell became garden:irrigate. The ARTIE script, which named the relation in code, failed with "No affordance 'garden:water-cell'". The dashboard, which reads titles, and Claude, which reads meaning, both carried on.

What could close it
  • Publish each domain relation at a URI that explains it, as HEART already does for its own relations.
  • Let a server offer an old relation and its new name together for a while, so a rename can be gradual.
  • Reuse shared vocabularies where they exist, such as ALPS descriptors shared between gardens, or schema.org's action types.
  • Accept the limit: some meaning is domain-specific. A watering act will always need a client that understands watering.
Why I withdrew it

Rule 3 itself says the effort should go into media types "or in defining extended relation names". A domain relation like garden:water-cell is exactly that, and it doesn't need a global registry. What a client needs is a standard way to survive a server renaming things, and HEART has one: every form carries a relation, a title and a schema, and a Reasoner reads them while it runs. Under rename-act, Claude chose garden:irrigate with no change. The only client that failed was a script that hard-coded the old name, which is withdrawn gap 3's mistake.

Withdrawn gap 2. Is HEART a media type, or a new protocol on top of HTTP?

What it means

Rule 2 says you may fill gaps HTTP leaves open, but not change how HTTP works. HEART asks for more than plain HTTP does:

  • every act must carry If-Match (otherwise 428);
  • failures come in a fixed order: 428, 412, 409, 422;
  • clients ask for a layout with Prefer: forms=link, schema=link;
  • clients pick a dialect with Accept-Profile.
Why it matters

The more rules a client must learn beyond HTTP and the media type, the more HEART looks like its own protocol. Then generic tools, caches and libraries can't fully take part, which is what rule 2 is protecting.

The case for HEART

Each piece is an existing standard used as written. 428 Precondition Required is RFC 6585. Prefer is RFC 7240, which lets anyone define tokens. The check order is the server's own business. Problem details are RFC 9457. Caches see ordinary ETag, Vary and Cache-Control. A plain HTTP client that ignores everything HEART adds can still read a valid L0 response. Only its acts need more: it must send back the ETag it was given, in If-Match.

The honest weakness

Accept-Profile comes from a W3C draft, Content Negotiation by Profile, that never became a Recommendation. And taken together, the rungs, layers and tokens can feel like a protocol even if each part is legal.

What could close it

Keep L0 working with nothing but HTTP and the media type. Make every rule above L0 optional for clients. And say in the spec, rule by rule, which standard each requirement rests on, as the Internet-Draft starts to do.

Why I withdrew it

Rule 3 says "Any effort spent describing what methods to use on what URIs of interest should be entirely defined within the scope of the processing rules for a media type". HEART's requirements are exactly those processing rules. Rule 6 says transitions "may be determined (or limited by) the client's knowledge of media types", so a generic client that knows HEART's rules well is doing what Fielding asked, not coupling to a protocol. Rule 2 is about changing HTTP itself; its failure note is "resource interfaces are object-specific, not generic", and HEART's rules apply the same way to every resource. What remains true is small: Accept-Profile comes from a draft standard. That's a note about standards maturity, not a REST problem.

Withdrawn gap 3. Clients can couple themselves anyway

What it means

Rule 5 is about the client's assumptions as much as the server's design. A server can send fully self-describing responses, and a client can still ignore that and hard-code "the act is called this, and the field is called that". That client is as brittle as a generated one, just in different places.

What the exhibit showed

The ARTIE script uses the same library as the ARTIE dashboard. It named garden:water-cell and milliliters in code. It survived the moved URL, the renamed member, the new title and the tighter limit, because the forms carried those. It broke on exactly the two names it had written down: the renamed relation, and a new required field, method, that it had never heard of.

Why it matters

HEART removes coupling only for clients that don't add it back. "Our API is hypermedia" doesn't make every client evolvable. Early binding is a choice every client author makes.

What could close it

It can't be fully closed, and shouldn't be: sometimes a script should fail loudly when the meaning changes. What helps is a client library that makes the late-bound way easy. That means looking acts up by meaning or title, filling fields from the form's defaults and examples, and reporting clearly what changed when it can't.

Why I withdrew it

The script isn't a generic client. It's early-bound code that happens to use the ARTIE library, and nobody expects early-bound code to survive server-directed change. It fails rule 6 by its own design, not HEART's. Using it as evidence that changes "hurt ARTIE" was a red herring. No generic ARTIE client broke under any change. The dashboard acted correctly under all seven. Claude acted under six, and under the new required input it asked the person a real question instead of guessing. Neither sent anything the garden refused. In the exhibit the script stays only as a control, to show what early binding costs.

The verdict, in one paragraph

By Fielding's rules, OpenAPI isn't REST, and it doesn't claim to be. It's a precise contract for HTTP-based remote calls, and it's good at that. HEART follows all six rules for the clients it's built for: generic clients that know its media type. The server owns its URLs, every step is a choice the server offered in the current state, and HTTP caching is used the way REST intends. In the exhibit, no generic client broke under any change. What's still open is how often a model chooses well, what reading by meaning costs, what to do when the meaning isn't in the representation, and how this holds up at scale.

The first version of this verdict named three weak spots: relations not shared beyond one API, requirements that risk reading as a protocol, and clients that couple themselves. All three are withdrawn; see "What I got wrong first".
