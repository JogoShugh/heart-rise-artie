HEART · employees service · 3 November 2026

Many Records, a Few States

One goal over many employees, each in one of three states. ARTIE runs the goal once with a model, writes the way it found as a script, and runs that script after with no model: the model and the forms it needs follow the states, not the number of records.

Information and controls, in brief

  • Every answer can carry two things: what is true now (information) and what can be done now (controls). Fielding's hypertext keeps them together.
  • The browser is generic because it is coupled to formats, not sites. It knows HTML and forms, and no bank, wiki or shop; each sends its own controls. ARTIE is coupled the same way: to HAL, the HEART profile, JSON Schema and problem details, and to no API.
  • On the Web, controls followed the state: a form present when an act was possible, absent with a reason when it wasn't. Nobody needed the server's rules in advance.
  • APIs took the controls out of the answer, and the rules drifted: into interface files, then documentation, then generated clients, and now a model's training, each copy staler than the last. One SDK per API, now one set of agent tools per API.
  • HEART puts them back in the answer, true now: links instead of addresses a client builds, forms offered by state, and a reason when one isn't. With them, one generic client serves a person, an agent and a script, and a job can be written as a goal in plain words.
  • The full story, on one GitHub pull request: Information and Controls.

Fielding, in brief

  • The complaint (2008): most "REST APIs" are a list of operations a client must know in advance. "That is RPC. It screams RPC."
  • Enter knowing almost nothing: "A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types…"
  • Information and controls together: "When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions."
  • For change over time: "REST is software design on the scale of decades: every detail is intended to promote software longevity and independent evolution."
  • More, with his six rules verbatim: Information and Controls.

HEART, ARTIE and the formats, in brief

  • HEART (Hypermedia Enforced Agentic Reliable Transactions): a protocol profile for APIs. Each answer carries, or links to, the actions its resource allows in its state now; an action not offered is not allowed, and the answer can say why. Every write sends the ETag it read (If-Match): a stale one is refused 412, a missing one 428.
  • ARTIE (Autonomous Restful Traversal and Interactive Engine): HEART's reference client. Generic, like a browser: coupled to the formats below, not to any API. It follows links and forms, sends the ETag, and caches what it may. It runs a goal written in plain words with a model, and a kept script (.heart.yaml) with none.
FormatWhat an answer holdsHere
HALThe resource's state, and _links: related resources by relationThe base of the two below
HAL-FORMSHAL, and _templates: each action's method, target and fieldsSpring HATEOAS's format, widely used; what this service answers when a client asks for nothing in particular
HAL Schema FormsHAL, and _forms: each action's method, a link to its target, and a JSON Schema for what it takesHEART's reference format, with its profile: forms named as link relations, and integrity hashes a client can check
OpenAPINot an answer: a separate description of every endpoint, its path, method and bodyThe same service's endpoints, as code mode uses them
  • Rungs: at L0 the forms and their schemas are inside each answer. At L2 they are linked: the forms for one state published once at their own address, shared by every resource in that state, and cached for a year. A client asks with Prefer: forms=link, schema=link.
  • Kept script and pins: a run's way written as data, run again with no model; its pins record the forms the run was offered, so a changed form is caught before any request.
  • Code mode: a model writing programs against an API, run in a sandbox (Anthropic's "code execution with MCP", Cloudflare's Code Mode).

Two architectures

A bag of endpoints

flowchart TD
  D["1 Description: every operation"] --> M{{"2 Model writes code"}}
  M --> P["3 Program builds URLs"]
  P --> S[("Service")]
  S -- "4 status, body" --> P
  1. The client is told every operation up front: paths, methods, bodies.
  2. The model works out the way and writes the code: every run (fresh), or once (saved).
  3. The program builds each address itself, from path templates and IDs.
  4. The server's rules show only after the call: a changed operation is an error, if the program reads it.

Hypermedia

flowchart TD
  B(["1 Bookmark"]) --> R["2 State + controls now"]
  R --> C{{"3 Client picks a control"}}
  C -- "act + If-Match" --> S[("Service")]
  S -- "4 next state or refusal" --> R
  1. The client enters at a bookmark, knowing only media types.
  2. Each answer carries what is true now and what can be done now: the links, the forms this state allows, an ETag.
  3. The client selects a link or a form; an act carries the ETag it read.
  4. The server answers with the next state, or refuses with a reason: 409 not offered, 412 stale, 428 no validator, 422 doesn't fit.

How ARTIE uses the model

Wayfinding: sync, reason, act

flowchart TD
  W(["Goal words"]) --> Y["1 Sync"]
  Y --> Q{{"2 Reason: model"}}
  Q --> A["3 Act"]
  A --> Y
  A -. "4 trace" .-> G["artie generate"]
  G --> K[".heart.yaml + pins"]
  1. Sync, no model: read the representation; fetch its forms and schemas by link; revalidate them with their ETags.
  2. Reason, the model: it sees only the state, the forms offered now and the step's words, and picks one form and its values. ARTIE checks the values against the form's schema.
  3. Act, no model: send it with If-Match. A 412 reads again and decides again.
  4. Every exchange is traced. artie generate turns the trace into a kept script and its pins.

A kept run: the model only where something changed

flowchart TD
  T(["Next step"]) --> Y["1 Sync"]
  Y --> P{"2 Pin holds?"}
  P -- "yes" --> A["3 Act, no model"]
  P -- "changed" --> F{{"4 Words: model"}}
  F --> A
  A --> T
  A -. "5 after the run" .-> K["Keep the repair"]
  1. Sync: the same deterministic read as above.
  2. Guard: the form the step uses is held to its pin before any request.
  3. Act: the script's own values, with If-Match; no model.
  4. A changed form: the step falls back to its words, and the model chooses from what is offered now.
  5. Keep: a repair that worked, every value the script's own, is written into the script and its pins, so the next run needs no model.

The work this is about

  • Work done in bulk, again and again: the same business process over many records, every day, for months.
  • Its shape can be found up front. One exploratory run with the model finds the way: which links, which forms, which values. Records in different states take different paths, but a few known ones, not a new one each time.
  • Inference spent once, to make the work deterministic. The way is kept and run with no model, held to the server's controls. The model comes back only at the edges: where the service changed, or a record is in a state not met before.
  • Not infinite novelty. Tasks that are new in every run are another matter; there, a model in the middle of every run earns its keep.

In short

  • ARTIE found the way once, in plain words, and wrote it down. One goal run with the model over 6 employees (48,491 tokens, 18 calls), then artie generate wrote the script: a loop over the list, acting on what each employee offers.
    More
    • The goal is plain text (shown below). The model planned each move: search, open each employee, give notice or dismiss, go back.
    • artie generate saw that the run visited the members of one list one by one, and wrote that as a loop (whenever) with one case per action the run took (when-offered), not as six steps by name.
    • The script is held to the forms the run was offered (its pins), so a changed form is caught before any request.
  • The script then used no model at any size, and fetched 3 form sets a run, one per state, for 6 employees or 90: right in 15 runs of 15.
    More
    • For each employee it reads what the server offers right now, and takes the matching case: give notice, dismiss, or leave it.
    • A form set is the list of actions the server offers for a resource in one state, published once at its own address and shared by every resource in that state. ARTIE keeps it for the run: three states, three fetches, however many employees.
    • Correct means: each working employee now on notice, each on notice now dismissed, the dismissed left, and no one else touched.
  • Without a case for a state, the model is asked for each record in it: a script with the give-notice case alone asked 2, 10 and 30 times. Keeping the new case after the first time (not built yet) takes it back to none.
    More
    • That script knows only what to do with working employees. For one on notice no case matches, so ARTIE falls back to the step's words and asks the model which offered action fits. The model picks dismiss, correctly, but for every such employee, in every run.
    • The fix: once the model's choice has worked, write it into the script as a new case, as ARTIE already does when a release renames a field.
  • Code mode writes a loop, so its tokens per run hardly grow with the number of employees: about 10k on endpoints, 24k to 36k on HAL-FORMS alone. It pays them in every run, with a sandbox.
    More
    • Code mode is the model writing Python in a sandbox. It lists the employees and loops over them, so 90 cost about what 6 did.
    • But it finds the way and writes the program again in every run: 1,000 runs cost 10 to 35 million tokens, and each program starts a sandbox.

How the generated script works

flowchart TD
  S(["1 Search by surname"]) --> E["2 Each employee in the list"]
  E --> O{"3 What does it offer?"}
  O -- "give notice" --> G["act: give notice"]
  O -- "dismiss" --> D["act: dismiss"]
  O -- "nothing" --> N["4 note: left as is"]
  1. One search, as the server offers it, by name.
  2. whenever visits each member of the list, by its link.
  3. when-offered takes the first case whose act the employee offers now. The server decided its state; the script only reads the offer.
  4. An employee that offers none of the cases takes otherwise, with no model.

The goal, and the script ARTIE wrote from it

artie/t5.goal.md: the goal, as a person writes it
---
start: http://localhost:8099/
limits: { moves: 100 }
---

Move every employee named Miller one step through leaving: give notice to anyone working, dismiss anyone on notice, and leave the dismissed as they are.

- Find the employees named Miller
  - Move each of them one step: give notice to anyone working, dismiss anyone on notice, and leave the dismissed as they are `moves 60`
artie/t5.generated.heart.yaml: what artie generate wrote from the goal run
# Generated by artie generate from ../runs/artie/artie-goal-t5-20261103-122953.yaml, the run of t5.goal.md.
# Every selection as that run made it, nested as it nested, with no model.
# The members of a list the run visited one by one are each acted on by what they offer (when-offered).
# What it was offered is pinned in t5.generated.pins.yaml, held to before every act.
#   artie run t5.generated.heart.yaml
heart: 1
kind: kept
start: http://localhost:8099/

steps:
  - act: staff:search-employees
    fields:
      name: Miller
    intent: Find the employees named Miller
    then:
      - whenever:
          - when-offered:
              - act: staff:give-notice
                inferred: give notice to this employee
                from-intent: "Move each of them one step: give notice to anyone working, dismiss anyone on notice, and leave the dismissed as they are"
                then: []
              - act: staff:dismiss
                inferred: dismiss this employee
                from-intent: "Move each of them one step: give notice to anyone working, dismiss anyone on notice, and leave the dismissed as they are"
                then: []
            intent: "Move each of them one step: give notice to anyone working, dismiss anyone on notice, and leave the dismissed as they are"
            otherwise:
              - note: none of these acts is offered here
  • The run opened six employees one by one; generate wrote the loop, not six steps by name.
  • from-intent keeps the goal step's words with each case, so a changed form falls back to them.

Code mode on HAL-FORMS: its last program, at 90 employees a loop it wrote, its fourth try 
import os,urllib.request,json,collections
b=os.environ['API_BASE'];t=os.environ['API_TOKEN']
H={'Authorization':'Bearer '+t}
def g(p):
    r=urllib.request.urlopen(urllib.request.Request(b+p,headers=H));return json.load(r),r.headers['ETag']
items=[];p='/employees?name=miller'
while p:
    d,_=g(p);items+=d['_links']['item'];n=d['_links'].get('next');p=n['href'] if n else None
res=collections.Counter();errs=[]
for i in items:
    e,et=g(i['href'])
    k={'working':'giveNotice','on notice':'dismiss'}.get(e['status'])
    if not k: continue
    tp=e['_templates'][k]
    h=dict(H);h['If-Match']=et
    data=None
    if tp.get('contentType'): h['Content-Type']=tp['contentType'];data=b'{}'
    try:
        r=urllib.request.urlopen(urllib.request.Request(b+tp['target'],data=data,method=tp['method'],headers=h));res[(k,r.status)]+=1
    except Exception as x:
        res[(k,str(x))]+=1;errs.append(x.read())
print(res,errs[:2])
c=collections.Counter()
for i in items: c[g(i['href'])[0]['status']]+=1
print(c)
  • It decides each employee's state from its status member, then takes the matching form's target and method from _templates, with the ETag it read.
  • Its earlier programs in the run wrote without If-Match (428) or dismissed with the wrong method (405); the server refused them, and nothing wrong was written.

How it was run bench, seeding, files
  • Bench: exhibits/mcp-over-openapi/bench.py --arms artie-generated,artie-grow,code-fresh,code-heart-noapi --tasks t5 --reps 5 --population N,N,N, for N of 2, 10 and 30. Sonnet 5.5; code mode had 16 turns and the sandbox of the other runs.
  • Seeding: the notice release on (PUT /_sim/employees/changes), then each employee hired, given notice and dismissed through the service's own acts, before the measured requests.
  • Names: the goal run and the generated script's runs seeded employees named Miller; the one-case script's and code mode's runs seeded another surname, shown here as Miller.
  • Right: every employee moved one step (working to on notice, on notice to dismissed), the dismissed left, and no one else touched.
  • The goal run: artie run t5.goal.md --reasoner claude at 6 employees (runs/artie/artie-goal-t5-20261103-122953.yaml), then artie generate its trace --format yaml: artie/t5.generated.heart.yaml and its pins.
  • Files: the generated script's runs in runs/states-generated-2.jsonl, -10, -30; the others in runs/states-2.jsonl, -10, -30; ARTIE's traces in runs/artie/.
  • The plan: spec/PLAN-COST-FOLLOWS-STATES.md. The release-through-change runs: Wayfinding Through Change.
Limits said plainly
  • The one-case script was written by hand, as generate would write it from a run that met only those working.
