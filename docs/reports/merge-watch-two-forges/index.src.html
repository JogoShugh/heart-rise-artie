One Script, Two Forges

The release goal walked once with Claude on GitHub and kept as a script. The same script then released five pull requests on GitHub and five merge requests on GitLab, with no model. Follows The Release, Captured Once with Claude.

1 capture, on GitHub: 20 calls claude-sonnet-5-5 · 33,876 input tokens · 3,040 output · 29,424 read from cache · 61 steps in 58 s · the capture
GitHub: 5 replays, 0 calls 56 to 61 steps, 18 to 22 s each · 4 promoted, 504 stopped by S3 as it should
GitLab: 5 replays, 0 calls same script, unchanged · 56 to 61 steps, 16 to 18 s each · 4 promoted, 504 stopped by S3 as it should

How it works

  • One set of words for both forges. The goal and the script name relations from a shared scm: profile: scm:pulls-get, scm:merge, scm:comment. Neither says GitHub or GitLab. The only difference between the runs is one input: scm, the gateway's address.
  • One gateway program, two connectors. Each forge sits behind the HEART gateway with its own connector: github-scm on 8098, gitlab on 8094. A connector is declarations only, no code.
  • Normalized on the way out. Each connector answers in scm's words. GitLab's opened reads as open, its merged as closed with merged: true, and its detailed_merge_status as mergeable_state. Where a value had to change, GitLab's own is kept under upstream. Going in, scm's method: squash becomes GitHub's merge_method: squash or GitLab's squash: true.
  • Everything else is the same parties. The watcher, the CI wrapper in front of the real Jenkins, the library preview and Dev. On GitLab, Jenkins fetches the merged commit from GitLab.
