The Merge Watch Release

A pull request released to Dev across five parties.

  • Each party is its own HEART service at its own address:
    • GitHub, through the gateway
    • an offer watch
    • a real Jenkins, behind a wrapper
    • the preview Jenkins deploys
    • Dev
  • Every wait is a RISE reply. ARTIE makes the reply before it asks; the party it asks answers it, signed.
  • Every address after a party's entry is handed over by an answer's links.

What happened, in order

  1. ARTIE reads the gateway's entry and opens the pull request.
  2. It makes its reply, then asks the offer watch to be told when the pull request offers github:merge. GitHub is still working out mergeability; the watch says it is still looking, then, once GitHub has, answers the reply, linking the pull request.
  3. ARTIE follows that link and merges by squashing: a real commit on main in git. It reads the merge commit's sha from the pull request.
  4. It makes another reply and asks the CI wrapper to build that commit. The wrapper starts the Jenkins job; Jenkins' notifications become signed answers: progress, then completed, linking the deployment, the smoke script it archived, and the log.
  5. ARTIE reads the smoke script the build links, and runs the scenarios against the deployment it links.
  6. All passed: it promotes the merged commit to Dev, citing the smoke run. Not all: it comments on the pull request with those that failed.

What is and isn't ARTIE yet

  • These runs were made by ReleaseTrace (heart-sims tests), a scripted client that plays ARTIE's part step by step, by the goal below, by links alone. It is not yet ARTIE running release.goal.md: that needs two additions to the goal grammar, At {url} (another party's entry, mid-goal) and running a script a link hands over. Those are the next step.
  • The smoke scenarios are coded in the same client, from smoke.goal.md; the build archives and links that goal. Capturing it as a kept script, walked once by ARTIE with the model, comes with the grammar.
  • ARTIE's replies are made through the release's control route (POST /_release/replies/{reply}), as ARTIE's runner will make them itself.
  • The offer watch is its own party, not part of the gateway: the gateway has no watch, and this one works for any HEART resource.

The goals

release.goal.md
---
start: http://localhost:8098/
inputs:
  owner:   { default: acme }
  repo:    { default: web }
  pull:    { question: "Which pull request?" }
  watcher: { default: http://localhost:8099/ }
  jenkins: { default: http://localhost:8170/ }
  dev:     { default: http://localhost:8190/ }
---

Release a pull request to Dev once it can be merged and its build passes its smoke test.

- In {owner}/{repo}, open pull request {pull} `as pr`
- At {watcher}, ask to be told when {pr} offers `github:merge` `as watch`
- Once {watch} says it does, follow the pull request it links, and merge it by squashing `as merged`
  Or give up after 30 minutes, and comment on {pr} why.
- At {jenkins}, build commit {merged.merge_commit_sha}, asking to be told how it goes `as build`
- Once {build} has succeeded:
  - Follow its `ci:deployment` link `as preview`
  - Run the smoke script {build} links as `ci:smoke-test`, with deployed = {preview} `as smoke`
  Or, once {build} has failed, comment on {pr} with the stage that failed, linking the log {build} links as `ci:log`.
- At {dev}, open Dev; if {smoke.passed}, promote commit {merged.merge_commit_sha}, citing {smoke} `as promotion`
  Otherwise, comment on {pr} with the scenarios that failed and why.
smoke.goal.md, kept in the library's repository, archived by each build
---
start: "{deployed}"
inputs:
  deployed: { question: "Which deployment of the library?" }
---

Check that the library works as a member would use it. Each scenario starts at the library's entry.

- Find a loan: search the loans for "Matilda"; it should list "Matilda". `S1`
- Read it: open that loan; it should say who wrote it and when it is due, and offer renewing. `S2`
- Renew: renew it; its due date should move three weeks later. `S3`
- A refusal is explained: renew it again with the version read before the renewal; it should be refused as stale,
  and the refusal should link the loan to read again. `S4`
- Report a problem: report "missing pages" on the loan, choosing from the kinds the library lists, with a short
  comment; the loan should show the problem reported. `S5`
