HEART and ARTIE · after the merge watch

The Other R’s

Everyone talks about reasoning. Business systems run on repeatability, reliability, resilience and right behavior. The merge watch keeps reasoning to the one place it earns its keep, and lets the other R’s carry the load.

Each R gets a short section: what it means, what the merge watch did, and the evidence. The evidence sits under Technical detail; Show all detail above opens every one.

1The complaint

People building with AI keep meeting the same surprise: the same input, sent twice, gets two different answers. When they ask why, they are told it’s probabilistic.

  • Everyone knows a model is probabilistic. That is a description, not an answer.
  • Business systems have been held to other standards for decades: transactions that commit or don’t, requests that are safe to retry, audit logs, changes reviewed before they ship.
  • Those expectations didn’t lapse because a model is in the loop. The AI revolution promised more capability, not less dependability.
  • The fix isn’t a better prompt. It is architecture: decide with the model where judgment is needed, and let everything else be deterministic, checked and kept.
  • People who have worked in this field for years should be offering exactly that, or something close. The rest of us, building systems that must be reliable and right, can reasonably ask for it.

2Where reasoning earns its keep

In the merge watch, the model does two jobs. It decides each step once, the first time the step is needed. And it writes one sentence to an author whenever a merge gives up. Everything else runs without it.

  • Deciding is reasoning used once: reading the goal’s words against what the server offers, and choosing a relation, a check or a field. Kept, it never needs asking again.
  • Writing to a person is reasoning used every time, because every case is different. The goal marks that one line reasoned.
  • Over an hour: 2,740 steps, 5 model calls. That isn’t a model doing less than it could. It is a model doing only what nothing else can.
    - Once it can be merged, merge it by squashing.
      Or give up after 3 minutes.
      Otherwise, tell its author in one friendly sentence why it wasn't merged and what to do next. `reasoned`

3Who carries the other R’s

If the model carries only reasoning, the rest has to come from somewhere. In the merge watch, three parties carry it: the server, the script, and the people.

  • The server carries what must be true now: which acts are allowed, why not, and whether the state is still the one you read.
  • The script carries what must be the same every time: kept decisions, replayed; a memory of what it saw; good manners.
  • The people carry what must be accountable: a goal they can read, a script they can review, a record of every act, and a way to stop it.

4Same every time

Repeatability · same goal, same state, same result

The second pull request is merged the way the first was, not reconsidered. The decision was made once, on a real pull request, and kept.

Technical detail: the kept decisions, and the script line each became 
merge it by squashing: decided github:merge, at …/pulls/820
if: it's labelled hold: decided the check {"github:labels":["hold"]}, at …/pulls/820
leaveWhere("leave it, and say so once.") { "github:labels" has hold }
act("github:merge", "merge_method" to "squash") {}

Every later pull request, every later look, runs those lines. No model is asked.

Reliability · it works every time, unattended

An hour, a stream of bumps, no one watching. Six merged, two left alone, five authors told why, and the watch stopped when its issue was closed.

Fewer dice rolls, fewer losses: each step that runs on a kept decision is a step that can’t come out differently.

Reproducibility · show afterwards exactly what happened, and why

Every run keeps a capture: each step, its request and answer, and the model’s stated reason for each decision. From it, the script is generated, line by line, and each line points back to the goal line it came from.

5When things go wrong

Resilience · keep going, and never make it worse

A look that fails is tried again at the next. A wait that never ends gives up on time. A merge chosen from a view that has since changed is refused, not applied.

Technical detail: a failed look, and a stale merge 
note: A look failed: …; looking again next time.

PUT …/pulls/825/actions/merge
If-Match: "seq-0.hsf.L0.ca86bad8d04b304a"
→ 412 Precondition Failed      the pull request changed since it was read

Resilience comes mostly from the server saying no clearly, and the client treating no as normal.

Recoverability · stop, and pick up where it left off

Run with a memory, the watch remembers what each pull request looked like and how long each wait has run. Restarted, it answers only what changed, and a wait gives up when it would have.

Technical detail: a wait that resumes 
artie run merge.kts owner=JogoShugh --remember watch.yaml

From the feature that pins it down: “pull request 1 has waited since noon, so it gives up at ten past, though the second run began at seven past.”

Refusal · the server may say no, and says why

When merging isn’t possible, the server doesn’t just withhold the form. It gives the reason, in its own words, which the model can pass on and the author can act on.

Technical detail: why not 
{ "rel": "/profiles/github#merge", "title": "Merge",
  "reason": "A draft can't be merged; mark it ready for review first." }

6Doing the right thing

Right behavior · only what is allowed, now

The script can’t merge a draft, because merge isn’t offered on a draft. The wrong move isn’t forbidden by a prompt; it is simply not there.

Technical detail: the forms on a draft 
"_forms": { "github:comment": { … }, "github:close": { … }, "github:edit": { … } }
once("github:merge", giveUp = 3.minutes, …) { act("github:merge", "merge_method" to "squash") {} }

once waits for the merge form to appear. Until it does, nothing is sent.

Restraint · the model only where judgment lives

One line of the goal is marked reasoned. That mark is restraint written into the language: a person decides, in advance, where the model may act on its own each time.

Recency · the rules come from the server, at the moment of acting

The script holds no rule about drafts, conflicts or permissions. It reads them, every look, from the answers. When GitHub changes a rule, the gateway’s answer changes, and the script is current without a release.

Respect · work alongside people

Held pull requests are left alone and noted once, however often they change. A wait gives up once for each pull request, so each author is told once. Good manners are part of correct behavior when software works next to people.

Technical detail: noted once, for the whole run 
note: Left …/pulls/810: leave it, and say so once.
note: Left …/pulls/805: leave it, and say so once.
note: Left …/pulls/822: leave it, and say so once.

An early run noted the same held pull request about twenty times in an hour; the note is now kept once per pull request.

7People in charge

Readability · a person can read what it will do

The goal is fifteen lines of plain words. The generated script is thirty-five lines a developer can read in a minute.

Reviewability · someone else can check it before it runs

The script has no model in it except the one marked line, so it can be reviewed like any code: in a pull request, by a colleague, before it touches anything.

Technical detail: the script, and what it is held to 
watch(until = { at("watch") { "state" eq "closed" } }) {
    act("github:pulls-list", "owner" to owner, "repo" to repo, "labels" to label) {
        whenever {
            has { "github:labels" has label }
            leaveWhere("leave it, and say so once.") { "github:labels" has hold }
            once("github:merge", giveUp = 3.minutes, otherwise = { why -> … }) {
                act("github:merge", "merge_method" to "squash") {}
            }
        }
    }
}
forms:
  github:merge:
    integrity: sha256-CY/mjcpRO2grR/xbdjTqaUXZFQaG/Q9F8YHBJMIkiIk=
    method: PUT

The pins say exactly which forms the script was reviewed against. If the server changes one, the script refuses to act.

Responsibility · every act traced

Each act in the record names the goal line it came from, the decision behind it, and the server’s answer. When software acts in someone’s name, that is what accountability looks like.

Revocability · stop it cleanly

Close the watch’s issue and the watch ends at its next look. Change a form on the server and a pinned script stops rather than guess.

8Rate · what it costs to run

Five model calls an hour: 12,979 tokens in, 971 out. A watch that asked the model at every look would have made thousands of calls, with thousands of chances to answer differently.

  • Cost and energy are part of whether a system is fit to run all day, every day.
  • The cheapest model call is the one a kept decision makes unnecessary.

9What to ask for

For anyone building business systems with AI, or buying them, these are fair questions. A good answer needn’t be this design, but it should be close.

  • Where exactly does the model run? Which steps, and why those? Can you point to them?
  • Can a decision be kept and replayed? If I run it again on the same state, do I get the same result?
  • Who enforces what is allowed? The prompt, or the system the agent acts on?
  • What happens when the system says no? Does the agent stop, retry blindly, or pass the reason on?
  • Can I read, and review, what it will do before it does it?
  • Is every act recorded, with the reason it was taken?
  • How do I stop it, and what happens to work in progress?
  • What does an hour of it cost, in calls and tokens?
Reason once, then let the other R’s carry the load.
