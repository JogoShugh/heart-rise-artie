What HEART needed, found by these runs

Native needed nothing changed. Each fix below is in ARTIE, test first, and the runs after it are on the fixed code.

  • The planner says why before each move. 1079117, 0ca4df2

    At the branch list it went back about one time in four instead of on to main; each wasted pair of moves ran its step out. Asked for its reason first, it went on to main every time. HEART reasoned runs 1 and 2 are from before this.

  • A follow reads a list's next pages to find a titled link. 4b75a7c

    The script followed the branch list to main as the run had; once the list grew, main was on its second page. The list offers next links; ARTIE follows them, building no address.

  • A script's act refused 412 is decided again once. 4b75a7c

    GitHub changes a new pull request a moment after making it; the script's edit, sent with the ETag it had just read, was refused. ARTIE has read it again; when the form is still offered and the lock file still holds, the act is sent once more. A second 412 stops the script.

What this trial does not test

  • A service that changes. Today's GitHub is the GitHub the native model learned. New features, moved paths, renamed fields in the gateway: where knowledge from training goes stale and what the service offers doesn't. That is the next trial.
  • The duplicate's link. Both arms closed the duplicate as a duplicate; native sent the original's id and GitHub kept no link to it. The checker asks for the reason, not the link.

On a GitHub it knows, Claude alone was faster, needed fewer model calls, and got it right every time from the start. HEART got there too, after the three fixes these runs found, and is slower for the gateway and its two calls a move. The case for HEART is the service that moves, which this trial left still.

Two scripts, one task

Both do the triage task with no model; both passed every run made on the code as it ended. Claude wrote the Python in one call from its own run's transcript. artie generate wrote the Kotlin from one HEART run's capture, with a lock file beside it.

import sys, os, json, time, base64
import urllib.request, urllib.error

OWNER, REPO, LABEL, STAMP = sys.argv[1:5]
TOKEN = os.environ.get("GITHUB_TOKEN")
if not TOKEN:
    sys.exit("GITHUB_TOKEN is not set")

API = "https://api.github.com"
R = "/repos/%s/%s" % (OWNER, REPO)


def req(method, path, body=None, ok=(200, 201, 204)):
    print("%s %s" % (method, path), flush=True)
    data = json.dumps(body).encode() if body is not None else None
    r = urllib.request.Request(API + path, data=data, method=method)
    r.add_header("Authorization", "Bearer " + TOKEN)
    r.add_header("Accept", "application/vnd.github+json")
    r.add_header("X-GitHub-Api-Version", "2022-11-28")
    r.add_header("User-Agent", "triage-script")
    if data is not None:
        r.add_header("Content-Type", "application/json")
    try:
        with urllib.request.urlopen(r) as resp:
            status = resp.status
            raw = resp.read()
    except urllib.error.HTTPError as e:
        status = e.code
        raw = e.read()
    if status not in ok:
        sys.exit("FAILED: %s %s -> HTTP %d: %s" % (method, path, status, raw.decode(errors="replace")[:500]))
    if raw:
        try:
            return json.loads(raw)
        except ValueError:
            return None
    return None


def b64(s):
    return base64.b64encode(s.encode()).decode()

Much of the time between them is strictness. Before and after each act, ARTIE checks what the Python never does: it won't send what it can't stand behind, and a refusal stops it before its harm. The Python is fast because it trusts its memory and takes any 2xx as success, which is how an ignored field passed.

The Python, read closely

It is good code for what it is: what one model remembers of one API, written down. Its weaknesses are the weaknesses of that.

weakEvery address and field is the model's memory of GitHub.
"/git/ref/heads/main", "/git/refs", "/contents/…", "/pulls/%d/merge", "sub_issue_id", "state_reason"
Nothing in the script was read from the service: each path, each field, each value of state_reason is what the model learned of GitHub's REST API. Move one path, rename one field, add one required field, and the script fails at that line, or worse, sends something the service quietly ignores. It can't tell which.
weakWhere its memory runs out, it guesses, and a guess that is ignored passes.
"duplicate_of": crash_id, "duplicate_of_issue_id": crash_id
It sends two field names for the duplicate's original, hoping one is right. GitHub ignored both: the duplicate is closed as a duplicate of nothing. Its own check asks only for state_reason, so the script says done. A field the service doesn't know is never refused, only dropped.
weakNo validators: every write is blind.
req(…) sends no If-Match on any PATCH, PUT or POST
It never meets a 412 because it never says what it read. That is why it never stalled on GitHub's late change to a new pull request; it is also why it would overwrite a change someone else made between its read and its write, and never know.
weakIt reads GitHub's internals to decide when to merge, and merges past failing checks.
mergeable_state in ("clean", "unstable", "has_hooks")
GitHub's word for whether a pull request can be merged is a field the model interprets, not an action the service offers. "unstable" means a check is failing or still running (one the branch doesn't require): the script merges it anyway, as it would one with no checks at all.
weakIt does what was already done, and code the task never needed.
PATCH … {"state": "closed", "state_reason": "completed"} on the crash issue; the reopen branch after creating it
The merge has already closed the crash issue; the script closes it again, as a fixed step. It reopens the crash issue if it isn't open just after making it, a case that can't happen. A script that can't see what is possible does everything, in case.
weakIt stops half done, and running it again makes a second set.
sys.exit("FAILED: …") at the first error; nothing checks what an earlier run left
A failure leaves issues, a branch and maybe a pull request behind, with nothing to say which. Run again with the same stamp, it opens the issues again; there is no record of what it did beyond the lines it printed.
weakNo retries, no rate limits, a pinned API version.
"X-GitHub-Api-Version": "2022-11-28"; urlopen with no retry
A 502 or a secondary rate limit ends the run. The API version header pins it to the GitHub the model remembers; a version that drops a field it uses is found by failing.
strongIt reads every number, id and sha from the answers.
crash_no, crash_id = crash["number"], crash["id"]; "sha": pr_now["head"]["sha"]
Nothing from the run that taught it is written in: issue numbers, ids, the head sha the merge is held to, all come from GitHub's answers as it goes. It merges only the head it saw.
strongIt goes straight to what it needs.
GET /git/ref/heads/main, then POST /git/refs
23 requests where the ARTIE script makes 58: no list to page through, no block to come back to. On a GitHub that matches its memory, that is why it is three times faster.
noteIt checks its end state, its own way.
the three GETs at the end
It reads the three issues back and checks state, state reason and the lock: a good habit, but only for what it thought to check, and not the duplicate's original, which it had guessed at.

The Kotlin, for fairness

strongRelations, not addresses.
act("github:open-issue", …), follow("github:repos-list-branches"), act("github:close-duplicate", …)
Each step names what the service offers; ARTIE finds the form or link in the representation it holds and builds the request from it. A moved path, a new required field, is the service's to say.
strongHeld to what was offered.
heart-script.pins.yaml: each form's integrity, checked before every act
A form that changed, or is no longer offered, stops the script before it sends anything: it refuses before its harm, never after.
strongEvery write says what it read.
If-Match on every act; sync() after making a resource; a 412 decided again once
It can't overwrite what it didn't see. Where GitHub changes something on its own, it reads again and decides again, within what its lock file allows.
strongIt waits on the service's word.
until(tries = 20) { offers("github:merge") }
Whether the pull request can be merged is whether merge is offered, not a field it interprets.
strongEvery value has a source.
issueNumber = state.long("number"); heart-script.derivation.yaml
Each variable is read where the run found it, and the derivation file says, for each value, where it came from and by which rule.
weakIt replays the run's route, not the shortest.
follow("github:repos-list-branches") { follow("item", "main") { … } }
The planner got to main by the branch list, so the script does too: 58 steps to the Python's 23, and the list pages as it grows. It is slower for every request going through the gateway.
weakIt leans on what the service did on its own.
no close of the crash issue
The run made no act at the crash issue's close: the merge had closed it. The script relies on that, and on its check to catch it if GitHub ever doesn't.
noteIts words can carry a value from the run.
intent = "close it as a duplicate of the issue with id ${issueId} (#215)"
An intent's words are only words: the act's values are its fields, here issueId, read fresh. But the words still say #215, the run's number.

The Python is faster because it knows GitHub. The Kotlin is slower because it asks. The trial ran against the GitHub the model knows; the next one changes it.
