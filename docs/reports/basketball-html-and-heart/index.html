How to read it
  • Every act goes through a form the game's last answer offered, sent with If-Match, the version just read.
  • What is offered depends on the game's phase: scheduled offers only tip-off; a timeout offers only resume-play and correct-score; a break offers only start-period.
  • In the HTML, offered acts are bright buttons that open a dialog; acts not offered are grey and say why when pressed.
  • The same server answers both dialects: no controller code per dialect, one declaration of the resource.

Building a volleyball scoring domain from this one
  • Copy domains/basketball and rename it. The HEART library serves it; there are no controllers to write.
  • declaration: the vocabulary (BasketballProfile), the resource type (Games), each act's input and what it records (GameActs). For volleyball: point, side-out, rotation, substitution, timeout, end-set.
  • domain: the events, the state and its fold, and the rules a schema can't say (GameService). For volleyball: sets to 25, win by 2, a fifth set to 15, rotation on side-out.
  • The phase-to-acts table in domains/basketball/README.md is the design: write the volleyball one first (scheduled, set live, timeout, between sets, match over), and each row becomes what the game offers in that phase.
  • store and config: copied nearly as they are (games and rosters, in memory or Postgres).
  • The HTML for people and the HEART JSON both come for free, as shown above.
