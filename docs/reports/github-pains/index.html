GitHub Automation Pains

Automating GitHub through its API: what hurts, and where HEART helps

13 pains people meet when scripts, bots and agents drive GitHub, each with its sources, what our own runs showed, how HEART answers it, and what we would still have to build. Researched 2026-10-23; a tile filters the pains by fit.

The pains

Why can't I merge?

strong

What people hit

The API says a pull request can't be merged, but not why. mergeable_state is a single undocumented word (blocked, behind, unstable, dirty, unknown), and the merge itself answers 405 for a draft, missing reviews, failing required checks or a ruleset alike. Each script works the reason out again from branch protection, reviews and checks, and each gets it slightly wrong.

Our evidence

Under the meddler's M4 (the pull request turned into a draft), artie-bare sent the merge 30 times, a second apart, and got 405 "Pull Request is still a draft" each time before giving up after about 62 s.

How HEART answers

Offer the merge only when it would be taken, and say why it isn't in hr:unavailable: "a draft", "needs 1 approving review", "check build is failing". One place works the reason out, the gateway, and every client reads it.

Still to build

The gateway's GitHub connector doesn't yet derive each blocking reason (draft, reviews, required checks, rulesets) from GitHub's data into hr:unavailable.

Sources (2)
  • GitHub REST docs: get a pull request, merge a pull request documented
    mergeable_state appears in the schema only as "required, string", with no meanings. The merge endpoint answers "405 Method Not Allowed if merge cannot be performed".
  • GitHub Community #21886: the reason a pull request isn't mergeable reported
    GitHub staff, 2018: "There isn't an API that summarizes why a PR is mergeable or not, only that it is or isn't." The asker fell back on the undocumented mergeable_state.

Mergeability arrives later

medium

What people hit

Right after a pull request opens or its base moves, mergeable is null while GitHub works it out. Scripts poll with hand-written loops and backoff, and some read null as "no".

Our evidence

Claude's Python polls GET /pulls/N up to 30 times, 2 s apart. The careful ARTIE script says until(tries = 20) { offers("github:merge") }. artie-bare retries the merge itself.

How HEART answers

The wait is said once, in the task's words ("once the merge is offered"), not as a loop of field checks. The polling is still there underneath; HEART makes it one rule in one place, not faster.

Still to build

Backoff on the wait, and a wait that ends with the reason when the merge will never be offered (it's a draft), instead of running out of tries.

Sources (2)
  • GitHub REST docs: get a pull request documented
    "If the value is null, then GitHub has started a background job to compute the mergeability. After giving the job time to complete, resubmit the request."
  • Zuul's GitHub driver reported
    Reading null during the calculation as "not mergeable" gave false negatives; Zuul stopped checking it and relied on branch protection instead.

Two writers, one overwritten

strong

What people hit

A bot and a person, or two bots, change the same issue or pull request. The later write wins and the earlier is lost without a word: labels flipped back, a description edit undone, an issue someone closed as not planned closed again as completed.

Our evidence

In the meddler's storm (M1, M2, M3, M5), Claude's plain Python and artie-bare both did harm in 4 of 4 runs and exited 0. artie-goal did no harm: 4 of 5 runs succeeded and the fifth stopped safely.

How HEART answers

Every act carries the validator of the state it was chosen from, and a changed resource answers 412, so the client decides again on what is there now. The goal client then acts only on what is still offered.

Still to build

Honesty about the limit: GitHub can't check a condition atomically, so the gateway reads, compares, then writes. That narrows the window to milliseconds; it doesn't close it. Only the endpoints with a body sha (merge, file contents) are truly safe.

Sources (2)
  • Our probe of GitHub, 2026-10-23 probed
    PATCH /issues/677 on the scratch repository with If-Match answered 400: "Conditional request headers are not allowed in unsafe requests unless supported by the endpoint". The same PATCH without it: 200. GitHub has no general optimistic locking on writes.
  • GitHub REST docs: merge a pull request documented
    A few endpoints carry their own precondition in the body instead: the merge's sha ("409 Conflict if sha was provided and pull request head did not match"), and a file update's sha.

Resource not accessible by integration

strong

What people hit

A workflow or app gets a 403 and has to guess the cause: the GITHUB_TOKEN is read-only by default, scoped to the repository that triggered it, restricted on pull requests from forks, or an app's permissions changed. People widen permissions until it works.

Our evidence

Not measured. Our runs use one personal token with full access to the scratch repository.

How HEART answers

The same as the merge: an act the token can't make isn't offered, and hr:unavailable says which permission is missing. A person or an agent sees "contents: write needed" before trying, not a 403 after.

Still to build

The gateway doesn't read what the caller's token may do. GitHub tells fine-grained tokens and apps which permissions an endpoint needs in a response header (X-Accepted-GitHub-Permissions, to be confirmed), which could feed this.

Sources (2)
  • GitHub Community #57878 reported
    One of many threads on the same 403 and the permissions block that fixes it.
  • GoReleaser: resource not accessible by integration reported
    The GITHUB_TOKEN is scoped to the triggering repository, so writing to another one (a Homebrew tap) needs a personal access token.

A retry makes a second issue

medium

What people hit

A create times out, the script retries, and there are now two issues or two comments. GitHub's API takes no idempotency key, so careful bots embed a marker and look for it before resending.

Our evidence

artie-bare retries a write only after an until step, and only the merge, which GitHub refuses twice. No run has timed out on a create yet, so we haven't seen it.

How HEART answers

An act answered 201 names what it made in Location; a client that lost the answer can ask the gateway what that act made. The gateway, not every script, keeps the key.

Still to build

Idempotent acts in the gateway: a key per act, kept with what it made. Not built.

Sources (1)
  • laravel-error-monitor-github reported
    A write whose answer never arrived may have succeeded, so it is never simply sent again: the package looks for its fingerprint in the repository's issue list first, not in search, which lags.

Lists and search lag writes

medium

What people hit

A script creates something, then looks for it in a list or search, and it isn't there yet. Scripts sleep, or pick the wrong item.

Our evidence

The ladder waits 10 s before checking a run, because GitHub's lists catch up a few seconds late. The meddler reads each next issue number directly instead of listing.

How HEART answers

A HEART client follows the Location of what it made, not a list. The careful script never searches for its own issues.

Still to build

Nothing for our own writes. Someone else's new items still come through lists.

Sources (1)
  • GitHub status, December 2025 reported
    During an incident, search results could be up to three minutes old. Search is an index that can lag the write.

Rate limits, especially on writes

against

What people hit

5000 requests an hour, plus secondary limits that change without notice: about 80 content-creating requests a minute and 500 an hour, writes costing 5 points to a read's 1, at most 100 at once.

Our evidence

The careful run made 237 GitHub calls for the triage; the bare script made 19 for the same writes. Caution costs calls today.

How HEART answers

Not yet an answer. It could be: most of the careful run's extra calls are re-reads, and a re-read sent with If-None-Match and answered 304 is free.

Still to build

The gateway's re-reads as conditional requests, per token. A count of GitHub calls per arm on the care dial.

Sources (2)
  • GitHub REST docs: rate limits documented
    Secondary limits as above; they are subject to change without notice, and may apply for undisclosed reasons.
  • GitHub REST docs: best practices documented
    A conditional request answered 304, made with the same authorization, doesn't count against the primary limit.

Too many tools for an agent

strong

What people hit

GitHub's MCP server exposes about 100 tools. Loaded all at once they fill the context, exceed some clients' tool limits, and agents pick the wrong one. GitHub's answer is to let people switch toolsets and single tools on and off by hand.

Our evidence

artie-goal, reasoning from what each representation offers, came through the storm without harm. It saw a handful of acts at a time, not 100 tools.

How HEART answers

The tools an agent sees are the acts this resource offers now. A closed issue offers no "close"; a draft offers no "merge". The list is short because the state makes it short, not because someone configured it.

Still to build

A measured comparison: the same goal by an agent on GitHub's MCP server and on heart-mcp, counting tokens, tools seen and wrong calls.

Sources (2)
  • GitHub changelog, 2025-12-10: tool-specific configuration documented
    An X-MCP-Tools header enables single tools, instead of the 27 two toolsets would bring in.
  • Arcade: lessons from GitHub's MCP server launch secondhand
    Users loaded every tool into their agent's context and were frustrated when the agent struggled.

Agents act on the wrong thing

medium

What people hit

Agents close issues as duplicates of issues that don't match, say an issue is solved when it isn't, or write a review without reading the pull request.

Our evidence

Under M3 (the team says the duplicate is a different crash), the Python and bare runs closed it as a duplicate anyway. artie-goal kept the team's call.

How HEART answers

HEART can't make the judgement right. It can make acting on a changed state fail, and a goal's "Done when" can say what must be true afterwards, checked by code, not by the model's word.

Still to build

The goal grammar ("Once…", "Done when") in spec/ideas/goals-that-work-alongside-others.md, unbuilt.

Sources (2)
  • A report about the Claude Code issue bot (third-party mirror) secondhand
    The bot closed issues as duplicates of issues that didn't match them.
  • Gigazine on GitHub Copilot's coding agent, 2025 secondhand
    In a Microsoft repository, the agent claimed to have solved issues it hadn't.

Actions' own writes don't start workflows

none

What people hit

A pull request opened with the GITHUB_TOKEN doesn't start its checks (or starts them awaiting approval), so an auto-merge waits forever. People switch to an app token or a personal token.

Our evidence

Not met: the scratch repository has no workflows.

How HEART answers

Nothing to fix; it's GitHub's rule against loops. At most, why-absent could say "checks haven't started" instead of the merge simply never appearing.

Sources (1)
  • GitHub docs: triggering a workflow documented
    Events triggered by the GITHUB_TOKEN will not create a new workflow run, except workflow_dispatch and repository_dispatch.

Two green pull requests, a red main

none

What people hit

Each pull request passes on its own; together they break the main branch.

Our evidence

Not met.

How HEART answers

GitHub's merge queue answers this. HEART would only drive it.

Sources (1)
  • Graphite: what is a merge queue secondhand
    The merge race, and merge queues that test each change on top of the ones ahead of it.

Backports resolved silently and wrongly

none

What people hit

Backport bots cherry-pick onto release branches; with conflicts resolved automatically, a backport can carry a line the original never had.

Our evidence

Not met.

How HEART answers

A git content problem, not an API one. Out of HEART's reach.

Sources (1)
  • gophercloud #2685 reported
    Every cherry-pick used the 'theirs' strategy, which resolved conflicts automatically and put in a line the original didn't have.

Events arrive twice, or out of order

medium

What people hit

A bot driven by webhooks gets the same delivery twice or events out of order, and acts on a state that has already moved.

Our evidence

Not met: our runs aren't driven by webhooks.

How HEART answers

Treat the event as a hint and act on the resource as it is now: read it, act with its validator. A stale or repeated event then finds nothing to do.

Still to build

Weak evidence: no GitHub-specific source checked. Worth confirming before it's claimed.

Sources (1)
  • Hookdeck: delivery guarantees secondhand
    Webhooks are delivered at least once; exactly once is at least once with idempotent handling.

pains.kts: the script that lays them out
// What people struggle with when they automate GitHub through its API, and where ARTIE and HEART answer it, as a page.
// The findings live in pains.yaml; this script only lays them out. The look comes from the reports' shared assets
// (report-shell.html, report-base.css, theme-switch.js), inlined, so the page needs nothing else at runtime.
//   artie run pains.kts out=../../docs/reports/github-pains/index.html artifact=/tmp/github-pains.html
// out gets a whole document for GitHub Pages; artifact, when given, the same page without the document skeleton.
import java.io.File
import org.yaml.snakeyaml.Yaml

val data by input(default = "pains.yaml", question = "Where are the findings?")
val out by input(question = "Where to write the page?")
val artifact by input(default = "", question = "Where to write the artifact copy, if anywhere?")
val source by input(default = "pains.kts", question = "Where is this script, to show it on the page?")
val assets by input(default = "../../docs/reports/assets", question = "Where are the reports' shared assets?")

fun Any?.map(): Map<String, Any?> = (this as? Map<*, *>).orEmpty().entries.associate { it.key.toString() to it.value }
fun Any?.list(): List<Any?> = (this as? List<*>).orEmpty()
fun Map<String, Any?>.text(key: String) = this[key]?.toString().orEmpty()

class Source(val label: String, val url: String, val confidence: String, val says: String)
class Pain(
    val id: String, val title: String, val fit: String, val hit: String, val sources: List<Source>,
    val ours: String, val heart: String, val missing: String, val seen: Boolean,
)
class Workflow(val name: String, val pains: List<String>, val why: String, val today: String)

val yaml = Yaml().load<Any?>(File(data).readText()).map()
val pains = yaml["pains"].list().map { it.map() }.map { p ->
    Pain(p.text("id"), p.text("title"), p.text("fit"), p.text("hit"),
        p["sources"].list().map { it.map() }.map { Source(it.text("label"), it.text("url"), it.text("confidence"), it.text("says")) },
        p.text("ours"), p.text("heart"), p.text("missing"), p["seen"] == true)
}
val workflows = yaml["workflows"].list().map { it.map() }.map { w ->
    Workflow(w.text("name"), w["pains"].list().map { it.toString() }, w.text("why"), w.text("today"))
}
val byId = pains.associateBy { it.id }

/** The fits in the order the page shows them: what each means, and the shared tone that colours it. */
class Fit(val means: String, val tone: String)
val fits = linkedMapOf(
    "strong" to Fit("HEART answers it directly", "good"),
    "medium" to Fit("HEART helps; the pain stays", "safe"),
    "against" to Fit("HEART makes it worse today", "bad"),
    "none" to Fit("not HEART's to answer", "quiet"),
)
val confidences = linkedMapOf(
    "documented" to "GitHub's own docs",
    "probed" to "we tried it against GitHub",
    "reported" to "a public thread or issue",
    "secondhand" to "a third party's account, not checked against GitHub",
)

fun esc(s: String) = s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace("\"", "&quot;")
fun tone(fit: String) = fits[fit]?.tone ?: "quiet"
fun fitTag(fit: String) = """<span class="tag ${tone(fit)}">${esc(fit)}</span>"""
fun conf(c: String) = """<span class="conf $c">$c</span>"""

val tiles = fits.entries.joinToString("") { (fit, f) ->
    """<button class="tile ${f.tone}" type="button" data-fit="$fit" aria-pressed="false"><b>${pains.count { it.fit == fit }}</b>""" +
        """<span class="name">$fit</span><span class="sub">${esc(f.means)}</span></button>"""
}

val summaryRows = pains.joinToString("\n") { p ->
    """<tr data-fit="${p.fit}"><td><a href="#${p.id}">${esc(p.title)}</a></td><td>${fitTag(p.fit)}</td>""" +
        """<td>${if (p.seen) "yes" else """<span class="none">no</span>"""}</td>""" +
        """<td>${p.sources.joinToString(" ") { conf(it.confidence) }}</td></tr>"""
}

val cards = pains.joinToString("\n") { p ->
    val sources = p.sources.joinToString("") { s ->
        """<li><a href="${esc(s.url)}" rel="noopener" target="_blank">${esc(s.label)}</a> ${conf(s.confidence)}""" +
            """<div class="says">${esc(s.says)}</div></li>"""
    }
    val missing = if (p.missing == "-") "" else """<div class="row"><h4>Still to build</h4><p>${esc(p.missing)}</p></div>"""
    """<article class="pain ${tone(p.fit)}" id="${p.id}" data-fit="${p.fit}">
      <header><h3>${esc(p.title)}</h3>${fitTag(p.fit)}</header>
      <div class="row"><h4>What people hit</h4><p>${esc(p.hit)}</p></div>
      <div class="row"><h4>Our evidence</h4><p>${esc(p.ours)}</p></div>
      <div class="row"><h4>How HEART answers</h4><p>${esc(p.heart)}</p></div>
      $missing
      <details><summary>Sources (${p.sources.size})</summary><ul class="sources">$sources</ul></details>
    </article>"""
}

val workflowRows = workflows.joinToString("\n") { w ->
    val chips = w.pains.joinToString(" ") { id ->
        byId[id]?.let { """<a class="tag ${tone(it.fit)}" href="#$id">${esc(it.title)}</a>""" } ?: esc(id)
    }
    """<tr><td><b>${esc(w.name)}</b><div class="sub">${esc(w.why)}</div></td><td>$chips</td>""" +
        """<td class="num">${w.pains.count { byId[it]?.fit == "strong" }}</td><td class="sub">${esc(w.today)}</td></tr>"""
}

val confidenceKey = confidences.entries.joinToString(" ") { (c, means) -> "${conf(c)} ${esc(means)}" }

val style = """
.conf { font: 11px var(--mono); padding: 0 6px; border-radius: 4px; border: 1px solid var(--rule); color: var(--muted); white-space: nowrap; }
.conf.documented, .conf.probed { color: var(--good); border-color: var(--good); }

td:first-child { min-width: 220px; }

.pain > header { display: flex; gap: 10px; align-items: baseline; flex-wrap: wrap; justify-content: space-between; }
.pain .row { display: grid; gap: 2px; }
.pain details summary { cursor: pointer; font-size: 14px; color: var(--muted); }
.sources { margin: 8px 0 0; padding-left: 18px; display: grid; gap: 8px; font-size: 14px; }
.says { color: var(--muted); max-width: 72ch; }
"""

val body = """
  <div class="tiles">$tiles</div>
  <div class="chipbar" id="showing" hidden><span id="showing-text"></span><button type="button" id="clear">clear</button></div>
  <section>
    <h2>At a glance</h2>

"""

val script = """
// The fit tiles: one pressed shows only its pains and rows; pressing it again, or clear, shows all.
(function () {
  var tiles = document.querySelectorAll('.tile[data-fit]'), bar = document.getElementById('showing');
  function show(fit) {
    tiles.forEach(function (t) { t.setAttribute('aria-pressed', String(t.dataset.fit === fit)); });
    var shown = 0, all = 0;
    document.querySelectorAll('.pain[data-fit], tbody tr[data-fit]').forEach(function (el) {
      el.hidden = !!fit && el.dataset.fit !== fit;
      if (el.classList.contains('pain')) { all++; if (!el.hidden) shown++; }
    });
    bar.hidden = !fit;
    document.getElementById('showing-text').textContent = fit ? 'showing ' + shown + ' of ' + all + ' pains: ' + fit : '';
  }
  tiles.forEach(function (t) {
    t.addEventListener('click', function () { show(t.getAttribute('aria-pressed') === 'true' ? '' : t.dataset.fit); });
  });
  document.getElementById('clear').addEventListener('click', function () { show(''); });
})();
"""
