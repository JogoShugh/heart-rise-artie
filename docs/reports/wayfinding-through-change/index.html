Wayfinding Through Change

One business process, run again and again while the service changes under it. Two architectures: a bag of endpoints, where a model writes code against operations, and hypermedia, where a client follows the controls the server offers. Two places for the model: in the middle of every run, or at the edges, to find the way once and to repair after a change.

In short

  • The question: as a service evolves, which architecture keeps a repeated process right, safe and auditable, and where must the model sit for that?
  • Wayfinding. From endpoints, the client builds every address itself. Code mode worked the way out again each run (27 programs for two tasks), or froze it (saved programs with employee IDs and an ETag written in). From hypermedia, ARTIE's kept script follows what the server hands it: the search's item link titled "Bilbo Baggins", the new employee's Location.
  • Evolution. A release renamed a field. The frozen code broke silently, 8 runs of 8, each exit 0. Fresh code adapted by reading the whole description again every run. ARTIE's pins noticed the changed form before any write, and the model repaired that one step.
  • Controls. The endpoint side had no conditional writes until we added them to its OpenAPI twin, and using them stays the client's choice. The HEART side offers its controls with the state: the forms allowed now, an ETag, a 412 when stale. No client wrote over the teammate.
  • Security. Code mode ran model-written code every run, so it needed a sandbox every run. ARTIE ran none: its script is data in a closed vocabulary.
  • Compliance. ARTIE's process is one kept script a person can review and diff, pinned to the server's forms, with a trace of every refusal and its reason. Code mode's was 27 different programs.
  • The model at the edges. ARTIE called it once per task to find the way, and after the release to repair: 8 runs of 20. Code mode called it in every fresh run. The tokens follow: 17,524 against 158,995, plus 42,483 once for ARTIE's wayfinding.
  • Repaired, not yet kept. ARTIE repaired in memory on every run after the release; its kept script and pins were not rewritten. Keeping the repair is the next step for self-repair.

Self-repair, done but not kept

  • What happened: in each of runs 7 to 10, ARTIE's pins refused the changed form, it fell back to the step's words, the model chose position, and the act was done. Then the run ended. The kept script, pins and config are unchanged on disk, so each later run repaired again: 3,093 tokens in t1, 1,288 in t3, every time.
  • The optimization: keep the repair. After a repaired act is done, write the chosen step into the kept script and its form into the pins, so only the first run after a change pays. With it, 17,524 tokens would have been 4,381.
  • What exists: repin: auto or propose writes new pins, but only when the script's own values still fit a changed form (on-change: values). A repair by the model needs the step itself written again.
  • What a run can tell is safe: the repair was chosen among forms the server offered, and the server took it with If-Match; what is saved is data in the closed vocabulary, not code.
  • What it must take care with: a value made from state is saved as a reference, never as the literal. t3's repair sent "ring bearer, retired"; saved, that must be ${state.role}, retired. ARTIE's trace records where each value came from (/role of the state read), so it can.
  • What a run can't tell: that the meaning stayed when the name changed. For that: checks in the kept script (the end state the first run reached), and propose for a person to approve, where compliance asks for review.

Where code mode did well

  • Fresh code mode was right every time. Every write to an existing record carried If-Match, 30 of 30, once the description offered it.
  • It adapts with no machinery of its own. It reads the current description every run, so a rename costs it nothing extra. ARTIE needed its pins and a fallback for the same.
  • A saved program with a status check would have recovered. An assert r['status'] < 300 would have exited nonzero, and the model would have written a new one. These programs had none, and no person added one.
  • Its sandbox held: no network but the service, read-only, 1 CPU, 256 MB, 64 processes, 120 s.
  • It can carry ARTIE. Code mode could run ARTIE in a container beside its sandbox: find the way through hypermedia on the first pass, keep it as a .heart.yaml, run that each later time, and write again only when ARTIE's exit says a form changed (spec/ideas/code-mode-runs-artie.md).

How it was run service, sandbox, bench
  • Service: heart-sims' employees service (employees.test), reset before every run. ARTIE uses its HEART side; code mode uses its OpenAPI twin, the same operations.
  • The twin, made fair first: plain JSON reads carry an ETag and answer 304 to If-None-Match; plain acts take an optional If-Match and refuse a stale one with 412; the description says so (spec/SPEC.md, decided 2026-11-02). Before that, code mode couldn't make a conditional write.
  • Code mode's library: generated from the twin's description on each run: one function per operation, each answering status, ETag and body, with if_match where a write takes it, documented "refused 412 if the state moved since".
  • Sandbox: python:3.12-slim in Docker on an internal network with only the service, read-only, 1 CPU, 256 MB, 64 processes, 120 s.
  • Teammate: PUT /_sim/employees/meddle: right after Frodo is next read, his role becomes "keeper of the Red Book". Rename: PUT /_sim/employees/changes, renamed: hire and update take position for role.
  • ARTIE: artie generate --format yaml from one goal run per task with the model (t1 25,390 input tokens, 10 calls; t3 17,093, 7 calls), then artie run on the .heart.yaml, with the reasoner given only for the fallback.
  • Bench: exhibits/mcp-over-openapi/bench.py --arms code-fresh,code-saved,artie-data --tasks t1,t3 --reps 10 --sequence, Sonnet 5.5. Lines in runs/code-vs-data-fresh.jsonl; saved programs in runs/codemode/; ARTIE's traces in runs/artie/.
Limits said plainly
  • One model, one service, two tasks, ten runs each.
  • t3's kept script had one review by hand; the saved programs had none. A reviewer would likely have caught the fixed IDs and ETag, and might have added a status check.
  • Code mode's 412 path was never tested: its programs read Frodo again after the teammate, so no write of theirs was stale.
  • The rename is one kind of change. A change the pins don't see (the same form, a new meaning) would pass ARTIE's guard too.
  • ARTIE's tokens here are the fallback's only. Its goal runs came from earlier benches, counted above, not in the 20 runs.
  • An earlier run of this comparison, with harness bugs since fixed, is set aside; this run alone counts.
  • Built for this: the twin's validators (heart-core, both servers, the TCK); artie generate --format yaml; artie run NAME.heart.yaml, with decide held as data.
