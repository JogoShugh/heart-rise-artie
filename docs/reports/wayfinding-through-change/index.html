Wayfinding Through Change

One business process, run again and again while the service changes under it. Two architectures: a bag of endpoints, where a model writes code against operations, and hypermedia, where a client follows the controls the server offers. Two places for the model: in the middle of every run, or at the edges, to find the way once and to repair after a change.

The work this is about

  • Work done in bulk, again and again: the same business process over many records, every day, for months.
  • Its shape can be found up front. One exploratory run with the model finds the way: which links, which forms, which values. Records in different states take different paths, but a few known ones, not a new one each time.
  • Inference spent once, to make the work deterministic. The way is kept and run with no model, held to the server's controls. The model comes back only at the edges: where the service changed, or a record is in a state not met before.
  • Not infinite novelty. Tasks that are new in every run are another matter; there, a model in the middle of every run earns its keep.

In short

  • The question: as a service evolves, which architecture keeps a repeated process right, safe and auditable, and where must the model sit for that?
  • Nine clients, two choices. The architecture: a bag of endpoints, or hypermedia. Where the model sits: in every run, or at the edges. Code mode ran on both architectures, writing programs, keeping them as skills, or handing the work to ARTIE; ARTIE on hypermedia, with the model at the edges.
  • Code mode and ARTIE together. Told to give ARTIE a goal once and run what ARTIE keeps, code mode wrote no program and needed no sandbox: right 20 of 20 on 107,607 tokens, about 3.1k a run choosing which kept script fits. With a harness running the kept scripts and calling code mode only when ARTIE fails: 56,366, the model in the first run of each task and ARTIE's own reasoner at the release, about ARTIE alone.
  • Code kept well. Kept as skills that take arguments and raise on a status they didn't expect, code mode's programs were right 20 of 20: each failure showed, and the model wrote the skill again. It paid about 8.2k every run to read the task and fill the skill's arguments, and ran 59 programs in a sandbox.
  • Wayfinding. From endpoints, the client builds every address itself. Code mode worked the way out again each run (27 programs for two tasks), or froze it (saved programs with employee IDs and an ETag written in). From hypermedia, told nothing but the address, code mode found its way every run, about 100 different programs per variant: through the links and forms, and, as the service answers by itself, also through the OpenAPI description its index links to (19 of 20 runs). With that withheld, HAL-FORMS alone was enough: 20 of 20. ARTIE's kept script follows what the server hands it: the search's item link titled "Bilbo Baggins", the new employee's Location.
  • Evolution. A release renamed a field. The frozen code broke silently, 8 runs of 8, each exit 0. Fresh code adapted on either architecture, by reading the service again every run. ARTIE's pins noticed the changed form before any write; the model repaired that one step, once, and the repair was kept.
  • Controls. The endpoint side had no conditional writes until we added them to its OpenAPI twin, and using them stays the client's choice. The HEART side refuses a write without If-Match (428): code mode on it met 57 of those refusals, then sent the ETag. A control guards only what the client pairs with it: one program sent a fresh ETag with a role computed before the teammate's change, and wrote over it. ARTIE takes both from the representation it acts on, and kept the teammate's change every time.
  • Security. Code mode ran model-written code every run, so it needed a sandbox every run. ARTIE ran none: its script is data in a closed vocabulary.
  • Compliance. ARTIE's process is one kept script a person can review, pinned to the server's forms, with a trace of every refusal and its reason; a release changed it by a few lines of diff. Code mode's was a different program almost every run.
  • The model at the edges. ARTIE called it once per task to find the way, and once after the release to repair: 2 runs of 20, 4,381 tokens, plus 42,483 once for its wayfinding. Code mode called it in every run: 158,995 tokens with a library made for it, 456,893 to 551,629 finding its way through the hypermedia. Priced with the prompt cache, as the API bills it: ARTIE 2,958; code mode 35,117 with a library, 123,786 to 178,872 on HEART.

Fielding, in brief

  • The complaint (2008): most "REST APIs" are a list of operations a client must know in advance. "That is RPC. It screams RPC."
  • Enter knowing almost nothing: "A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types…"
  • Information and controls together: "When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions."
  • For change over time: "REST is software design on the scale of decades: every detail is intended to promote software longevity and independent evolution."
  • More, with his six rules verbatim: Information and Controls.

HEART, ARTIE and the formats, in brief

  • HEART (Hypermedia Enforced Agentic Reliable Transactions): a protocol profile for APIs. Each answer carries, or links to, the actions its resource allows in its state now; an action not offered is not allowed, and the answer can say why. Every write sends the ETag it read (If-Match): a stale one is refused 412, a missing one 428.
  • ARTIE (Autonomous Restful Traversal and Interactive Engine): HEART's reference client. Generic, like a browser: coupled to the formats below, not to any API. It follows links and forms, sends the ETag, and caches what it may. It runs a goal written in plain words with a model, and a kept script (.heart.yaml) with none.
FormatWhat an answer holdsHere
HALThe resource's state, and _links: related resources by relationThe base of the two below
HAL-FORMSHAL, and _templates: each action's method, target and fieldsSpring HATEOAS's format, widely used; what this service answers when a client asks for nothing in particular
HAL Schema FormsHAL, and _forms: each action's method, a link to its target, and a JSON Schema for what it takesHEART's reference format, with its profile: forms named as link relations, and integrity hashes a client can check
OpenAPINot an answer: a separate description of every endpoint, its path, method and bodyThe same service's endpoints, as code mode uses them
  • Rungs: at L0 the forms and their schemas are inside each answer. At L2 they are linked: the forms for one state published once at their own address, shared by every resource in that state, and cached for a year. A client asks with Prefer: forms=link, schema=link.
  • Kept script and pins: a run's way written as data, run again with no model; its pins record the forms the run was offered, so a changed form is caught before any request.
  • A pin holds what a form does, not where it is: each form's act (method, content type, template pointers and schema), its target set aside. ARTIE never builds an address, so a form the server moves goes on with no model; a new method or a renamed field is a new act, and stops the step. Strict stops at any change.
  • Code mode: a model writing programs against an API, run in a sandbox (Anthropic's "code execution with MCP", Cloudflare's Code Mode).

Two architectures

A bag of endpoints

flowchart TD
  D["1 Description: every operation"] --> M{{"2 Model writes code"}}
  M --> P["3 Program builds URLs"]
  P --> S[("Service")]
  S -- "4 status, body" --> P
  1. The client is told every operation up front: paths, methods, bodies.
  2. The model works out the way and writes the code: every run (fresh), or once (saved).
  3. The program builds each address itself, from path templates and IDs.
  4. The server's rules show only after the call: a changed operation is an error, if the program reads it.

Hypermedia

flowchart TD
  B(["1 Bookmark"]) --> R["2 State + controls now"]
  R --> C{{"3 Client picks a control"}}
  C -- "act + If-Match" --> S[("Service")]
  S -- "4 next state or refusal" --> R
  1. The client enters at a bookmark, knowing only media types.
  2. Each answer carries what is true now and what can be done now: the links, the forms this state allows, an ETag.
  3. The client selects a link or a form; an act carries the ETag it read.
  4. The server answers with the next state, or refuses with a reason: 409 not offered, 412 stale, 428 no validator, 422 doesn't fit.

How ARTIE uses the model

Wayfinding: sync, reason, act

flowchart TD
  W(["Goal words"]) --> Y["1 Sync"]
  Y --> Q{{"2 Reason: model"}}
  Q --> A["3 Act"]
  A --> Y
  A -. "4 trace" .-> G["artie generate"]
  G --> K[".heart.yaml + pins"]
  1. Sync, no model: read the representation; fetch its forms and schemas by link; revalidate them with their ETags.
  2. Reason, the model: it sees only the state, the forms offered now and the step's words, and picks one form and its values. ARTIE checks the values against the form's schema.
  3. Act, no model: send it with If-Match. A 412 reads again and decides again.
  4. Every exchange is traced. artie generate turns the trace into a kept script and its pins.

A kept run: the model only where something changed

flowchart TD
  T(["Next step"]) --> Y["1 Sync"]
  Y --> P{"2 Pin holds?"}
  P -- "yes" --> A["3 Act, no model"]
  P -- "changed" --> F{{"4 Words: model"}}
  F --> A
  A --> T
  A -. "5 after the run" .-> K["Keep the repair"]
  1. Sync: the same deterministic read as above.
  2. Guard: the form the step uses is held to its pin before any request.
  3. Act: the script's own values, with If-Match; no model.
  4. A changed form: the step falls back to its words, and the model chooses from what is offered now.
  5. Keep: a repair that worked, every value the script's own, is written into the script and its pins, so the next run needs no model.

Layers and boundaries

A program written against endpoints ties the task to them, and leaves no layer between: a policy can only sit at the endpoint. A client that follows what the server offers leaves room for one in front of it, in it, and before it runs.

  • On HEART, with no library made for it, code mode took about three times the tokens: it found its way again in every run. The hypermedia let it find the way; only a client that keeps the way spends the model once.
  • Every request counted reached the server. Code mode on HEART's reads of /openapi.json are not counted.
  • ARTIE's 56 304s are its state read again before each use (Layer 1 is no-cache): a conditional GET, answered with no body. Its 70 form-set and schema fetches are immutable for a year and served from its cache within a run; each run here started a new process with an empty cache, so each fetched them once. A cache kept between runs would take them to zero.

Many records, a few states

The same service, one goal run over many employees, each in one of three states: a kept script that branches on what the server offers used no model at any size, and fetched one form set per state. Its own page: Many Records, a Few States.

Self-repair

  • At the release: in run 7, ARTIE's pins refused the changed forms, each step fell back to its words, the model chose position, and the acts were done. After the run, the repairs were written into the kept scripts and their pins (keep: auto), so runs 8 to 10 ran with no model.
  • Kept without a person only where it is safe: the run finished; the repair made the act the script was making; and every value it sent is one the script sent. Each is copied as the script wrote it, so an input stays an input and ${state.role}, retired stays a reference, never the literal "ring bearer, retired".
  • Not kept automatically: a value the script never sent, such as a new required reason; a repair that made another act; a run that didn't finish. keep: propose says what it would keep and writes nothing, where compliance asks for a person.
  • Moved, not changed: a release that served the acts at new addresses, run on t1's kept script: each form's integrity changed and its act didn't, so hire, update and dismiss went on, held by their acts: 0 tokens, 2 runs of 2 right. A release that made update a PATCH changed its act: one model call, 1,265 tokens, and the repair was kept.
  • What a run can't tell by its pins: that the meaning stayed when the name changed. artie generate writes a check after each act that changes the resource it holds, from what the first run saw it change (status becomes "on notice"): a release that changed what an act does stops the run there, as the scripts code mode had ARTIE keep do.
  • What a reviewer sees: one line per field and one per pin. The hand-review comment in t3's script stays as it was.

Where code mode did well

  • Fresh code mode was right every time. Every write to an existing record carried If-Match, 30 of 30, once the description offered it.
  • It adapts with no machinery of its own. It reads the current description every run, so a rename costs it nothing extra. ARTIE needed its pins and a fallback for the same.
  • It found its way from a bookmark, told nothing. Given only the address, it read / and used everything it found there: the links, the forms, and the OpenAPI description / links to. Right 20 of 20 as the service answers by itself, and 20 of 20 with the description withheld.
  • Kept as skills, its code recovered. Saved with arguments in place of IDs and an exception on any status it didn't expect, a skill failed loudly where the frozen programs failed silently: at the teammate's change (a 412) and at the rename (a 422). The model wrote it again each time, and it was right 20 of 20.
  • Its sandbox held: no network but the service, read-only, 1 CPU, 256 MB, 64 processes, 120 s.
  • It carries ARTIE. Given ARTIE in a container as its one tool, code mode wrote no program: it gave ARTIE each task as a goal once, then ran what ARTIE kept, right 20 of 20. Its strength, reading a task in plain words, stays; the acts are ARTIE's, held to the server's controls.

How it was run service, sandbox, bench
  • Service: heart-sims' employees service (employees.test), reset before every run. ARTIE uses its HEART side; code mode uses its OpenAPI twin, the same operations.
  • The twin, made fair first: plain JSON reads carry an ETag and answer 304 to If-None-Match; plain acts take an optional If-Match and refuse a stale one with 412; the description says so (spec/SPEC.md, decided 2026-11-02). Before that, code mode couldn't make a conditional write.
  • Code mode's library: generated from the twin's description on each run: one function per operation, each answering status, ETag and body, with if_match where a write takes it, documented "refused 412 if the state moved since".
  • Sandbox: python:3.12-slim in Docker on an internal network with only the service, read-only, 1 CPU, 256 MB, 64 processes, 120 s.
  • Teammate: PUT /_sim/employees/meddle: right after Frodo is next read, his role becomes "keeper of the Red Book". Rename: PUT /_sim/employees/changes, renamed: hire and update take position for role.
  • ARTIE: artie generate --format yaml from one goal run per task with the model (t1 25,390 input tokens, 10 calls; t3 17,093, 7 calls), then artie run on the .heart.yaml, its config on-change: intent and keep: auto, with the reasoner given only for the fallback.
  • Bench: exhibits/mcp-over-openapi/bench.py --tasks t1,t3 --reps 10 --sequence, Sonnet 5.5, the same service, sequence and harness for every arm. Code mode on endpoints in runs/code-vs-data-fresh.jsonl; on HEART in runs/code-heart.jsonl, runs/code-heart-hsf.jsonl and runs/code-heart-l2.jsonl, with every program it ran; ARTIE's in runs/artie-keep.jsonl; saved programs in runs/codemode/; ARTIE's traces in runs/artie/.
  • Code mode on HEART, four more variants (runs/code-heart-more.jsonl), each changing one thing: the OpenAPI description withheld by a proxy that answers /openapi.json 404 (sandbox/no-openapi.conf); the format's document, spec/HAL-SCHEMA-FORMS-HR.md, beside the program, with the prompt saying so (the sandbox reaches no other network); L2 with 16 turns. Two more (runs/code-heart-docprompt.jsonl): the same document in the system prompt, marked for the prompt cache.
  • Code mode on HEART, told: "The service is at the address in the environment variable API_BASE; every request needs the header Authorization: Bearer followed by the environment variable API_TOKEN." HSF, also: "Accept: application/hal+json; Accept-Profile: <https://w3id.org/heart-rise/hal-schema-forms>". L2, also: "Prefer: forms=link, schema=link".
  • Code mode, keeping skills (runs/skill-artie-sequence.jsonl): the endpoint library and sandbox above, and two more tools, save_skill (a SKILL.md and a module defining run(**arguments)) and run_skill; told to save its work as a skill taking the values a person would change, looking up IDs and ETags each time and raising on a status it didn't expect, and to run a saved skill when one fits.
  • Code mode with ARTIE as its tool (runs/code-artie-sequence-final.jsonl): three tools and no sandbox. artie_find: ARTIE runs a goal in plain words with its own reasoner, then artie generate --format yaml keeps it, with on-change: intent and keep: auto. artie_run: a kept script. artie_look: one address the service handed ARTIE, read with no model. ARTIE runs in its own container (Java 25), sharing the service container's network, so the service is at localhost; it holds the model key. Told how a goal is written: a sentence, then its steps, a step done for each of many saying so in its own words.
  • A harness running ARTIE (runs/escalate-sequence.jsonl): the same tools for the first run; it records the kept scripts that did the task, runs them after with no model, and calls code mode with ARTIE's exit and reason only when one fails.
Limits said plainly
  • One model, one service, two tasks, ten runs each.
  • Every code-mode client had 8 turns, but one variant with 16. On HEART at L2, fetching each form set and schema by link used them up in 5 t3 runs before a write landed.
  • A program's output reaches the model 4,000 characters at a time, so a document read in the sandbox takes several turns.
  • t3's kept script had one review by hand; the saved programs had none. A reviewer would likely have caught the fixed IDs and ETag, and might have added a status check.
  • Fresh and saved code mode's 412 path was never tested: their programs read Frodo again after the teammate, so no write of theirs was stale. A skill met one 412, raised, and was written again to read and retry.
  • The rename is one kind of change. A change the pins don't see (the same form, a new meaning) would pass ARTIE's guard too, unless a check after the act sees what it changed. ARTIE alone ran scripts with no such checks; the scripts code mode had ARTIE keep had them.
