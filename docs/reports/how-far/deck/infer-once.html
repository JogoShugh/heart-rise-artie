Infer once. Then what?

When to think, and how “once” stays true

Hightower: when to think

Once. Infer the task, then run it as plain, deterministic code. Zero tokens per run. ZTA

The gap

“Everywhere” includes tomorrow. A script frozen against out-of-band URLs breaks, or pays tokens to re-learn.

Fielding: why it stays true

Every answer carries its controls. The replay checks its act is still offered. That check is free.

The goal, in words (release.goal.md)
Release a pull request to Dev once it can be merged and its build passes its smoke test.

- Open pull request {pull} of {owner}/{repo} `as pr`
- At {watcher}, ask to be told when {pr} offers scm:merge `as watch`
- Once {watch} is answered, at {pr}, merge it by squashing `as merged`
- At {jenkins}, build commit {merged.merge_commit_sha}, asking to be told how it goes `as build`
- Once {build} is answered, follow its in-reply-to link to the build `as built`
  - Run the smoke script it links as ci:smoke-test, on the deployment it links as ci:deployment, with book = {book}, author = {author}, renewable = {renewable}, problem = {problem}, comment = {comment} `as smoke`
- If {smoke.passed}, at {dev}, open environment {environment} and promote commit {merged.merge_commit_sha}, citing {smoke.passing} of {smoke.of} scenarios passed `as promotion`
  Otherwise, at {pr}, act scm:comment with body = "Not promoted to Dev: smoke scenarios {smoke.failed} failed."
The kept script, from one model run (release.heart.yaml)
steps:
  - act: scm:pulls-get
    fields:
      owner: ${owner}
      repo: ${repo}
      pull_number: ${pull}
    intent: Open pull request ${pull} of ${owner}/${repo}
    then:
      - keep-as: pr
  - enter: ${watcher}
    steps:
      - ask: watcher:watch
        fields:
          resource: ${pr.@self}
          offers: scm:merge
        reply: watch
  - once-answered:
      reply: watch
      steps:
        - enter: ${pr.@self}
          steps:
            - act: scm:merge
              fields:
                method: squash
              intent: merge it by squashing
              then:
                - check:
                    - field: state
                      is: closed
                    - field: merged
                      is: true
                    - field: mergeable_state
                      is: unknown
                - keep-as: merged
  - enter: ${jenkins}
    steps:
      - ask: ci:build
        fields:
          commit: ${merged.merge_commit_sha}
        reply: build
  - once-answered:
      reply: build
      steps:
        - follow: hr:in-reply-to
          intent: follow its in-reply-to link to the build
          then:
            - run-script: ci:smoke-test
              on-link: ci:deployment
              inputs:
                book: ${book}
                author: ${author}
                renewable: ${renewable}
                problem: ${problem}
                comment: ${comment}
              as: smoke
  - given:
      - at: smoke
        field: passed
        is: true
    then:
      - enter: ${dev}
        steps:
          - act: env:get-environment
            fields:
              id: ${environment}
            inferred: get environment ${environment}
            from-intent: open environment ${environment} and promote commit {merged.merge_commit_sha}, citing {smoke.passing} of {smoke.of} scenarios passed
            then:
              - act: env:promote
                fields:
                  commit: ${merged.merge_commit_sha}
                  smoke: # review: the reasoner chose it, asked "promote commit 30a0fa96e3eed2ae20b2b5fa7613a115d56312a3, citing 5 of 5 scenarios passed"
                    passed: ${smoke.passing}
                    of: ${smoke.of}
                intent: open environment ${environment} and promote commit {merged.merge_commit_sha}, citing {smoke.passing} of {smoke.of} scenarios passed
                then:
                  - check:
                      - field: commit
                        is: ${merged.merge_commit_sha}
    otherwise:
      - at: ${pr.@self}
        steps:
          - act: scm:comment
            fields:
              body: "Not promoted to Dev: smoke scenarios ${smoke.failed} failed."

“A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types that are appropriate for the intended audience (i.e., expected to be understood by any client that might use the API). From that point on, all application state transitions must be driven by client selection of server-provided choices that are present in the received representations or implied by the user’s manipulation of those representations. The transitions may be determined (or limited by) the client’s knowledge of media types and resource communication mechanisms, both of which may be improved on-the-fly (e.g., code-on-demand). [Failure here implies that out-of-band information is driving interaction instead of hypertext.]”

Roy T. Fielding, “REST APIs must be hypertext-driven”, 20 Oct 2008
