HEART and ARTIE · a run report

One Goal, Decided Once

A merge watch written in fifteen lines of plain words: the model decides each step once, the steps run on as a script, and the model comes back only where the words say so.

Each section is short. The technical detail sits under Technical detail at its end; Show all detail above opens every one.

1The job

Dependency bumps pile up in a repository. A person wants them merged as soon as they can be, left alone when someone objects, and the author told plainly when a bump can’t go in.

  • Three outcomes for every bump: merged, left (labelled hold, said once), or told why (the wait gave up).
  • The work never ends by itself. It runs until a person closes the watch’s issue.
  • Only one part needs judgment: putting the server’s reason into a friendly sentence. The rest is rules.
  • The aim: decide the rules once with a model, run them many times without one.
Technical detail: the stand-ins that made the bumps

A Dependabot stand-in, exhibits/dependabot-sim/bump.kts, opens real pull requests on a scratch repository (JogoShugh/heart-github-test): a branch, a one-line version file, a pull request into deps-main, and its labels.

artie run bump.kts owner=JogoShugh to=5.0.1 file=deps-501.txt label=dependencies,hold
artie run bump.kts owner=JogoShugh to=5.0.2 file=deps-502.txt label=dependencies draft=true
artie run bump.kts owner=JogoShugh to=5.0.3 file=deps-503.txt label=dependencies
  • Two bumps that write the same file conflict once one of them merges; that is how the conflicts in the hour run were made.
  • A draft can’t be merged until someone marks it ready, so its wait gives up.
  • person.kts close=yes closes the watch’s issue at the end, as a person would.

2A short history of hypertext

Information that carries its own way forward is an old idea. For forty years each system came with its own reader; then the Web split the client from the content.

  • 1945 Vannevar Bush’s memex, in “As We May Think”: a desk of documents and the trails a reader makes between them. Never built.
  • 1965 Ted Nelson coins “hypertext”. 1968 Douglas Engelbart demonstrates NLS: live, linked, editable, on NLS terminals only.
  • 1987 HyperCard: millions of linked stacks, readable only in HyperCard. Content and reader came as a pair.
  • 1989–1991 Tim Berners-Lee’s proposal at CERN, then the public Web: URIs name things, HTTP moves them, HTML describes them. Any browser, any site.
  • 1993 Mosaic, and forms: pages that say not only where to go but what can be done, with which fields.
  • 2000 Roy Fielding names the architecture REST. 2008 he complains that APIs have dropped its central constraint.
  • 2012–2023 HAL puts links into JSON; OpenAPI moves the rules into a description; agents carry them in training.
  • 2026 HEART puts the controls back in the answer, and ARTIE reads them, as a browser reads a page.

3Fielding’s complaint

Fielding’s dissertation defined REST by four interface constraints. Eight years later he wrote, in so many words, that the APIs calling themselves REST had dropped the one that matters most.

REST is defined by four interface constraints: identification of resources; manipulation of resources through representations; self-descriptive messages; and, hypermedia as the engine of application state.Roy T. Fielding, dissertation, 2000, §5.1.5
I am getting frustrated by the number of people calling any HTTP-based interface a REST API. Today’s example is the SocialSite REST API. That is RPC. It screams RPC. There is so much coupling on display that it should be given an X rating.Roy T. Fielding, “REST APIs must be hypertext-driven”, 20 October 2008
What needs to be done to make the REST architectural style clear on the notion that hypertext is a constraint? In other words, if the engine of application state (and hence the API) is not being driven by hypertext, then it cannot be RESTful and cannot be a REST API. Period. Is there some broken manual somewhere that needs to be fixed?Roy T. Fielding, 2008
  • His rules for a REST API, verbatim: “A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types that are appropriate for the intended audience (i.e., expected to be understood by any client that might use the API).”
  • “A REST API should spend almost all of its descriptive effort in defining the media type(s) used for representing resources and driving application state, or in defining extended relation names and/or hypertext-enabled mark-up for existing standard media types.”
  • “A REST API must not define fixed resource names or hierarchies (an obvious coupling of client and server). Servers must have the freedom to control their own namespace.”
  • What he meant by hypertext, in his comments on that post: “When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions.”
  • And machines: “Machines can follow links when they understand the data format and relationship types.”
  • The diagram shows where the rules went instead: an interface file, the docs, a generated client, the model’s training. Each copy is frozen earlier and drifts from the server.
Technical detail: the trade Fielding named, and HEART’s answer to each constraint
The trade-off, though, is that a uniform interface degrades efficiency, since information is transferred in a standardized form rather than one which is specific to an application’s needs.Fielding, dissertation, §5.1.5
REST is software design on the scale of decades: every detail is intended to promote software longevity and independent evolution. Many of the constraints are directly opposed to short-term efficiency.Fielding, comment on “REST APIs must be hypertext-driven”, 2008
ConstraintIn this run
Identification of resourcesEach pull request, issue and list has a URL the gateway handed over; the script never builds one.
Manipulation through representationsMerge is a PUT to the merge form’s target with {"merge_method": "squash"}, as the form’s JSON Schema says.

4The goal in words

The whole job, as the person wrote it. No code, no API names: inputs, one sentence of context, and a list of steps in the words a person would use.

Merge dependency bumps once they can be merged. Keep watching until the watch's issue is closed.

- In {owner}/{repo}
  - Open an issue titled "Merge watch", saying "Close this issue to stop the watch." `as watch`
  - Whenever a pull request labelled {label} changes `as pr`
    - If it's labelled {hold}, leave it, and say so once.
    - Once it can be merged, merge it by squashing.
      Or give up after 3 minutes.
      Otherwise, tell its author in one friendly sentence why it wasn't merged and what to do next. `reasoned`
- Until someone closes {watch}
  • Six constructs: Whenever, If, Once, Or give up, Otherwise, Until. Each is a plain English word with one meaning.
  • as watch names the issue so the Until can read it again later, by the address the server gave.
  • reasoned is the only mark that keeps the model in the loop. Everything else is decided once.
  • Nothing in it says GitHub, PUT, or mergeable_state. Those come from the server’s answers at run time.
Technical detail: the front matter 
---
start: https://localhost:8392/
inputs:
  owner: { question: "Whose repository?" }
  repo:  { default: heart-github-test, question: "Which repository?" }
  label: { default: dependencies, question: "Which label marks a dependency bump?" }
  hold:  { default: hold, question: "Which label means a person objects?" }
---
  • start is the bookmark: the gateway’s service index. Fielding’s “initial URI”.
  • Inputs are asked for when not given, and become the script’s inputs later.
  • The run: artie run merge.goal.md owner=JogoShugh --reasoner claude --rung L2.

5Decide once, replay forever

The first time a step is needed, the model reads the goal’s words against what the server offers right there, and decides. The decision is kept. Every later time, for every pull request, it is replayed with no model.

  • A decision is small: a relation (github:merge), a check as facts ({"github:labels": ["hold"]}), or fields (squash).
  • It is made on a real resource, live, not from documentation.
  • The replay is safe because the server checks it: a kept decision to merge acts only where the merge form is offered now.
  • So the model is needed once per kind of step, not once per pull request or per look.

6The server says what is possible

“Once it can be merged” needs no rule about drafts, conflicts or checks. The gateway offers the merge form only when GitHub would accept it, and says why when it won’t.

  • The wait is just this: look again until github:merge appears among the forms.
  • When it never does, the reason is already there, in the server’s words, in hr:unavailable.
  • This is Fielding’s “information becomes the affordance”: the client acts on what the representation offers, not on what it knows about GitHub.
  • The client knows no rule for mergeability. If GitHub adds one tomorrow, the gateway’s answer changes and the script doesn’t.

7Where the model stays

One step changes every time: why this bump couldn’t merge, said kindly to this author. The goal marks it reasoned, so it is never replayed.

  • The model gets the goal’s words and the server’s reason, and picks a form the pull request offers.
  • Nothing of it is kept: the next give-up asks again, with its own reason.
  • The model writes words; it decides no rule. Whether to give up, and why, came from the server.
  • One mark, one place. Everything else in the watch runs without inference.
Technical detail: what the model is sent 
tell its author in one friendly sentence why it wasn't merged and what to do next.
The wait gave up, and the server says why: A draft can't be merged; mark it ready for review first.
  • The goal’s words, then the server’s reason from hr:unavailable, verbatim.
  • With it, as with every reasoner call: the pull request’s state, its offered forms with their JSON Schemas, and its links by relation and title, never an address.
  • The reasoner is told to write words a field takes exactly as the intent describes them: “one sentence” is one sentence.

10The script it became

From the run’s capture, artie generate writes the same watch as a Kotlin script: every decision named, nothing to ask a model except the one reasoned line.

  • Each goal line becomes one script construct. The mapping is kept, line and column, in merge.derivation.yaml.
  • Relations are named (github:merge), checks are facts ("github:labels" has hold), the give-up is a duration.
  • What the run was offered is pinned in merge.pins.yaml: if the gateway changes a form, the script refuses to act rather than guess.
Technical detail: merge.kts 
heart("https://localhost:8392/") {
    act("github:repos-get", "owner" to owner, "repo" to repo, intent = "get repository $owner/$repo") {
        act("github:open-issue", intent = """Open an issue titled "Merge watch" …""", fields = {
            "title" to "Merge watch"
            "body" to "Close this issue to stop the watch."
        }) {
            keepAs("watch")
        }
    }
    watch(until = { at("watch") { "state" eq "closed" } }) {
        act("github:pulls-list", "owner" to owner, "repo" to repo, "labels" to label) {
            whenever {
                has { "github:labels" has label }
                leaveWhere("leave it, and say so once.") { "github:labels" has hold }
                once("github:merge", giveUp = 3.minutes, otherwise = { why ->
                    act(intent = "tell its author in one friendly sentence why it wasn't merged and what to do next. The wait gave up, and the server says why: ${why ?: "no reason given"}")
                }) {
                    act("github:merge", "merge_method" to "squash") {}
                }
            }
        }
    }
}

12Observations

  • The controls carried the rules. The goal never said what makes a pull request mergeable. The server said it, by offering merge or not, which is what Fielding meant by information that “becomes the affordance”.
  • The reason came with the refusal. “A draft can't be merged; mark it ready for review first” is the server’s sentence. The model turned it into a kind one; it didn’t have to work it out.
  • Decide once is safe because the server re-checks. A kept decision acts only where its form is offered now, under If-Match. Replay can’t act on a state the server no longer offers.
  • A representation should change only when its resource does. Each pull request used to embed its whole repository, including counts like open_issues that change whenever anything happens in the repository. Every pull request then looked changed every few minutes. The gateway now embeds a repository by what names it, with its counts one link away, and a held pull request is seen to change only when it does.
  • The model stayed where judgment lives. One marked line, one kind of question. Everything a rule can do, a rule did.
  • Fielding’s bookmark rule held. The run began at one URI and reached every resource by links and forms the server gave. Not one address was built by the client.
