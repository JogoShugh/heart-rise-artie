Form Lineage

How a script's act always traces back to the resource's current state, at each rung, and how the lenient and strict guards decide.

The one rule. Every form a run uses comes from the resource it just read. That read is never cached: the resource answers no-cache. Everything below the resource is content-addressed and cached for a year, and it is only reached through the link the fresh resource gives right now.

Key

Green: read fresh every time. Blue: immutable, cached, its address is its hash. Red: the run stops.

Why a cached form can't go stale

  1. The run reads the resource fresh.
  2. The resource names the set it offers right now, by hash.
  3. If the cache holds that hash, those bytes are exactly that set. The address is the content.
  4. If the cache doesn't hold it, the client fetches it and checks the bytes against the hash.
  5. The guard looks for the target form in that set, the current one.

An old set in the cache is never used unless the fresh resource names it again. The server owes nothing at an old address: the client always reaches a set or schema through the fresh resource, which names only what it serves now.

  • Both modes always check the target form's own integrity.
  • Lenient stops only when the target form changed or is gone.
  • Strict also stops when the set changed for any reason: a form added, dropped, or changed.
  • At L0 there is no set, so strict skips the set check there.
  • Pins are per form. Each form keeps its own list of sets it was seen in.
  • Re-pinning happens once, after the run, and only for acts that were done.

The same form, used twice, renamed in between

On two fresh issues, the script comments twice. The first comment goes through with the comment form as recorded.

The gateway then renames the comment's field from body to content, as an API's next version might. It does this with a new connector setting: rename: { content: body }.

The second comment: both modes stop. The guard reports that github:comment changed, with the pinned hash and the offered one. Nothing is sent, and only the first comment exists.

Found on the way: the client used to check the fields against the new schema before asking the guard. It now asks the guard first, so the refusal names the real cause.

What counts as a change

Any change to what the form does changes its hash: a field added, even an optional one; a field dropped or renamed; a new method or target. Both modes stop.

A new title or description does not count. Wording is left out of the hash on purpose, so a reworded form is the same form.

Accepting an added optional field as compatible would need a schema comparison. That is not built.

Nothing changes

Strict: finishes, issue closed.

Re-pin after the unrelated change

Lenient run with repin: auto: finishes, adds the new set for comment and close. A strict run afterwards: finishes.

With propose, never, or --no-repin: nothing written. A strict run afterwards: stops.
