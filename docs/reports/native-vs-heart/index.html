Native or HEART-Shaped

Give Claude a goal and some tools, and it works the task out from what it already knows. Give the same goal to ARTIE in front of a HEART service, and Claude only chooses among what the service offers. A run can then become a script that needs no model, or keep the model for just the steps that need judgement.

At run time, three ways to mix

The second diagram shows a first run turning into a script with no model. That is one option, not the only one. A step can stay an intent inside a script, and the model is then called for that step on every run. Below, the seven steps of the GitHub task, coloured by who decides each one.

the model decides, every run the script decides

In all three, the service still bounds every request: the model, where it is called, only chooses among what is offered.

What Claude does alone

  1. Plans from what it already knows. It recalls the API from training or reads its docs, and picks endpoints such as POST /repos/{o}/{r}/issues.
  2. Acts, then fixes and retries. It reads the errors and adjusts. What it may do is whatever its tools allow, plus its own judgement.
  3. May write a script. The URLs, parameters and order are fixed in it, from Claude's understanding of the API.

What ARTIE does

  1. The service says what's possible, one step at a time. Claude chooses only among the forms and links in hand. If a merge isn't offered, Claude can't send a merge.
  2. The model's role is narrowed twice. The planner picks the next move, and the reasoner fills an offered form. The runner refuses moves the step doesn't allow, and the server refuses stale or unoffered acts.
  3. The run can become a script. Each value records where it came from. The script follows relations, not URLs, and a lock file pins what was offered. Steps that need judgement can stay intents.

Why it's better against a HEART service

  • Nothing has to be known in advance. It works on a service the model has never seen, such as an internal API with no public docs.
  • The service enforces its own rules. "Can it be merged?" is answered by whether merge is offered, not by Claude remembering to check.
  • No made-up endpoints. Requests only go to addresses the server handed over.
  • A change shows up as a refusal, not a wrong action. When a form changes, the pinned script stops before it acts.
  • Waiting is part of the protocol. until offers("merge") reads the state machine the server shows, with no polling loop over fields that are guessed at.

Where it isn't better

  • It needs a HEART service, or a gateway in front of one. The GitHub connector was real work. Against a plain REST API, Claude alone is the only option.
  • A reasoned run isn't cheaper. The live goal run took 22 reason steps; Claude alone would likely use fewer calls. The saving comes from the steps that stop needing the model.
  • It's less flexible. Claude alone can mix in other tools: reading a file, running tests, posting a message. A goal run only does what the service offers.

The trade: some flexibility goes. In return, the model's role shrinks to choosing among options the service vouches for, at the steps where you still want it, and to nothing where you don't.
