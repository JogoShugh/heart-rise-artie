What changed to get here

Changes in this pass: SPEC 0.4 conformance, one step at a time

Each step started with a Gherkin feature in server-spring/src/test/resources/features/. The bdd-gates log (.claude/tdd-events.log) shows each one failing before the fix and passing after; the git pre-commit check refuses a commit that skips that order.

  • Gates installed. Claude Code hooks block production edits without a feature change, log every test run, run Detekt after each edit, and keep the build green before a turn ends. Konsist tests guard the domain boundary (server) and the Transport boundary (client).
  • Step 1 · rendering ladder. No Prefer now returns L0: everything in one response. forms=cid gives L1, forms=cid, schema=cid gives L2. L1 and L2 sets have different addresses, and Layer 2 no longer sends Vary. (§6.4, §6.5)
  • Step 2 · Layer 1 caching. Cache-Control: no-cache, ETags like "seq-1.hsf.L2" that differ per dialect and rung, and 304 on revalidation. Before, an L1 ETag revalidated an L2 request: a wrong cache hit. (§6.1, §6.2)
  • Step 3 · conditional acts. An act without If-Match gets 428; a bad body gets 422, not 400; checks run in the order 428, 412, 409, 422. (§6.2)
  • Step 4 · profiles. Link: rel="profile" on every Layer 1 response; Accept-Profile negotiation; 406 for an unsatisfiable Accept; the media-type profile parameter is gone. (§6.1)
  • Step 5 · templates. {bedId} became {id}, the Layer 1 property it resolves from. Before, a rule-following client posted to /beds/actions/water-cell and got 404. (§6.9.1)
  • L5 guard. Both dialects offer the same acts in every state, now checked over HTTP.
  • Client C1 · real wire format. ARTIE parsed a format no SPEC version defines. It now reads 0.4 _forms, checks Link: rel="profile", and holds the ETag.
  • Client C2 · conditional acts. If-Match on every act; templates expanded by the [0.5] rule only; 412, 409, 428 and 422 each handled their own way.
  • Client C3 · real HTTP. HttpTransport and live scenarios against server-spring. The second live run found a server bug: the first snapshot (event 5) answered 500 after its event was committed. Fixed, with a Postgres test.
  • Client C4 · L2 walk. Layer 1, set, schemas, through an HTTP cache that serves immutable layers without a request and revalidates Layer 1 to 304. Bytes that do not hash to their address are refused.

Example: the first failing check decides the status code

Rule
SPEC 0.5 §6.2: a server checks an act in a fixed order and returns the first failure: 428 no If-Match, 412 stale If-Match, 409 act not in the current manifest, 422 body fails the schema. The order matters because 412 tells a client to discard its act, while 422 says the act itself was malformed.
How
Bed 2 is PLANTED, at state version 1. Each row sends a request that is wrong in its own way and in every later way: the sow-seed rows are illegal for a planted bed and also carry an empty seedType. Only the evaluation order can pick the code.
Before
The first run after writing this feature failed 9 scenarios. Rows 1-3 got 400 instead of 428, 412 and 409: Spring's @Valid @RequestBody validated the body before the handler ever looked at If-Match. An act with no If-Match at all went through with 200.
After
GardenBedController.act() checks the precondition and the manifest first. The body is bound and validated afterwards, by ActBodyBinder. All rows pass.

Example: a stale act is dropped, not resent

Rule
SPEC §6.3: on 412 the client re-syncs and discards the pending act. The user's intent may mean something else now, so resending it could overwrite someone else's write.
How
The scripted server answers the act with 412, then answers the re-sync GET with a newer bed. The scenario checks the exact requests the client sent after entering: one POST, one GET, and no second POST. It also checks that the client now holds the newer ETag.
Mutation check
Treating 412 like 428 (re-sync, then resend) made this scenario fail, because the resent act was not in the new manifest. The change was reverted. The same rule passes live: live-server.feature has a second client write first, and ARTIE gets StaleAct from the real server.

Limits

What this baseline does not cover

  • The server's Cucumber suite uses @WebFluxTest, but production runs Spring MVC on Tomcat. The live journal and ARTIE's live scenarios exercise the real stack; the in-process suite does not.
  • ARTIE has no Reason step (L6) and no RISE yet. It fetches schemas one after another, not in parallel.
  • HAL-FORMS is served at L0 only. Its Layer 2/3 addressing needs a SPEC decision first; see spec/CONFORMANCE-GAPS.md.
  • The cache-demo exhibit still uses its own 0.3-era fixtures ({bedId}, no Prefer). It demonstrates the caching mechanism, not 0.4 conformance.
  • The Docker build of Dockerfile.origin was verified on 3 Oct, before the fixed random seed. The cache-demo run above used the local server.py with the regenerated fixtures.
  • server-node has no tests.
  • The bdd-gates pre-commit check runs only after git config core.hooksPath .githooks. Until then, commits in this pass ran it by hand first.
