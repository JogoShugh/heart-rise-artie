HEART and ARTIE · before the merge watch

Information and Controls

How the Web put what is true and what can be done in the same answer, how APIs split them apart, and how HEART puts them back together, shown on one GitHub pull request.

Each section is short. The technical detail sits under Technical detail at its end; Show all detail above opens every one. Code is shown as the servers sent it, abridged; diffs show lines removed in red and added in green.

1Information and controls

Every answer a server gives can carry two things: what is true now, and what can be done now. Fielding’s definition of hypertext is about keeping them together.

When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions.Roy T. Fielding, comment on “REST APIs must be hypertext-driven”, 2008
  • Information: the pull request is open, it bumps left-pad to 6.0.1, its author is JogoShugh.
  • Controls: it can be merged, commented on, closed, edited, right now.
  • Together, they guide whoever reads them step by step: each answer offers the next moves, and the moves change as the state changes.
  • “Or automaton”: the reader may be a person, an AI agent, or a plain script. Fielding meant all of them.
  • This page follows one pull request, #825 on a scratch repository, from the Web’s way, through the JSON API era, to HEART. The next page, One Goal, Decided Once, puts it to work.

2The browser: a generic client with a deliberate coupling

A browser is generic, but it isn’t uncoupled. It is tightly coupled to media types, and to nothing else.

  • It knows HTML (text, links, forms), PNG and JPEG (images), CSS (presentation), and JavaScript, which REST calls code on demand.
  • It knows nothing about any site. Not banks, not wikis, not shops. Each site sends its own controls, in those formats.
  • That coupling is the design, not a flaw: it is why one program works with every site, including sites written after it shipped.
  • A generic API client can work the same way: coupled to a media type, not to an API, and usable by a person, an agent or a script.
Think of it in terms of the Web. How many Web browsers are aware of the distinction between an online-banking resource and a Wiki resource? None of them. They don’t need to be aware of the resource types. What they need to be aware of is the potential state transitions — the links and forms — and what semantics/actions are implied by traversing those links. A browser represents them as distinct UI controls so that a user can see potential transitions and anticipate the effect of chosen actions. A spider can follow them to the extent that the relationships are known to be safe. Typed relations, specific media types, and action-specific elements provide the guidance needed for automated agents.Roy T. Fielding, comment, 2008
Of course the client has prior knowledge. Every protocol, every media type definition, every URI scheme, and every link relationship type constitutes prior knowledge that the client must know (or learn) in order to make use of that knowledge. REST doesn’t eliminate the need for a clue. What REST does is concentrate that need for prior knowledge into readily standardizable forms. That is the essential distinction between data-oriented and control-oriented integration.Roy T. Fielding, comment, 2008
Technical detail: code on demand, REST’s one optional constraint
REST allows client functionality to be extended by downloading and executing code in the form of applets or scripts. This simplifies clients by reducing the number of features required to be pre-implemented. Allowing features to be downloaded after deployment improves system extensibility. However, it also reduces visibility, and thus is only an optional constraint within REST.Roy T. Fielding, dissertation, 2000, §5.1.7
  • JavaScript is the browser’s code on demand: a site extends the client at run time. It is optional, and the Web works without it.
  • Fielding’s sixth rule (section 4) names it too: a client’s knowledge of media types “may be improved on-the-fly (e.g., code-on-demand).”
  • HEART uses no code on demand. Everything a client needs arrives as data in the media type: links, forms, JSON Schemas, reasons.
GET /repos/JogoShugh/heart-github-test/pulls/825 HTTP/1.1
Accept: application/hal+json

HTTP/1.1 200 OK
Content-Type: application/hal+json
Link: <https://w3id.org/heart-rise/hal-schema-forms>; rel="profile"
Vary: Accept, Prefer, Accept-Profile

The only things the client is coupled to: HTTP, the HAL media type, the HEART profile, JSON Schema, and problem details for refusals. All standardizable, as Fielding put it.

3When the Web had controls

Picture pull request #825 as a classic web app would serve it: a page with its information and, in the same page, the forms that act on it.

<h1>Bump left-pad from 1.0.0 to 6.0.1</h1>
<p>Open · by <a href="/JogoShugh">JogoShugh</a> · label <a href="/labels/demo">demo</a></p>
<p><a href="/pulls/825/commits">Commits</a> · <a href="/pull/825.diff">Diff</a></p>

<form method="post" action="/pulls/825/merge">
  <select name="merge_method">
    <option>merge</option> <option selected>squash</option> <option>rebase</option>
  </select>
  <button>Merge</button>
</form>

<form method="post" action="/pulls/825/comments">
  <textarea name="body" required></textarea>
  <button>Comment</button>
</form>

Now the same page for a draft. The server leaves the merge form out, and says why in its place:

  <h1>Bump left-pad from 1.0.0 to 5.0.2</h1>
- <form method="post" action="/pulls/823/merge">
-   <select name="merge_method"> … </select>
-   <button>Merge</button>
- </form>
+ <p class="why">A draft can't be merged; mark it ready for review first.</p>
  <form method="post" action="/pulls/823/comments"> … </form>
  • The browser knows nothing of pull requests, drafts or merging. It renders what came.
  • The form says the method, the address and the fields. The browser builds the request from it; it never builds an address itself.
  • The controls follow the state: present when merging is possible, absent with a reason when it isn’t.
  • A person reads the reason. A spider skips the form. Nobody needs the server’s rules in advance.

4Fielding’s 2008 complaint, and his six rules

By 2008 “REST API” meant almost any HTTP interface with JSON. Fielding objected, in public, and listed what a REST API must do.

I am getting frustrated by the number of people calling any HTTP-based interface a REST API. Today’s example is the SocialSite REST API. That is RPC. It screams RPC. There is so much coupling on display that it should be given an X rating.Roy T. Fielding, “REST APIs must be hypertext-driven”, 20 October 2008
What needs to be done to make the REST architectural style clear on the notion that hypertext is a constraint? In other words, if the engine of application state (and hence the API) is not being driven by hypertext, then it cannot be RESTful and cannot be a REST API. Period. Is there some broken manual somewhere that needs to be fixed?Fielding, 2008

“API designers, please note the following rules before calling your creation a REST API.” Each rule as he wrote it, then what it means for pull request #825:

  1. A REST API should not be dependent on any single communication protocol, though its successful mapping to a given protocol may be dependent on the availability of metadata, choice of methods, etc. In general, any protocol element that uses a URI for identification must allow any URI scheme to be used for the sake of that identification. [Failure here implies that identification is not separated from interaction.]

    For #825: its links may point anywhere, with any scheme: a web page, a diff, a git: address. The client follows by relation, not by assuming every link is the same API over HTTP.

  2. A REST API should not contain any changes to the communication protocols aside from filling-out or fixing the details of underspecified bits of standard protocols, such as HTTP’s PATCH method or Link header field. Workarounds for broken implementations (such as those browsers stupid enough to believe that HTML defines HTTP’s method set) should be defined separately, or at least in appendices, with an expectation that the workaround will eventually be obsolete. [Failure here implies that the resource interfaces are object-specific, not generic.]

    For #825: merge is plain HTTP: a PUT, a precondition (If-Match), standard status codes. No custom headers, no verbs in the body.

  3. A REST API should spend almost all of its descriptive effort in defining the media type(s) used for representing resources and driving application state, or in defining extended relation names and/or hypertext-enabled mark-up for existing standard media types. Any effort spent describing what methods to use on what URIs of interest should be entirely defined within the scope of the processing rules for a media type (and, in most cases, already defined by existing media types). [Failure here implies that out-of-band information is driving interaction instead of hypertext.]

    For #825: the method for merging, and its fields, should come from the media type’s form, not from a page of documentation about PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge.

  4. A REST API must not define fixed resource names or hierarchies (an obvious coupling of client and server). Servers must have the freedom to control their own namespace. Instead, allow servers to instruct clients on how to construct appropriate URIs, such as is done in HTML forms and URI templates, by defining those instructions within media types and link relations. [Failure here implies that clients are assuming a resource structure due to out-of band information, such as a domain-specific standard, which is the data-oriented equivalent to RPC’s functional coupling].

    For #825: the client should never assemble /pulls/825/merge from a pattern. The address arrives in the form.

  5. A REST API should never have “typed” resources that are significant to the client. Specification authors may use resource types for describing server implementation behind the interface, but those types must be irrelevant and invisible to the client. The only types that are significant to a client are the current representation’s media type and standardized relation names. [ditto]

    For #825: the client needn’t know it holds “a pull request”. It holds a HEART representation offering a form named github:merge.

  6. A REST API should be entered with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types that are appropriate for the intended audience (i.e., expected to be understood by any client that might use the API). From that point on, all application state transitions must be driven by client selection of server-provided choices that are present in the received representations or implied by the user’s manipulation of those representations. The transitions may be determined (or limited by) the client’s knowledge of media types and resource communication mechanisms, both of which may be improved on-the-fly (e.g., code-on-demand). [Failure here implies that out-of-band information is driving interaction instead of hypertext.]

    For #825: one bookmark, the gateway’s address, and from there every step chosen from what the answers offer.

There are probably other rules that I am forgetting, but the above are the rules related to the hypertext constraint that are most often violated within so-called REST APIs. Please try to adhere to them or choose some other buzzword for your API.Fielding, 2008
Technical detail: more from his comments on that post
Hypertext does not need to be HTML on a browser. Machines can follow links when they understand the data format and relationship types.
A truly RESTful API looks like hypertext. Every addressable unit of information carries an address, either explicitly (e.g., link and id attributes) or implicitly (e.g., derived from the media type definition and representation structure). Query results are represented by a list of links with summary information, not by arrays of object representations (query is not a substitute for identification of resources). Resource representations are self-descriptive: the client does not need to know if a resource is OpenSocialist because it is just acting on the representations received.
You should not be building clients that are dependent on the resource naming structure. There is simply no need to do so — the hypertext sends the client directly to the desired application state.
REST is software design on the scale of decades: every detail is intended to promote software longevity and independent evolution. Many of the constraints are directly opposed to short-term efficiency. Unfortunately, people are fairly good at short-term design, and usually awful at long-term design. Most don’t think they need to design past the current release.Roy T. Fielding, comments on “REST APIs must be hypertext-driven”, October 2008

  • 159 addresses, every one of them plain data. None says which method, which fields, or whether it is allowed now.
  • No merge control. Merging is PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge, an address the client builds from the documentation: one of 823 paths in GitHub’s description.
  • To do “merge it once it can be merged”, the client must already know every rule below, and keep up when GitHub changes them.

What a client has to know, before it can merge

Draft or not. A draft can’t be merged, yet GitHub calls draft #823 mergeable and clean:

{ "number": 823, "draft": true, "mergeable": true, "mergeable_state": "clean" }

Mergeable can be unknown. For a moment after any change, GitHub hasn’t worked it out yet; the client must look again:

{ "mergeable": null, "rebaseable": null, "mergeable_state": "unknown" }

The states aren’t listed. GitHub’s own description of mergeable_state gives a type and one example, no list of values:

"mergeable_state": { "type": "string", "example": "clean" }

The request. Built by hand, with the head’s commit to guard against a moving branch:

PUT /repos/JogoShugh/heart-github-test/pulls/825/merge
{ "merge_method": "squash", "sha": "a712a489f97688df42d118607ee780817d112d8e" }

The answers. Each to be understood in advance, as the description words them:

200 if merge was successful
405 Method Not Allowed if merge cannot be performed
409 Conflict if sha was provided and pull request head did not match
422 Validation failed
403 Forbidden · 404 Resource not found

Listing by label. GitHub’s pull request list has no label filter. A client must list issues by label, keep those that are pull requests, and follow each one’s pull_request.url:

GET /repos/{owner}/{repo}/pulls      ?state, head, base, sort, direction, per_page, page
GET /repos/{owner}/{repo}/issues     ?labels=dependencies   → keep items with "pull_request"

Permissions. Whether the caller may merge at all is in another resource, the repository, under permissions.push; and branch protection can still refuse.

Technical detail: even the documentation moves

GitHub’s description of the merge endpoint now opens with a note:

We recommend using the asynchronous merge API instead. This endpoint does not support stacked pull requests or merging with a merge queue.GitHub REST API description, “Merge a pull request”
  • A client built last year against this endpoint is now on the old way. Nothing in the answers told it so.
  • Every rule above lives in a client’s code, an SDK, or a model’s training, frozen when it was written.

6What losing the controls cost

Taking the controls out of the answer didn’t remove them. It moved them, and each move cost something.

  • The rules drifted. Into interface files, then documentation, then descriptions and generated SDKs, then a model’s training. Each copy is frozen earlier than the last.
  • The coupling moved. A browser is coupled to a handful of shared media types. An API client is coupled to one API, every path and rule of it.
  • The generic client vanished. One SDK per API; now one set of agent tools per API. The islands from before the Web, back again.
  • Standards splintered. HAL, HAL-FORMS, Siren, Collection+JSON, JSON:API, Hydra, UBER: good formats, each with links and some with forms, and none adopted everywhere.
  • The description won instead. OpenAPI succeeded by describing the bag of endpoints well. It made clients easier to generate, and kept them specific to one API.
  • Agents inherited it. An agent today gets a list of tools per API, written from the same descriptions, with the same frozen rules.

7The people who kept it alive

Through the JSON years, a few people kept building the case, and the tools, for controls in the answer.

  • Mike Amundsen defined H-Factors around 2010–2011, a way to measure “the level of hypermedia support and sophistication of a media-type”: links of several kinds, and control data for reads, updates and methods. He designed Collection+JSON (2011) and, with Irakli Nadareishvili, UBER; co-authored ALPS with Leonard Richardson and Mark Foster; and wrote the HAL-FORMS specification, the forms layer for HAL.
  • His books carry the argument: Building Hypermedia APIs with HTML5 and Node (2011), RESTful Web APIs with Leonard Richardson (2013), RESTful Web Clients: Enabling Reuse Through Hypermedia (2017), Design and Build Great Web APIs (2020), and RESTful Web API Patterns and Practices Cookbook (2022). In 2016 he live-coded a hypermedia client on stage: “From Zero to Hyper in 30 minutes”.
  • Mike Kelly published HAL as an Internet-Draft in 2012: links and embedded resources in JSON, the base HEART builds on.
  • Spring HATEOAS, led by Oliver Drotbohm with Greg Turnquist, made hypermedia ordinary in Java: HAL, HAL-FORMS, Collection+JSON, UBER and ALPS built in, with Siren and JSON:API from the community. The Spring team is now at Broadcom.
  • Adib Saikali, a Distinguished Engineer at Broadcom, has taken this to agents. His 2026 talk REST is for Agents: Rediscovering Spring HATEOAS (Spring I/O; Toronto Java Users Group) shows an agent guided through money transfers by the API’s own links and forms. His webinar Extend Your Existing APIs for Agentic Workflows with Spring HATEOAS argues that a tool list says what an agent can do, while hypermedia lets the server say what is allowed now.
  • HEART stands on their work: HAL as the base, forms as in HAL-FORMS, and the same conviction that the server should guide the client, step by step.

8Rebuilding the controls, step by step

Now the same pull request, #825, as the HEART gateway serves it, built up one change at a time from GitHub’s answer. Each step is a diff, and each answers one of Fielding’s rules.

Step 1 · Addresses leave the data and become links (rules 4 and 6)

  "number": 825,
  "state": "open",
- "url": "https://api.github.com/repos/JogoShugh/heart-github-test/pulls/825",
- "html_url": "https://github.com/JogoShugh/heart-github-test/pull/825",
- "comments_url": "https://api.github.com/repos/JogoShugh/heart-github-test/issues/825/comments",
- "diff_url": "https://github.com/JogoShugh/heart-github-test/pull/825.diff",
+ "_links": {
+   "self": { "href": "/repos/JogoShugh/heart-github-test/pulls/825" },
+   "alternate": { "href": "https://github.com/JogoShugh/heart-github-test/pull/825", "type": "text/html" },
+   "github:issues-list-comments": {
+     "href": "/repos/JogoShugh/heart-github-test/issues/825/comments", "type": "application/hal+json" },
+   "github:diff": { "href": "https://github.com/JogoShugh/heart-github-test/pull/825.diff", "type": "text/x-diff" }
+ }
  • Every address becomes a link with a relation and a media type. None is left in the state.
  • Links the gateway serves point at the gateway; a web page stays GitHub’s, typed text/html.

Step 2 · Related things are embedded as resources of their own

- "user": { "login": "JogoShugh", "url": "https://api.github.com/users/JogoShugh", … },
- "labels": [ { "name": "demo", "url": "https://api.github.com/repos/…/labels/demo" } ],
+ "_embedded": {
+   "author": { "login": "JogoShugh", "_links": { "self": { "href": "/users/JogoShugh" } } },
+   "github:labels": [ { "name": "demo", "_links": { "self": { … } } } ],
+   "github:base-repo": { "name": "heart-github-test", "full_name": "JogoShugh/heart-github-test",
+                         "default_branch": "main", "_links": { "self": { "href": "/repos/JogoShugh/heart-github-test" } } }
+ }
  • GitHub’s user becomes IANA’s author relation: a client knows who made it without knowing GitHub’s names.
  • The repository is embedded by what names it. Its counts, which change with everything in the repository, are one link away.

  • No sha field: the gateway takes the head’s commit from the state the client’s request names (step 5).

  • This is the HTML page from section 3, as JSON: the merge form gone, the reason in its place.
  • A person sees no Merge button. An agent can’t choose it. A script waiting for it keeps waiting, and can pass the reason on.

Step 5 · A version tag guards the act

GET /repos/JogoShugh/heart-github-test/pulls/825
→ 200 OK   ETag: "seq-0.hsf.L0.ca86bad8d04b304a"

PUT /repos/JogoShugh/heart-github-test/pulls/825/actions/merge
If-Match: "seq-0.hsf.L0.ca86bad8d04b304a"
{ "merge_method": "squash" }
→ 200 OK                        when #825 is as it was read
→ 412 Precondition Failed      when it has changed since
  • The act names the exact state it was chosen from. A merge is never applied to a state nobody saw.
  • The gateway binds GitHub’s sha from that same state: the client sends no commit hash, and knows no rule about it.

Step 6 · The answer describes itself (rules 3 and 5)

HTTP/1.1 200 OK
Content-Type: application/hal+json
ETag: "seq-0.hsf.L0.ca86bad8d04b304a"
Cache-Control: no-cache
Link: <https://w3id.org/heart-rise/hal-schema-forms>; rel="profile", <https://w3id.org/heart-rise>; rel="profile"
Vary: Accept, Prefer, Accept-Profile
  • The media type and the profile say how to read all of it. That is the whole of the client’s prior knowledge.
  • Nothing says “pull request”. The client sees forms and links, as a browser sees a page.
Technical detail: the rules, mapped
Fielding’s ruleIn the HEART answer for #825
1. Any URI schemeLinks keep their own schemes and types: text/html, text/x-diff, gateway resources.
2. No protocol changesPlain GET/PUT/POST, If-Match, 412, 428, problem details.
3. Describe the media typeMethods and fields live in each form; the profile defines how to read forms.
4. No fixed namesEvery address arrives in a link or a form’s target.
5. No typed resourcesThe client sees a HEART representation and relation names, never “pull request”.
6. Enter from a bookmarkOne URI, the gateway’s index; every step after it is chosen from what was offered.

9One client, for a person, an agent and a script

With the controls back in the answer, one generic client serves every kind of reader, the way one browser serves every visitor.

  • A person sees the merge form as a button, and the reason as text when it is missing.
  • An AI agent is shown the offered forms and links, by name and title, and chooses among them. It can’t choose what isn’t offered.
  • A script replays a kept choice: act("github:merge", "merge_method" to "squash"), which acts only where the form is offered now.
  • The server’s rules hold for all three, because all three act through the same controls. That is Fielding’s “user (or automaton)”, taken literally.

10What controls make possible: a goal in plain words

When the server says what can be done, and why not, a person can write a whole job in plain words. This is the goal the next page runs:

Merge dependency bumps once they can be merged. Keep watching until the watch's issue is closed.

- In {owner}/{repo}
  - Open an issue titled "Merge watch", saying "Close this issue to stop the watch." `as watch`
  - Whenever a pull request labelled {label} changes `as pr`
    - If it's labelled {hold}, leave it, and say so once.
    - Once it can be merged, merge it by squashing.
      Or give up after 3 minutes.
      Otherwise, tell its author in one friendly sentence why it wasn't merged and what to do next. `reasoned`
- Until someone closes {watch}
  • “Once it can be merged” is step 4: wait until the merge form appears. No rule about drafts, conflicts or mergeable_state.
  • “merge it by squashing” is step 3: the form’s merge_method, from its enum.
  • “tell its author … why it wasn’t merged” is step 4’s reason, in the server’s words, passed to the model.
  • “labelled {label}” and “labelled {hold}” are checks on the embedded labels from step 2.
  • “Until someone closes {watch}” reads the issue again by the link the server gave when it was created.
  • None of it names an endpoint. Every problem from section 5 is gone from the goal, because the answers carry it.
