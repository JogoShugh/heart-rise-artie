HEART and ARTIE

The Browser for Agents

How the Web made one client work with every site, and how a media type and a generic agent can do the same for APIs.

Each section is short. The technical detail sits under Technical detail at its end; Show all detail above opens every one.

1The question

One program, a browser, works with every site, including sites that didn’t exist when it was written. Agents don’t work that way.

  • The browser knows no site. It knows a few formats, chiefly HTML, and what a link and a form mean.
  • Every site speaks those formats, so every site works.
  • An agent is built per API: a GitHub agent, a Stripe agent, a billing agent, each with its own tools and prompts.
  • A private API starts with nothing until someone writes the docs or tools for it.
  • The claim of this essay: what made the browser generic can make an agent generic. HEART plays HTML’s part; ARTIE plays the browser’s.
Technical detail: what “coupled to a media type” means on the wire

A browser says which formats it reads in Accept; the site answers in one of them and names it in Content-Type. Nothing in the exchange names the site’s own vocabulary.

GET /orders/42 HTTP/1.1
Accept: text/html

HTTP/1.1 200 OK
Content-Type: text/html

A HEART client does the same, and asks for the HEART profile beside the media type:

GET /repos/acme/claims/pulls/20 HTTP/1.1
Accept: application/hal+json
Accept-Profile: <https://w3id.org/heart-rise/hal-schema-forms>

HTTP/1.1 200 OK
Content-Type: application/hal+json
Link: <https://w3id.org/heart-rise/hal-schema-forms>; rel="profile"
ETag: "seq-5.hsf.L2.e8e98768123683fa"
Cache-Control: no-cache
  • The base media type is HAL, application/hal+json. HEART is a profile over it, negotiated with W3C Content Negotiation by Profile (Accept-Profile, Link: rel="profile"), not a media-type parameter.
  • Two dialects: HAL Schema Forms (_forms, full JSON Schema per field) is the reference; HAL-FORMS (_templates, the format Spring HATEOAS ships) is an on-ramp, served collapsed only.
  • Both are generated from one source of truth for which acts are legal now, so they can’t disagree.
  • A server that varies an answer by Accept, Prefer or Accept-Profile sends Vary with them.

2Before the Web: links, but no generic client

Linked information is an old idea. For decades each system came with its own client.

  • 1945 Bush’s Memex: a desk of documents and the trails between them. Never built.
  • 1965 Nelson coins “hypertext”.
  • 1968 Engelbart’s NLS: live, linked, editable information, on NLS terminals only.
  • 1987 HyperCard: millions of linked stacks, readable only in HyperCard.
  • Content and reader came as a pair, so links stayed inside one system.
  • The Web didn’t invent links. It split the client from the content, with only agreed formats between them.

3The Web’s invention: a generic client

Three agreements made the split work: URIs name things, HTTP moves them, HTML describes them. Forms, from about 1993, completed it.

  • Links tell the browser where it can go next. Forms tell it what it can do: search, order, pay.
  • The page arrives with its own controls. The browser doesn’t know this shop takes a postcode; the form says so.
  • The browser’s knowledge stops at a clear line: protocol, names, media type, links and forms.
  • Everything about a site arrives in the site’s own pages, when it is needed.
  • So a site can change without breaking its visitors. Nobody updates the browser.
Technical detail: a form builds the request, not the client 
<form method="get" action="/search">
  <input name="q">
</form>

GET /search?q=tomatoes HTTP/1.1      ← built from the form's action and fields
  • The browser builds the address from the form, by a fixed algorithm (HTML’s “mutate action URL”), never from knowledge of the site.
  • A post form sends a body; the site usually answers 303 See Other with the next page’s address.
  • HEART keeps the same split. A lookup or search is a GET form whose target is an RFC 6570 template filled from the form’s own fields: searchBeds targets /beds{?name}, getBed targets /beds/{id}.
  • A GET form is safe: no body, no If-Match. Acts use POST, PUT, PATCH or DELETE, never GET, each with HTTP’s own meaning (PUT and DELETE idempotent).

4Fielding names it

In 2000 Roy Fielding described the Web’s architecture and called it REST. One of its four interface constraints is what makes a generic client possible.

When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions.Roy T. Fielding, 2008
  • Hypermedia as the engine of application state: the client moves on by choosing among the links and forms the current answer offers.
  • It is the constraint most HTTP APIs dropped. In 2008 Fielding wrote that an API not driven by hypertext “cannot be a REST API. Period.”
  • Information and controls, together: the theme of this essay.
  • “Or automaton”: he meant machines too. “Machines can follow links when they understand the data format and relationship types.”
  • A REST API should be entered “with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types.” A bookmark and a media type. Nothing else.
Technical detail: the four constraints, as HEART meets them
ConstraintIn HEART
Identification of resourcesEvery resource has a stable URL. Shared affordance sets and schemas have content-addressed URLs, one per distinct body.
Manipulation through representationsAn act sends a JSON body that the form’s JSON Schema describes, to the form’s target.
Self-descriptive messagesThe media type, the profile in Link: rel="profile", strong ETags, and refusals as RFC 9457 problems with a type URI.
Hypermedia as the engine of application stateOne service index is the bookmark. Every other resource is reached by links and forms; a client never builds a URI.
  • Collections list members under IANA’s item relation, each titled; paging uses next, prev, first, last.
  • ARTIE enforces the bookmark rule on itself: reading an address again is allowed only if the server handed that address over in this run.

5How APIs lost it: the rules moved away

Web APIs kept HTTP and URLs and swapped HTML for JSON. JSON carries data, but no links and no forms, so the rules had to live somewhere else.

  • The Web: the rules are in the page, written by the server as it answers. True now.
  • RPC and SOAP: in an interface file compiled into the client. True as of the release.
  • JSON APIs: in documentation a developer reads. True as of the reading.
  • OpenAPI: in a description of every operation, generated into SDKs. True as of the last build.
  • LLM agents: partly in training data. True as of training.
  • Each step puts the rules further from the server and freezes them earlier. The server goes on changing; the copy doesn’t know.
  • Each step also brings back the islands: a client generated for one API is a client for that API alone.
Technical detail: GitHub’s answer, and GitHub’s description

A pull request, as GitHub’s REST API returns it (abridged):

{ "number": 20, "state": "open", "draft": false,
  "mergeable": true, "mergeable_state": "blocked",
  "url":                 "https://api.github.com/repos/…/pulls/20",
  "html_url":            "https://github.com/…/pull/20",
  "diff_url":            "https://github.com/…/pull/20.diff",
  "issue_url":           "https://api.github.com/repos/…/issues/20",
  "commits_url":         "https://api.github.com/repos/…/pulls/20/commits",
  "comments_url":        "https://api.github.com/repos/…/issues/20/comments",
  "statuses_url":        "https://api.github.com/repos/…/statuses/{sha}",
  … }
  • Pull request #20 on our scratch repository had 157 members whose value is a URL. They are data: no method, no fields, no word on whether an act is allowed now.
  • Whether merge is allowed must be worked out from state, draft, mergeable, mergeable_state, the caller’s permissions and branch protection: rules the client has to know.

The same operation in GitHub’s OpenAPI description:

PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge
  operationId: pulls/merge
  responses:
    200: if merge was successful
    405: Method Not Allowed if merge cannot be performed
    409: Conflict if sha was provided and pull request head did not match
  • The description had 823 paths and 1,242 operations (commit of 18 October 2026), 30 of them for pull requests.
  • Every one is a template with placeholders. It lists what is possible ever; it can’t say what is possible now.

6Agents inherit the problem

A language-model agent is the most adaptable client ever built. In front of a browser it does what a person does. In front of JSON there is nothing to see.

  • The data says what the pull request is, not what can be done with it.
  • The agent answers from training, from docs it was given, or by trying and reading the error.
  • A famous public API mostly works. A private API starts with nothing. A changed API is confidently out of date.
  • The usual remedy, hand-written tools per API, is the islands again. The agent is generic; its connection to the world isn’t.
Technical detail: why a tool list isn’t a form

A hand-written tool for an agent (illustrative):

{ "name": "merge_pull_request",
  "description": "Merge a pull request. Fails if it can't be merged.",
  "inputSchema": { "type": "object",
    "properties": { "owner": {…}, "repo": {…}, "pull_number": {…},
                    "merge_method": { "enum": ["merge","squash","rebase"] } } } }
  • It uses JSON Schema, like a HEART form. The difference is when it is true.
  • A tool is offered whether or not merge is possible for this pull request now. The agent learns by calling it.
  • Its inputs include the address parts (owner, repo, pull_number): the agent builds the target.
  • The Model Context Protocol lets a server’s tool list vary with the caller’s authorization, not with the state of what the tools act on.
  • A HEART form exists only while the act is legal, targets one resource, and asks only for what the act needs.

7HEART: a media type for agents

The browser’s answer was never to know more about sites. It was a media type that carries the controls. HEART does that for agents, in JSON.

  • Links by relation in _links: author, next, or a service’s own. A client follows a relation; it never builds an address.
  • Forms in _forms: method, target, and inputs in JSON Schema, the schema language models already use for tools.
  • Forms follow the state. No merge form until the pull request can be merged. An open issue offers close; a closed one offers reopen.
  • Why an act is absent. A missing form can link to its reason.
  • Refusal of anything not offered. The rules the forms show are the rules the service enforces.
  • The rules are back in the answer, true now. The name says it: Hypermedia, Enforced, for Agentic, Reliable Transactions.
Technical detail: a representation, collapsed (L0)

A pull request through the HEART gateway, abridged:

{ "number": 20, "state": "open", "title": "Bump left-pad to 1.0.3",
  "_links": {
    "self":   { "href": "https://localhost:8392/repos/acme/claims/pulls/20" },
    "curies": [ { "name": "github", "href": "…{rel}", "templated": true } ],
    "alternate": { "href": "https://github.com/acme/claims/pull/20", "type": "text/html" },
    "github:commits": { "href": "…/pulls/20/commits", "type": "application/hal+json" },
    "hr:unavailable": { "href": "…/unavailable/sha256-…", "integrity": "sha256-…" } },
  "_embedded": {
    "author": { "login": "ana", "_links": { "self": { "href": "…/users/ana" } } } },
  "_forms": {
    "github:merge": {
      "title": "Merge", "method": "PUT",
      "_links": { "target": { "href": "…/pulls/20/merge" } },
      "schema": { "type": "object", "properties": {
        "merge_method":   { "enum": ["merge", "squash", "rebase"] },
        "commit_title":   { "type": "string" },
        "commit_message": { "type": "string" } } } },
    "github:comment": { … }, "github:close": { … }, "github:edit": { … } } }
  • GitHub’s *_url members are lifted out of the state into _links, each with a type. API links are rewritten to the gateway; web pages keep their own address.
  • GitHub’s user is embedded under IANA’s author, so a client knows who made it without knowing GitHub’s names.
  • The merge form has no sha field: the gateway binds it from the state the client read, so a merge lands only on the head it was offered for.
Technical detail: an act, and how it is refused 
PUT …/pulls/20/merge HTTP/1.1
Content-Type: application/json
If-Match: "seq-5.hsf.L2.e8e98768123683fa"

{ "merge_method": "squash" }

428precondition-requiredNo If-MatchSend again, conditionally
412staleThe state changed since it was readRead again; drop the act, decide again
409not-offeredThe act isn’t offered in this stateRead again; it may be gone for good
422invalid-inputA field breaks the schemaFix the input; violations point at the fields

Content-Type: application/problem+json

{ "type": "https://w3id.org/heart-rise/problems/stale",
  "title": "The resource changed since it was read", "status": 412 }
  • The checks run in that order: 428, 412, 409, 422.
  • A client tells refusals apart by status and type, never by reading the prose.
  • ETags are strong and change whenever the bytes do, even if only the rendering changed.
Technical detail: shared, cached controls (L1, L2)

A client says how it wants the controls with Prefer. At L2 the forms and schemas are separate resources, named by a digest of their bytes:

GET …/pulls/20                     Prefer: forms=link, schema=link
→ 200  state + _links.forms → /affordance-sets/sha256-…   (no-cache, ETag)
GET /affordance-sets/sha256-…
→ 200  _forms with schema.$ref and integrity              (max-age=31536000, immutable)
GET /schemas/sha256-…
→ 200  the schema                                         (immutable)
RungPreferWhat arrives
L0noneState, forms and schemas in one answer
L1forms=linkState, and a link to the affordance set
L2forms=link, schema=linkState; the set; each schema on its own
  • Every pull request in the same situation shares one affordance set, at one address, cached once.
  • In steady state, a sync of an unchanged resource is one conditional GET answered 304, and nothing more.
  • The explanation of absent acts is shared the same way: a function of state alone, fetched only when someone asks why.
{ "unavailable": [
    { "rel": "github:merge",
      "reason": "Branch protection blocks the merge: a required check or review is missing." } ] }
Technical detail: choices that come from the state 
"playerNumber": {
  "type": "integer",
  "hr:options": {
    "pointer": "/{team}/players",
    "valueField": "number", "promptField": "name",
    "where": { "fouledOut": false } } }
  • Not “any integer”: one of this team’s players who haven’t fouled out, read from the resource itself.
  • Or from another resource: a ticket’s agent takes its choices from /agents{?priority}, filtered to those on duty.
  • The client offers only those values. The server refuses any other with 422 at that field.
  • JSON Schema validators ignore the unknown keyword, so plain clients still work.

8ARTIE: the generic agent

If HEART is the HTML of this story, ARTIE is the browser. It knows HEART, and no service.

  • ARTIE reads representations, follows relations, fills in forms, sends them with the right preconditions and understands refusals.
  • It doesn’t know GitHub, a ticket desk or a basketball game. They arrive in their own representations, as sites do.
  • The model sits in the person’s seat, not the browser’s. It chooses among what is offered, as a person picks a button.
  • It never types an address and never invents an action.
  • A new service needs one thing: its bookmark.
Technical detail: the sync, reason, act cycle 
sync    GET   resource      Cache-Control: no-cache, If-None-Match: "…"   → 200 or 304
reason        choose one of the forms in hand, fill its schema               (a model, or a script)
act     PUT   form target   If-Match: "…"                                  → 2xx, or a refusal
  • Sync: every resource is revalidated on every read; an unchanged one costs a 304.
  • Reason: only over forms present now. A model is handed the state, the offers and the links, and answers by naming one offer and its fields; it has no way to answer with a URL.
  • Act: always conditional. On 409 it reads again and decides again; on 412 it discards the act, so it never writes over someone else’s change.
  • Credentials are added below the cache, just above the wire, scoped to one origin. The model never sees them.
Technical detail: heart-script, ARTIE’s script language 
heart("https://localhost:8392/") {                       // the bookmark
    act("github:repos-get", "owner" to owner, "repo" to repo) {
        act("github:open-issue", fields = {
            "title" to "Bench watch, week $week"
            "body"  to "Close this issue to stop the watch."
        }) { keepAs("watch") }                           // remember the new issue by name
    }
}
  • A script is Kotlin. Every step names a relation, never a URL. Each nested block runs on the resource the act answered with.
  • An act whose form isn’t offered where the script stands is refused before anything is sent.
  • artie run script.kts owner=… runs it, with no model.

9From browsing to a routine

People automate what they do every week in a browser: bookmarks, macros, recorded tests. ARTIE does the same, with one improvement.

A goal, as a person writes it:

- Whenever a pull request labelled sowing changes
  - If it's labelled hold, leave it, and say so once.
  - Once it can be merged, merge it by squashing.
    Or give up after 5 minutes.
    Otherwise, say why it wasn't merged, unless it's said already.
  • The goal names no endpoint, no field and no URL.
  • ARTIE browses it once, with a model choosing among what the service offers.
  • Those choices become a script: relations to follow, forms to fill, checks to make. The forms it used are pinned.
  • From then on the script runs alone, with no model.
  • If the service stops offering a form, or changes one, the script stops before it sends anything. A recorded macro would click whatever is there.
Technical detail: the goal’s words, and what they become
In the goalMeansIn the script
Whenever …Every member of a list, now and as it changeswhenever { has { … } }
If …A check, decided once, on the memberhas, leaveWhere
unless it’s said alreadyAct only if the words aren’t thereactOnce(…, listedIn = …)
Once … Or give up afterWait for an act to be offered, up to a timeonce("github:merge", giveUp = …)
OtherwiseWhat to do on giving up, told the server’s reasonotherwise = { why -> … }
Until …When the whole watch endswatch(until = …)
whenever {
    has { "github:labels" has label }
    leaveWhere("a person holds it back") { "github:labels" has hold }
    once("github:merge", giveUp = 5.minutes, otherwise = { why ->
        follow("github:issues-get") {
            actOnce("github:comment", "body" to "Not merged: $why",
                listedIn = "github:issues-list-comments")
        }
    }) { act("github:merge", "merge_method" to "squash") }
}
  • The words are parsed by ARTIE. The model decides only how this service does what each line asks: which list, which check, which act.
  • Conditions are data (facts blocks), not if, so a script can be read back, checked and compared with its goal.
  • Each Whenever runs as a listener on its own thread; a slow one holds up only itself.
Technical detail: run, generate, run again 
artie run seed-bench.goal.md owner=acme --reasoner claude --trace runs/first.yaml
artie generate runs/first.yaml --out seed-bench.kts --script seed-bench.goal.md
artie run seed-bench.kts owner=acme

artie generate writes three files beside the script:

# seed-bench.pins.yaml: what the run was offered, held to before every act
forms:
  github:merge:
    integrity: sha256-…
    method: PUT
    sets: [ sha256-… ]
  • The script: inputs, relations, checks. No prompt, no model.
  • Pins: each form by its digest. Lenient (the default) refuses a form no longer offered or changed; strict also refuses one offered in a set not recorded for it.
  • Derivation: for every value in the script, the rule that bound it and where it came from: an input, an earlier answer, or the goal’s words.
  • A step the goal marks as a judgement stays a question for the model, in the person’s own words; everything else is pinned.

10Old systems, new clients: the gateway

Most services won’t speak HEART soon. The Web met the same problem in the 1990s and solved it with a front end.

  • Banks and airlines didn’t rewrite their mainframes. Web front ends rendered them as HTML.
  • A HEART gateway renders an existing API as HEART, from its published description and a short connector.
  • Out: the state, links lifted out of the data, and only the forms the state allows.
  • In: every act checked against what was offered, before the API hears it.
  • GitHub doesn’t change. Anyone can run a gateway, on a laptop, for the APIs they depend on.
Technical detail: a connector, in three parts

Which operations: only these are read from GitHub’s description; the rest are left out before parsing.

# connector.yaml
profile: github
include: [ pulls/get, pulls/list, pulls/merge, pulls/update, issues/create-comment, … ]
headers: { X-GitHub-Api-Version: "2022-11-28" }

Which acts: each a projection of one GitHub operation.

# pull.resource.yaml
acts:
  merge:
    operation: pulls/merge
    title: Merge
    fields: [merge_method, commit_title, commit_message]
    bind: { sha: /head/sha }      # merge only the head the client read
    stale: 409                    # GitHub's 409 here means the client's view is stale
    refused: 405                  # GitHub's 405 means it can't merge now

When each act is allowed, and why not:

# pull.reader.yaml
allowed:
  table: /state
  rows:
    open:   { allow: [close, merge, edit, request-review, update-branch, comment] }
    closed: { allow: [reopen, edit, comment] }
rules:
  - when: { /draft: true }
    absent: { merge: "A draft can't be merged; mark it ready for review first." }
  - when: { /mergeable_state: blocked }
    absent: { merge: "Branch protection blocks the merge: a required check or review is missing." }
  • The rules GitHub leaves to every client are written once, here, and served to all of them as forms and reasons.
  • The gateway calls GitHub as each caller, with their own token (UPSTREAM_AUTH=caller).
  • Members GitHub works out in the background (mergeable, mergeable_state) are marked volatile: they change the offers, not the validator an act is checked against.
  • A read can be held until a signed GitHub webhook says what changed, instead of polling.
Technical detail: or speak HEART natively

A service built on the HEART library declares its acts once, and which states offer them:

offers = Offers(
    keys = Status.entries,
    offered = { status ->
        when (status) {
            Status.NEW      -> listOf("assign", "comment", "changePriority")
            Status.ASSIGNED -> listOf("assign", "comment", "askCustomer", "resolve", "changePriority")
            Status.RESOLVED -> listOf("reopen", "close", "changePriority")
            Status.CLOSED   -> emptyList()
            …
        }
    },
    whyAbsent = SupportProfile::whyAbsent,
)
  • From the ticket desk domain. The library renders the forms, schemas, links, ETags and refusals; the domain records what each act does.
  • By the time an act reaches domain code, the library has checked it is offered, current and valid.

11What it costs, and what it isn’t

A generic client is bought with a shared format. That has a price.

  • A service must speak HEART, or someone must put a gateway in front of it. A good connector is real work.
  • A HEART agent does only what the service offers. An agent with a shell and hand-written tools can do more things, with fewer promises about any of them.
  • The Web made the same trade. A browser can’t do everything a native program can; it does a narrower thing for every site, safely.
  • HEART and ARTIE make that bargain for agents: the model chooses only among options the service vouches for.
Technical detail: the conformance ladder
RungWhat it proves
L0State and its legal acts together. Correct, not economical; not enough to claim compliance.
L1Affordance sets fetched by link, shared and cached.
L2Schemas fetched separately. The reference rung, and the minimum for compliance.
L3The caching proof: unchanged state costs a 304.
L4Concurrency and errors: If-Match, 412, 409, 428, problem types.
L5Both dialects from one source of truth.
L6Reasoning. Optional: a HEART client need not contain a model at all.
  • A test kit (the TCK) checks a server rung by rung.
  • The negotiation by profile it relies on is a W3C Working Draft, not yet a Recommendation.

12Close

  • The Web never made people guess. Every page arrives with what you can do next, and one client reads them all.
  • In 2008 Fielding said machines deserved the same, “or automaton”, years before an automaton could use it.
  • Now one can. It doesn’t need more knowledge of each API. It needs what the browser always had: the information and the controls, together.
