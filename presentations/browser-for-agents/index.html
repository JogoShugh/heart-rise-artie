HEART and ARTIE

The Browser for Agents

How the Web made one client work with every site, and how a media type and a generic agent can do the same for APIs.

1The question

One program, a browser, works with every site, including sites that didn’t exist when it was written. Agents don’t work that way.

  • The browser knows no site. It knows a few formats, chiefly HTML, and what a link and a form mean.
  • Every site speaks those formats, so every site works.
  • An agent is built per API: a GitHub agent, a Stripe agent, a billing agent, each with its own tools and prompts.
  • A private API starts with nothing until someone writes the docs or tools for it.
  • The claim of this essay: what made the browser generic can make an agent generic. HEART plays HTML’s part; ARTIE plays the browser’s.

2Before the Web: links, but no generic client

Linked information is an old idea. For decades each system came with its own client.

  • 1945 Bush’s Memex: a desk of documents and the trails between them. Never built.
  • 1965 Nelson coins “hypertext”.
  • 1968 Engelbart’s NLS: live, linked, editable information, on NLS terminals only.
  • 1987 HyperCard: millions of linked stacks, readable only in HyperCard.
  • Content and reader came as a pair, so links stayed inside one system.
  • The Web didn’t invent links. It split the client from the content, with only agreed formats between them.

3The Web’s invention: a generic client

Three agreements made the split work: URIs name things, HTTP moves them, HTML describes them. Forms, from about 1993, completed it.

  • Links tell the browser where it can go next. Forms tell it what it can do: search, order, pay.
  • The page arrives with its own controls. The browser doesn’t know this shop takes a postcode; the form says so.
  • The browser’s knowledge stops at a clear line: protocol, names, media type, links and forms.
  • Everything about a site arrives in the site’s own pages, when it is needed.
  • So a site can change without breaking its visitors. Nobody updates the browser.

4Fielding names it

In 2000 Roy Fielding described the Web’s architecture and called it REST. One of its four interface constraints is what makes a generic client possible.

When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions.Roy T. Fielding, 2008
  • Hypermedia as the engine of application state: the client moves on by choosing among the links and forms the current answer offers.
  • It is the constraint most HTTP APIs dropped. In 2008 Fielding wrote that an API not driven by hypertext “cannot be a REST API. Period.”
  • Information and controls, together: the theme of this essay.
  • “Or automaton”: he meant machines too. “Machines can follow links when they understand the data format and relationship types.”
  • A REST API should be entered “with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types.” A bookmark and a media type. Nothing else.

5How APIs lost it: the rules moved away

Web APIs kept HTTP and URLs and swapped HTML for JSON. JSON carries data, but no links and no forms, so the rules had to live somewhere else.

  • The Web: the rules are in the page, written by the server as it answers. True now.
  • RPC and SOAP: in an interface file compiled into the client. True as of the release.
  • JSON APIs: in documentation a developer reads. True as of the reading.
  • OpenAPI: in a description of every operation, generated into SDKs. GitHub’s lists more than twelve hundred. True as of the last build.
  • LLM agents: partly in training data. True as of training.
  • Each step puts the rules further from the server and freezes them earlier. The server goes on changing; the copy doesn’t know.
  • Each step also brings back the islands: a client generated for one API is a client for that API alone.

A description of everything possible can’t say what is possible now. GitHub’s description of merge says so itself:

PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge
  405: Method Not Allowed if merge cannot be performed
  • To find out whether merge is allowed, you try it.

6Agents inherit the problem

A language-model agent is the most adaptable client ever built. In front of a browser it does what a person does. In front of JSON there is nothing to see.

  • The data says what the pull request is, not what can be done with it.
  • The agent answers from training, from docs it was given, or by trying and reading the error.
  • A famous public API mostly works. A private API starts with nothing. A changed API is confidently out of date.
  • The usual remedy, hand-written tools per API, is the islands again. The agent is generic; its connection to the world isn’t.

7HEART: a media type for agents

The browser’s answer was never to know more about sites. It was a media type that carries the controls. HEART does that for agents, in JSON.

A form, as an agent receives it:

"_forms": {
  "github:merge": {
    "title": "Merge this pull request",
    "method": "PUT",
    "_links": { "target": { "href": "…/pulls/20/merge" } },
    "schema": { "properties": {
      "merge_method": { "enum": ["merge", "squash", "rebase"] } } } } }
  • Links by relation in _links: author, next, or a service’s own. A client follows a relation; it never builds an address. This is HAL, already used by Spring and others.
  • Forms in _forms: method, target, and inputs in JSON Schema, the schema language models already use for tools.
  • Forms follow the state. No merge form until the pull request can be merged. An open issue offers close; a closed one offers reopen.
  • Why an act is absent. A missing form can link to its reason: “Branch protection blocks the merge: a required check or review is missing.”
  • Refusal of anything not offered. The service refuses unoffered acts, writes over a changed state, and inputs outside the schema.
  • The rules are back in the answer, true now. The name says it: Hypermedia, Enforced, for Agentic, Reliable Transactions.

8ARTIE: the generic agent

If HEART is the HTML of this story, ARTIE is the browser. It knows HEART, and no service.

  • ARTIE reads representations, follows relations, fills in forms, sends them with the right preconditions and understands refusals.
  • It doesn’t know GitHub, a ticket desk or a basketball game. They arrive in their own representations, as sites do.
  • The model sits in the person’s seat, not the browser’s. It chooses among what is offered, as a person picks a button.
  • It never types an address and never invents an action.
  • A new service needs one thing: its bookmark.

9From browsing to a routine

People automate what they do every week in a browser: bookmarks, macros, recorded tests. ARTIE does the same, with one improvement.

A goal, as a person writes it:

- Whenever a pull request labelled sowing changes
  - If it's labelled hold, leave it, and say so once.
  - Once it can be merged, merge it by squashing.
    Or give up after 5 minutes.
    Otherwise, say why it wasn't merged, unless it's said already.
  • The goal names no endpoint, no field and no URL.
  • ARTIE browses it once, with a model choosing among what the service offers.
  • Those choices become a script: relations to follow, forms to fill, checks to make. The forms it used are pinned.
  • From then on the script runs alone, with no model.
  • If the service stops offering a form, or changes one, the script stops before it sends anything. A recorded macro would click whatever is there.
  • In our trials, a seed-bench goal like this one ran on GitHub once with a model, then with none.

10Old systems, new clients: the gateway

Most services won’t speak HEART soon. The Web met the same problem in the 1990s and solved it with a front end.

  • Banks and airlines didn’t rewrite their mainframes. Web front ends rendered them as HTML.
  • A HEART gateway renders an existing API as HEART, from its published description and a short connector.
  • Out: the state, links lifted out of the data, and only the forms the state allows.
  • In: every act checked against what was offered, before the API hears it.
  • GitHub doesn’t change. Anyone can run a gateway, on a laptop, for the APIs they depend on.

11What it costs, and what it isn’t

A generic client is bought with a shared format. That has a price.

  • A service must speak HEART, or someone must put a gateway in front of it. A good connector is real work.
  • A HEART agent does only what the service offers. An agent with a shell and hand-written tools can do more things, with fewer promises about any of them.
  • The Web made the same trade. A browser can’t do everything a native program can; it does a narrower thing for every site, safely.
  • HEART and ARTIE make that bargain for agents: the model chooses only among options the service vouches for.

12Close

  • The Web never made people guess. Every page arrives with what you can do next, and one client reads them all.
  • In 2008 Fielding said machines deserved the same, “or automaton”, years before an automaton could use it.
  • Now one can. It doesn’t need more knowledge of each API. It needs what the browser always had: the information and the controls, together.
