HEART and ARTIE

The Browser for Agents

How the Web made one client work with every site, and how a media type and a generic agent can do the same for APIs.

1The question

You have never installed a client for your bank’s website. Or for a newspaper, a shop or your council’s planning forms. One program, a browser, handles all of them, including sites that didn’t exist when it was written. That is so ordinary we forget how strange it is.

The browser can do it because of what it is coupled to. It doesn’t know any site. It knows a few formats, chiefly HTML, and a few rules for using them: follow a link, fill in a form and send it. Every site speaks those formats, so every site works.

Software agents today have the opposite arrangement. An agent that works with GitHub is built for GitHub: its tools, its endpoints, its rules. An agent for Stripe is built again for Stripe. An agent for your own billing system starts from nothing, until someone writes the documentation, the tools or the prompts for it. The coupling runs from each agent to each API, by hand.

This essay is about closing that gap. The claim is simple: what made the browser generic can make an agent generic. HEART is a media type that does for agents what HTML does for browsers. ARTIE is the generic agent that reads it. The rest is how we got here, and why the idea is older than it looks.

2Before the Web: links, but no generic client

Linked information is an old dream. In 1945 Vannevar Bush described the Memex, a desk that would store a researcher’s documents and the trails between them. It was never built. In 1965 Ted Nelson coined the word hypertext. In 1968 Douglas Engelbart demonstrated NLS: live, linked, editable information on a screen, with a mouse. In 1987 Apple shipped HyperCard, and millions of people built linked stacks of cards.

Each was remarkable, and each was an island. NLS ran on NLS terminals. A HyperCard stack ran in HyperCard. The content and the program that read it came as a pair, so knowledge could link only within one system.

The Web did not invent links. Its real invention was the split: the client on one side, the content on the other, and nothing between them but agreed formats and a protocol.

3The Web’s real invention: a generic client

Tim Berners-Lee’s proposal of 1989 and the public Web of 1991 rest on three agreements. URIs name things. HTTP moves representations of them. HTML describes a page. Anyone who implements the three can read anything published with them.

The decisive step came a few years later, between 1993 and 1995, when HTML gained forms. Until then a page could tell you where to go next. With forms, it could tell you what you could do: search, order, sign up, pay. The page arrived with its own controls. The browser didn’t need to know that this shop takes a quantity and a postcode. The form said so, and the browser drew it.

So the browser’s knowledge is general, and stops at a clear line. It knows the protocol, how to name and reach things, the media type, and what a link and a form mean. Everything about a particular site arrives in the site’s own pages, at the moment it is needed.

This is why a site can change without breaking its visitors. Rename a page, move a button, add a step to checkout: the next page you receive describes the new arrangement. Nobody updates your browser.

4Fielding names it

In 2000 Roy Fielding described the architecture behind the Web in his dissertation and called it REST. He named four constraints on the interface between client and server. Resources are identified. They are manipulated through representations. Messages describe themselves. And hypermedia is the engine of application state: the client moves from one state to the next by choosing among the links and forms the current representation offers.

The fourth constraint is what makes a generic client possible. It is also the one the industry quietly dropped. By 2008 so many HTTP interfaces called themselves REST that Fielding wrote a short, irritated post: “if the engine of application state (and hence the API) is not being driven by hypertext, then it cannot be RESTful and cannot be a REST API. Period.”

In the comments he defined what he meant, and the definition is the theme of this essay:

When I say hypertext, I mean the simultaneous presentation of information and controls such that the information becomes the affordance through which the user (or automaton) obtains choices and selects actions.

Note the words in brackets: or automaton. Fielding was not only describing people with browsers. In the same thread he wrote that “machines can follow links when they understand the data format and relationship types,” and that a REST API should be entered “with no prior knowledge beyond the initial URI (bookmark) and set of standardized media types.” A bookmark and a media type. Nothing else.

5How APIs lost it

When web APIs spread in the 2000s, they kept HTTP and URLs and swapped HTML for JSON. JSON is a fine format for data. But a JSON object has no link and no form. A list of pull requests arrives as data, and nothing in it says what you may do with any of them.

The knowledge didn’t disappear. It moved, and each move took it further from the answer a client holds. With RPC and SOAP, the rules lived in an interface file compiled into the client. With JSON APIs, they lived in human documentation. With OpenAPI, they live in a description of every operation the API will ever accept: GitHub’s lists more than twelve hundred. With today’s language-model agents, they live partly in training data.

Each of these is useful, and each brings back the islands. A client generated from an API’s description is a client for that API. When the API changes, the client is wrong until someone regenerates it. And a description of everything that is ever possible cannot say what is possible now. GitHub’s description of the merge operation is honest about this. It lists a response: “405 Method Not Allowed if merge cannot be performed.” To find out, you try.

6Agents inherit the problem

A language-model agent is the most adaptable client ever built. It reads, it reasons, it recovers from surprises. Put it in front of a browser and it does what a person does: reads the page, sees the buttons, chooses.

Put it in front of a JSON API and there are no buttons. It gets data and has to work out the rest. Which endpoint merges? Is merging allowed now? What does the request need? It answers from training, from documentation someone fed it, or from trying and reading the error. For a famous public API that mostly works. For a private API it starts with nothing. For an API that changed last week, it is confidently out of date.

The usual remedy is to wrap each API in hand-written tools. That works, and it is the islands again: one set of tools per API, each to be written, kept current and trusted. The agent is generic. Its connection to the world is not.

7HEART: a media type for agents

The browser’s answer was never to know more about sites. It was a media type that carries the controls. HEART takes the same route for agents. A HEART representation is JSON, so an agent reads it easily, and it brings back what JSON APIs dropped, element for element.

Links, by relation. Links sit in _links, named by what they mean: author, next, or a service’s own relation such as github:issues-list-comments. This is HAL, a format already used by Spring and others. A client follows a relation. It never builds an address.

Forms. Actions sit in _forms, each with a method, a target and its inputs described in JSON Schema, the same schema language that tool-using models and OpenAPI already use. A form is HTML’s <form>, for JSON.

"_forms": {
  "github:merge": {
    "title": "Merge this pull request",
    "method": "PUT",
    "_links": { "target": { "href": "…/pulls/20/merge" } },
    "schema": { "properties": {
      "merge_method": { "enum": ["merge", "squash", "rebase"] } } } } }

Forms that follow the state. A representation offers only the forms its current state allows. A pull request that can’t be merged has no merge form. Once it can be, the form appears. An open issue offers close; a closed one offers reopen instead. This is exactly what a web page does with its buttons, and exactly what a description of everything ever possible cannot do.

Why an act is absent. When a form is missing, the representation can link to a short explanation: “Branch protection blocks the merge: a required check or review is missing.” An agent can tell a person why, without guessing.

Refusal of anything not offered. A HEART service refuses an act it didn’t offer in that state, a write to a state that has changed since it was read, and inputs outside the schema. The rules the forms show are the rules the service enforces.

The name spells this out: Hypermedia, Enforced, for Agentic, Reliable Transactions.

8ARTIE: the generic agent

If HEART is the HTML of this story, ARTIE is the browser. It knows HEART: how to read a representation, follow a relation, fill in a form, send it with the right preconditions, and understand a refusal. It doesn’t know GitHub, a ticket desk or a basketball game. Those arrive in their own representations, as sites do.

The two stacks line up. On the Web a person chooses what to do, and the browser carries it out in terms of HTML. With HEART a model chooses among what is offered, and ARTIE carries it out in terms of HEART. The model is in the person’s seat, not the browser’s. It never types an address and never invents an action. It picks from the controls on screen, as a person picks a button.

That division is the point. The judgement stays with the model. The mechanics, and the guarantee that only offered acts are attempted, sit with a generic client that works for any HEART service. A new service needs a starting address, its bookmark, and nothing else.

9From browsing to a routine

People don’t only browse. When they do the same thing every week, they automate it: a bookmark, a macro, a recorded browser test. The browser makes this possible because each step is an act on a control the page offered.

ARTIE does the same, with one improvement. A person writes a goal in plain words: whenever a sowing plan can be merged, merge it; if it can’t be within five minutes, say why on it, unless that has been said already. ARTIE browses the goal once, with a model choosing at each step among what the service offers. Those choices become a script: the relations to follow, the forms to fill, the checks to make. The forms the script used are pinned with their fingerprints.

From then on the script runs alone, with no model. It is held to what it was offered: if the service stops offering a form, or changes one, the script stops and says so before it sends anything. A recorded macro would click on whatever is there. In our own trials, a goal like this one, watching a seed bench’s alerts, sowing plans and trays on GitHub, ran once with a model and then repeatedly with none.

10Old systems, new clients: the gateway

Most services won’t speak HEART soon, and they don’t have to. The Web met the same problem in the 1990s. Banks and airlines didn’t rewrite their mainframes. They put web front ends in front of them, programs that rendered the old system’s data as HTML so any browser could use it.

A HEART gateway is that front end for agents. Given GitHub’s published API description and a short connector, it renders GitHub’s answers as HEART: the state, the links lifted out of the data, and only the forms the state allows. On the way in, it checks every act against what it offered before GitHub hears it. GitHub doesn’t change. Anyone can run their own gateway, on a laptop, for the APIs they depend on.

11What it costs, and what it isn’t

A generic client is bought with a shared format, and that has a price. A service must speak HEART, or someone must put a gateway in front of it, and writing a good connector is real work. A HEART agent does only what the service offers. An agent with a shell and a dozen hand-written tools can do more things, in more places, with fewer promises about any of them.

That trade is the same one the Web made. A browser can’t do everything a native program can. It does a narrower thing for every site there is, safely, without being rebuilt for each. HEART and ARTIE make the same bargain for agents: the model chooses only among options the service vouches for, and only where judgement earns its place.

12Close

The Web never made people guess. Every page arrives with what you can do next and nothing you can’t, and one client reads them all. In 2008 Fielding said machines deserved the same, “or automaton”, years before anyone had an automaton that could use it.

Now we do. What it needs is not more knowledge of each API. It needs what the browser always had: the information and the controls, together.
